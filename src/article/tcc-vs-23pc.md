## TCC 和 2PC/3PC 的关系

TCC **借鉴了** 2PC 的思想，但**不是同一个东西**，核心差异在于：

| 对比项 | 2PC/3PC | TCC |
|--------|---------|-----|
| 层次 | **数据库/资源层**协议 | **业务应用层**协议 |
| 锁机制 | 持有数据库锁等待协调者 | 无数据库锁，业务自己预留资源 |
| 一致性 | 强一致性 | 最终一致性 |
| 实现者 | 数据库驱动/中间件 | **开发者自己写** Try/Confirm/Cancel |
| 性能 | 低（长时间持锁） | 高（锁粒度小） |

---

## 相似之处（为什么容易混淆）

```
2PC：  阶段1 准备(Prepare)  →  阶段2 提交/回滚(Commit/Rollback)
TCC：  阶段1 尝试(Try)      →  阶段2 确认/取消(Confirm/Cancel)
```

结构上确实都是"先预备，再决策"两段式，**TCC 是 2PC 思想在业务层的重新实现**。

---

## 一个例子感受区别

**转账 100 元场景：**

2PC 做法：
```
锁住 A 账户数据库行，等所有参与者准备好
→ 期间其他事务无法操作 A 账户
→ 强一致，但性能差
```

TCC 做法：
```
Try：    A 账户冻结 100 元（余额不变，冻结金额+100）
Confirm：冻结金额扣减，转入 B 账户
Cancel： 解冻 A 账户的 100 元

→ 没有数据库锁，业务代码控制，性能好
→ 中间状态（冻结中）是业务自己定义的
```

---

## 结论

> 2PC/3PC 是**数据库层**的强一致协议，属于刚性事务。
> TCC 是**业务层**对 2PC 思想的柔性实现，追求最终一致性，属于柔性事务。
>
> 两者形似神不似，原文的分类是准确的。
