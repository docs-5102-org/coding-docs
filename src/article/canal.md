## Canal 是什么？

**Canal** 是阿里巴巴开源的一个数据库变更订阅工具，专门用来**监听 MySQL 的 binlog 日志**，把数据库的增删改操作实时推送给下游系统。

---

## 它的原理

Canal 伪装成一个 **MySQL 的从库（Slave）**：

```
MySQL 主库
    ↓  正常情况：主库把 binlog 推给真实从库做主从同步
真实从库

    ↓  Canal 的做法：
Canal Server 伪装成从库，向主库发送 "我要同步" 的请求
主库以为 Canal 是一个从库，就把 binlog 推过来
Canal 解析 binlog → 提取出哪张表、哪行数据、改了什么
```

MySQL 本身感知不到 Canal 的存在，对它来说就是多了一个从库而已。

---

## 它能做什么

binlog 里记录了所有数据变更，Canal 解析后可以拿到：

- 哪张表发生了变更（`table_name`）
- 变更类型（INSERT / UPDATE / DELETE）
- 变更前的旧值 + 变更后的新值

拿到这些信息后，下游就可以做很多事：

| 用途 | 说明 |
|------|------|
| **缓存同步** | DB 更新 → Canal 感知 → 删除 Redis 缓存 |
| **搜索索引同步** | DB 更新 → Canal → 更新 Elasticsearch |
| **数据同步** | 主库数据实时同步到数据仓库（如 Hive） |
| **审计日志** | 记录所有数据变更历史 |

---

## 和延迟双删的关系

```
延迟双删：业务代码里手动删缓存，靠"等500ms"来兜底
            ↓ 缺点：可能删失败，延迟时间靠猜

Canal 方案：DB 一旦写成功，binlog 必然产生
            Canal 监听到 → 发消息给 MQ → 消费者删缓存
            ↓ 优点：删除动作与业务解耦，MQ 可重试，可靠性高
```

本质上 Canal 解决的是"**怎么可靠地感知到 DB 发生了变化**"这个问题，比在业务代码里手动处理更健壮。

---

## 简单理解

> Canal 就是一个"**数据库变更的监听器**"，MySQL 数据一变，它就知道，然后通知你去做后续处理。
