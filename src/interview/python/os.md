## 1 进程和线程的区别是什么

### 标准回答

- **进程** 是资源分配的基本单位，拥有独立的地址空间、文件描述符、虚拟内存等资源。
- **线程** 是 CPU 调度的基本单位，同一进程内的线程共享进程资源，但有各自的栈、寄存器和程序计数器。

### 核心区别

| 对比项 | 进程 | 线程 |
| :--- | :--- | :--- |
| 地址空间 | 相互独立 | 同一进程内共享 |
| 创建开销 | 大 | 小 |
| 切换开销 | 大 | 小 |
| 通信方式 | IPC | 直接共享内存 |
| 稳定性 | 一个进程崩溃通常不影响其他进程 | 一个线程崩溃可能导致整个进程退出 |

### Python 结合点

- `threading` 适合 **I/O 密集型** 任务，如爬虫、文件上传下载、网络请求。
- `multiprocessing` 适合 **CPU 密集型** 任务，如图像处理、数值计算、并行计算。
- CPython 存在 GIL，多线程不能真正并行执行 Python 字节码。

### 面试追问

- 为什么线程切换比进程切换更轻量？
- Python 里多线程和多进程该怎么选？
- 一个 Python Web 服务为什么常用多进程 + 协程模型？

## 2 什么是用户态和内核态

### 标准回答

操作系统为了保护系统资源，把运行权限分成两级：

- **用户态**：普通应用程序运行的状态，权限受限，不能直接访问硬件。
- **内核态**：操作系统内核运行的状态，权限最高，可以访问 CPU、内存、磁盘、网卡等硬件资源。

当程序执行系统调用，比如读文件、发网络包、申请内存时，会从用户态切换到内核态，完成后再返回用户态。

### Python 结合点

- `open()`、`read()`、`write()`、`socket.send()`、`socket.recv()` 本质都要经过系统调用。
- 协程高效的原因之一，是它减少了线程切换成本，但 **不能消除系统调用本身的开销**。

### 面试追问

- 系统调用为什么慢？

## 3 什么是上下文切换

### 标准回答

上下文切换指 CPU 从执行一个任务切换到执行另一个任务时，需要保存当前任务的上下文，并恢复下一个任务的上下文。上下文通常包括：

- 寄存器内容
- 程序计数器
- 栈指针
- 调度信息

### 类型

- **进程上下文切换**：涉及虚拟内存、页表等，成本较高。
- **线程上下文切换**：不需要切换整个地址空间，成本相对较低。
- **协程切换**：发生在用户态，通常更轻量。

### Python 结合点

- 线程数不是越多越好，线程过多会带来严重的上下文切换成本。
- `asyncio` 的一个优势就是减少线程切换，适合高并发 I/O。

- 为什么高并发场景下盲目加线程不一定更快？
- 协程为什么通常比线程更省资源？

## 4 线程同步方式有哪些

### 标准回答

常见线程同步方式有：

- 互斥锁 `mutex`
- 读写锁
- 信号量 `semaphore`
- 条件变量 `condition`
- 自旋锁

### Python 结合点

Python `threading` 常见同步原语：

```python
import threading

lock = threading.Lock()
rlock = threading.RLock()
semaphore = threading.Semaphore(3)
condition = threading.Condition()
event = threading.Event()
```

### 面试重点

- `Lock`：同一时刻只允许一个线程进入临界区。
- `RLock`：可重入锁，同一线程可以重复加锁。
- `Semaphore`：控制同时访问某类资源的线程数量。
- `Condition`：线程间等待和通知。
- `Event`：一个线程发信号，多个线程感知状态变化。

### `Lock` 和 `RLock` 有什么区别？

**`Lock` 不可重入，`RLock` 可重入。**

---

**Lock：同一线程加锁两次，直接死锁**

```python
import threading

lock = threading.Lock()

def foo():
    lock.acquire()
    lock.acquire()  # 死锁！等待自己释放，永远等不到
    lock.release()
    lock.release()
```

---

**RLock：同一线程可以多次加锁**

```python
import threading

rlock = threading.RLock()

def foo():
    rlock.acquire()  # 计数 1
    rlock.acquire()  # 计数 2，不会阻塞
    rlock.release()  # 计数 1
    rlock.release()  # 计数 0，真正释放
```

RLock 内部维护**计数器 + 持有线程**：

```
acquire() → 判断是否是当前线程持有
    ├─ 是 → 计数 +1，直接通过
    └─ 否 → 阻塞等待

release() → 计数 -1
    └─ 计数归零 → 真正释放，其他线程可以抢
```

---

**RLock 典型场景：递归函数加锁**

```python
rlock = threading.RLock()

def factorial(n):
    with rlock:          # 每层递归都会 acquire
        if n == 1:
            return 1
        return n * factorial(n - 1)  # 递归，同一线程再次 acquire
```

用 `Lock` 这里直接死锁，用 `RLock` 正常运行。

---

**对比：**

```
          Lock        RLock
同一线程重入   死锁         ✓ 允许
性能          稍快         稍慢（多维护计数器）
适用场景      简单互斥      递归、嵌套加锁
```

没有递归或嵌套加锁需求，用 `Lock` 就够了。

### Python 字典操作是线程安全的吗？

**单个操作是安全的，复合操作不安全。**

---

原因是 CPython 有 **GIL（全局解释器锁）**，保证每条字节码原子执行：

```python
d = {}

# 这些单步操作，GIL 保证原子性，线程安全
d['key'] = value    # 安全
x = d['key']        # 安全
d.pop('key')        # 安全
```

---

**但复合操作不安全：**

```python
# 不安全！读-判断-写 是三步，GIL 可能在中间切换线程
if 'key' not in d:        # 线程A执行到这
                          # 线程B也执行到这，key 都不存在
    d['key'] = value      # A和B都写入，后写的覆盖前写的
```

```python
# 不安全！读-改-写 三步
d['count'] = d['count'] + 1  # 可能丢失更新
```

---

**加锁解决：**

```python
import threading

lock = threading.Lock()
d = {}

# 复合操作加锁保护
with lock:
    if 'key' not in d:
        d['key'] = value

with lock:
    d['count'] = d['count'] + 1
```

---

**或者用线程安全的替代方案：**

```python
from collections import defaultdict
import queue

# defaultdict 避免判断 key 是否存在
d = defaultdict(int)
d['count'] += 1  # 但 += 本身仍不安全，还是要加锁

# 线程间传数据用 Queue，天然线程安全
q = queue.Queue()
q.put(item)
q.get()
```

---

**总结：**

```
单步操作（get/set/pop）   → GIL 保护，安全
复合操作（判断+写/读+改）  → 需要手动加锁
跨线程传数据              → 用 Queue
```

### 为什么加锁会影响性能？

加锁影响性能的原因有几个：

---

**1. 线程阻塞等待**

```
线程A 持有锁，执行中...
线程B 想要锁 → 阻塞挂起，什么都干不了
线程C 想要锁 → 阻塞挂起，什么都干不了

A 释放锁 → B/C 其中一个才能继续
```

本来可以并行的线程，变成了排队串行执行。

---

**2. 上下文切换开销**

```python
with lock:
    d['count'] += 1
```

```
线程B 被挂起
    │
    ├─ 保存 B 的寄存器、栈、程序计数器...
    ├─ 切换到其他线程
    ├─ 恢复其他线程的上下文
    └─ B 唤醒时再切回来，再保存/恢复一次

每次切换 = 几微秒的纯开销，高并发下累积很可观
```

---

**3. 锁竞争越激烈，性能越差**

```
低竞争（锁很快释放）：影响小
高竞争（锁持有时间长，大量线程等待）：性能急剧下降

极端情况：所有线程都在等一把锁
          并行程序 → 比单线程还慢（多了切换开销）
```

---

**4. CPU 缓存失效**

```
线程A 在 CPU核心1 修改了数据
线程B 在 CPU核心2 读取同一数据

→ 核心2 的缓存失效，必须从内存重新读
→ 内存访问比缓存慢 100 倍
```

---

**所以优化方向是减少锁的粒度：**

```python
# 粗粒度：整个操作都锁住
with lock:
    result = expensive_compute()  # 计算很慢，其他线程全在等
    d['key'] = result

# 细粒度：只锁必要的部分
result = expensive_compute()      # 计算不加锁，并行执行
with lock:
    d['key'] = result             # 只锁写入的一瞬间
```

## 什么是死锁，死锁产生的条件是什么

### 标准回答

死锁是指多个进程或线程互相等待对方持有的资源，导致所有参与者都无法继续执行。

### 死锁的四个必要条件

1. **互斥条件**：资源一次只能被一个线程或进程占用。
2. **请求并保持条件**：已经持有资源的线程还在请求新资源。
3. **不可剥夺条件**：资源不能被强制回收。
4. **循环等待条件**：存在资源等待环。

### Python 结合点

典型错误写法：

```python
import threading

lock_a = threading.Lock()
lock_b = threading.Lock()
```

线程 1 先拿 `lock_a` 再等 `lock_b`，线程 2 先拿 `lock_b` 再等 `lock_a`，就可能死锁。

### 避免死锁的方法

- 统一加锁顺序
- 一次性申请所有资源
- 使用超时机制
- 减少锁的粒度
- 尽量避免嵌套锁

### 活锁和死锁有什么区别？

**死锁是卡住不动，活锁是一直动但没有进展。**

---

**死锁：互相等待，全部阻塞**

```python
import threading

lock_a = threading.Lock()
lock_b = threading.Lock()

def thread1():
    lock_a.acquire()  # 拿到 A
    lock_b.acquire()  # 等待 B ← 永远等不到
    
def thread2():
    lock_b.acquire()  # 拿到 B
    lock_a.acquire()  # 等待 A ← 永远等不到
```

```
线程1 持有A，等待B
线程2 持有B，等待A
→ 双方都阻塞，程序卡死，CPU 占用 0%
```

---

**活锁：互相谦让，一直在动但没有进展**

```python
def thread1():
    while True:
        lock_a.acquire()
        if not lock_b.acquire(blocking=False):
            lock_a.release()  # 发现拿不到B，主动放弃A
            continue          # 重试
            
def thread2():
    while True:
        lock_b.acquire()
        if not lock_a.acquire(blocking=False):
            lock_b.release()  # 发现拿不到A，主动放弃B
            continue          # 重试
```

> lock.acquire(blocking=True)   # 默认，阻塞等待，直到拿到锁
> lock.acquire(blocking=False)  # 非阻塞，立即返回，拿不到就返回 False

```
线程1 拿到A，发现B被占，放弃A，重试
线程2 拿到B，发现A被占，放弃B，重试
线程1 拿到A，发现B被占，放弃A，重试
...
→ 双方都在运行，CPU 占用 100%，但永远没有进展
```

---

**对比：**

```
          死锁              活锁
状态      阻塞，不动         一直运行
CPU占用   0%               100%
发现难度  容易（程序卡死）    难（程序看起来在运行）
解决方案  固定加锁顺序        加随机退避时间
```

---

**活锁的解决：加随机等待，打破同步节奏**

```python
import random
import time

def thread1():
    while True:
        lock_a.acquire()
        if not lock_b.acquire(blocking=False):
            lock_a.release()
            time.sleep(random.uniform(0, 0.1))  # 随机等待，错开重试时机
            continue
```

### Python 如何给锁加超时？

用 `acquire(timeout=n)` 或 `with` 语句配合 `acquire`：

---

**基本用法：**

```python
import threading

lock = threading.Lock()

# acquire 返回 bool，True 表示拿到锁，False 表示超时
if lock.acquire(timeout=3):   # 最多等 3 秒
    try:
        # 拿到锁，执行业务
        pass
    finally:
        lock.release()
else:
    print("超时，没拿到锁")   # 超时处理
```

---

**实际场景：防止死锁**

```python
import threading
import time

lock_a = threading.Lock()
lock_b = threading.Lock()

def thread1():
    while True:
        if lock_a.acquire(timeout=1):
            try:
                if lock_b.acquire(timeout=1):  # 拿不到就超时放弃
                    try:
                        print("thread1 拿到两把锁")
                        return
                    finally:
                        lock_b.release()
                else:
                    print("thread1 等待 B 超时，重试")
            finally:
                lock_a.release()
        time.sleep(0.1)  # 随机退避，避免活锁
```

---

**三种拿锁方式对比：**

```python
lock.acquire()              # 一直等，可能永久阻塞
lock.acquire(blocking=False)  # 立即返回，拿不到直接 False
lock.acquire(timeout=3)     # 最多等 3 秒，超时返回 False
```

超时是防死锁的常用手段，配合重试和随机退避效果最好。

## 6 什么是僵尸进程和孤儿进程

### 标准回答

- **僵尸进程**：子进程已经结束，但父进程没有调用 `wait()` / `waitpid()` 回收其退出状态，导致子进程 PCB 仍然存在。
- **孤儿进程**：父进程先退出，子进程还在运行，此时子进程会被 `init` 或其他托管进程接管。

### Python 结合点

- 使用 `multiprocessing` 或 `subprocess` 时，如果不正确回收子进程，可能出现僵尸进程。
- 需要调用 `join()`、`wait()` 等方法回收资源。

```python
from multiprocessing import Process

def task():
    print("child process")

p = Process(target=task)
p.start()
p.join()
```

### 僵尸进程为什么占资源？

进程已经执行完毕，但父进程没有调用 `wait()` 回收它，内核还保留着它的进程表条目（PID、退出状态、运行时间等），等父进程来读。这个条目本身很小，但 PID 被占用，系统 PID 耗尽就无法创建新进程。

---

### 僵尸进程和正在运行的进程的本质区别？

```
正在运行的进程：占内存、CPU、文件描述符，有实际代码在执行
僵尸进程：代码已执行完，内存/CPU/文件描述符全部释放，只剩一条进程表记录
```

僵尸进程已经"死了"，只是死亡证明还没被父进程领走。

## 7 进程间通信（IPC）有哪些方式

### 标准回答

常见 IPC 方式包括：

- 管道 `pipe`
- 命名管道 `FIFO`
- 消息队列
- 共享内存
- 信号量
- 信号 `signal`
- Socket

### Python 结合点

`multiprocessing` 提供了多种进程通信方式：

```python
from multiprocessing import Process, Queue

def producer(q):
    q.put("hello")

def consumer(q):
    print(q.get())

q = Queue()
p1 = Process(target=producer, args=(q,))
p2 = Process(target=consumer, args=(q,))
p1.start()   # 启动 p1，主进程和 p1 同时运行
p2.start()   # 启动 p2，主进程和 p1 p2 同时运行
p1.join()    # 主进程在这里等，直到 p1 执行完
p2.join()    # 主进程在这里等，直到 p2 执行完
# 确保 p1 p2 都结束后，主进程才继续
print("所有子进程结束")
```

### 面试总结

- 同机进程通信追求性能时，可以考虑共享内存。
- 跨机器通信一般使用 Socket、RPC、消息队列。
- Python 多进程场景里最常见的是 `Queue`、`Pipe`、Manager。

## 8 什么是分页和分段

### 标准回答

- **分页**：把虚拟内存划分成固定大小的页，把物理内存划分成同样大小的页框。
- **分段**：按照逻辑模块划分内存，例如代码段、数据段、栈段。

### 区别

| 对比项 | 分页 | 分段 |
| :--- | :--- | :--- |
| 划分方式 | 固定大小 | 按逻辑意义划分 |
| 目的 | 提高内存利用率 | 便于逻辑管理 |
| 地址空间 | 一维 | 二维 |
| 碎片问题 | 可能有内部碎片 | 可能有外部碎片 |

### Python 结合点

Python 开发通常不直接操作分页和分段，但会被以下问题影响：

- 大对象申请内存失败
- 内存碎片
- 页缺失导致性能抖动
- 多进程 fork 后的写时复制开销

## 9 什么是虚拟内存

### 标准回答

虚拟内存是操作系统为每个进程提供的一套看起来连续、独立、比物理内存更大的地址空间。程序使用的是虚拟地址，操作系统和 MMU 负责把虚拟地址映射为物理地址。

### 作用

- 进程隔离
- 提高内存利用率
- 支持比物理内存更大的程序运行
- 支持按需加载

### Python 结合点

- Python 进程看到的是自己的虚拟地址空间。
- `fork()` 后父子进程一开始共享物理页，写入时才复制，这就是 **写时复制（Copy-on-Write）**。
- 大型 Python 服务中，预加载数据再 fork worker，是常见优化方式。

## 10 页面置换算法有哪些

### 标准回答

当发生缺页异常且内存已满时，操作系统需要选择一个页面换出，常见算法有：

- **OPT**：未来最长时间不再使用的页面先淘汰，理论最优，但无法真实实现。
- **FIFO**：最早进入内存的页面先淘汰，实现简单，但可能出现 Belady 异常。
- **LRU**：最近最久未使用的页面先淘汰，实践中效果较好。
- **Clock**：LRU 的近似实现，综合性能较好。

### Python 结合点

- `functools.lru_cache` 的命名就来自 LRU 思想。
- 大数据处理时，如果工作集远超内存，频繁缺页会导致严重抖动。

## 11 什么是缓冲区、零拷贝和 DMA

### 标准回答

- **缓冲区**：操作系统为了平衡生产者和消费者速度差异而设置的临时存储区。
- **DMA**：直接内存访问，允许外设在不频繁打断 CPU 的情况下直接和内存交换数据。
- **零拷贝**：尽量减少数据在内核态和用户态之间、以及内存缓冲区之间的复制次数。

### Python 结合点

- 文件上传、下载、网络转发时，数据复制次数越少越高效。
- Python 中 `sendfile()` 背后就利用了零拷贝思想。

```python
import os
```

常见服务器会利用内核能力提升静态文件传输效率，而不是用户态循环 `read` + `send`。

## 12 select、poll、epoll 有什么区别

### 标准回答

三者都是 **I/O 多路复用** 机制，用一个线程同时监听多个文件描述符。

### 对比总结

| 对比项 | select | poll | epoll |
| :--- | :--- | :--- | :--- |
| 文件描述符数量限制 | 有 | 无固定上限 | 无固定上限 |
| 数据结构 | 位图 | 链表/数组 | 红黑树 + 就绪链表 |
| 每次调用是否需要遍历全部 fd | 需要 | 需要 | 不需要全量遍历 |
| 内核到用户态拷贝 | 每次都要拷贝全集合 | 每次都要拷贝全集合 | 只返回就绪事件 |
| 适用场景 | 连接数少 | 中等规模 | 高并发 |

### Python 结合点

- `selectors` 模块对底层多路复用做了封装，会自动选择平台最佳实现。
- `asyncio`、`uvloop`、Tornado、gevent 等框架底层都依赖事件循环和 I/O 多路复用。

```python
import selectors

sel = selectors.DefaultSelector()
```

### 面试追问

- 为什么 `epoll` 更适合高并发？
- `epoll` 一定比 `select` 快吗？
- Windows 上为什么通常不是 `epoll`？

## 13 什么是水平触发（LT）和边缘触发（ET）

### 标准回答

- **水平触发 LT**：只要文件描述符处于可读或可写状态，就会持续通知。
- **边缘触发 ET**：只有状态从不可读变为可读、从不可写变为可写时才通知一次。

### 面试重点

- LT 更容易编程，不容易漏事件。
- ET 性能更好，但必须一次尽可能把数据读完或写完，通常要配合非阻塞 I/O 使用。

### Python 结合点

- 大多数 Python 开发者会用成熟框架，不直接操作 ET/LT。
- 但面试时要知道：**ET 编程更复杂，错误使用容易导致连接“假死”**。

### 面试追问

- 为什么 ET 必须配合非阻塞套接字？
- ET 模式下为什么要循环读到 `EAGAIN`？

## 14 阻塞 I/O、非阻塞 I/O、同步 I/O、异步 I/O 的区别

### 标准回答

这个问题经常被混淆，需要分两个维度理解。

### 维度一：阻塞与非阻塞

- **阻塞 I/O**：调用后当前线程会一直等到数据准备好。
- **非阻塞 I/O**：如果数据没准备好，会立即返回错误或状态码，不会一直等待。

### 维度二：同步与异步

- **同步 I/O**：数据准备好后，仍然需要应用自己把数据从内核拷贝到用户空间。
- **异步 I/O**：内核会把数据准备和拷贝都做完，完成后通知应用。

### Python 结合点

- `socket` 默认是阻塞 I/O。
- `asyncio` 不是内核级异步 I/O 的完整等价物，它本质上还是 **事件驱动 + 非阻塞 I/O + 回调/协程调度**。
- 真正意义上的异步 I/O，面试里可以提 `io_uring`、AIO 等，但 Python 日常业务开发接触较少。

### 面试追问

- `asyncio` 到底算同步还是异步？
- 非阻塞 I/O 为什么还要配合 I/O 多路复用？

## 15 线程池和进程池的适用场景

### 标准回答

- **线程池**：适合 I/O 密集型任务，减少线程频繁创建销毁的开销。
- **进程池**：适合 CPU 密集型任务，利用多核绕过 GIL。

### Python 示例

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor
```

### 如何选

- 网络请求、文件读写、爬虫：线程池。
- 大量计算、图像处理、模型推理前处理：进程池。
- 如果任务本身大量调用 C 扩展且会释放 GIL，也可能线程池有效。

## 16 什么是 GIL，它为什么存在

### 标准回答

GIL 是 **Global Interpreter Lock**，即全局解释器锁。它是 CPython 解释器中的一把互斥锁，保证任意时刻只有一个线程在执行 Python 字节码。

### 为什么会有 GIL

本质原因是 CPython 的内存管理和对象模型不是为真正多线程并行设计的，尤其是引用计数机制需要一个简单的全局保护。

### 影响

- 多线程对 I/O 密集型任务仍然有效。
- 多线程对 CPU 密集型纯 Python 代码效果差。

### Python 结合点

- 这是 Python 面试的高频题，通常会追问和多进程、协程的关系。

### 面试追问

- GIL 会在什么时机释放？
- GIL 和线程安全是一回事吗？
- Python 3.13 free-threaded 版本意味着什么？

## 17 协程为什么适合高并发 I/O

### 标准回答

协程是用户态的轻量级并发单元，切换由程序自己控制，不需要像线程那样频繁进入内核态进行调度，因此开销更小。

### 优势

- 切换轻量
- 内存占用小
- 非常适合大量网络连接
- 能把异步回调写成同步风格

### Python 结合点

```python
import asyncio

async def fetch():
    await asyncio.sleep(1)
```

- `asyncio` 适合高并发网络 I/O、RPC、消息消费、数据库访问。
- 不适合纯 CPU 密集型任务。

## 18 文件描述符是什么

### 标准回答

文件描述符（fd）是操作系统给进程维护的一个整数索引，用来表示一个已经打开的文件、Socket、管道等 I/O 资源。

### 面试重点

## 19 什么是软链接和硬链接

### 标准回答

- **硬链接**：多个文件名指向同一个 inode，本质上是同一份文件数据。
- **软链接**：类似快捷方式，保存的是目标路径。

| 是否能链接目录 | 通常不允许 | 可以 |
| 删除源文件后 | 仍可访问数据 | 链接失效 |

### Python 结合点

```python
import os

os.symlink("source.txt", "link.txt")
```

## 20 什么是缓存和缓冲，它们的区别是什么

### 标准回答

- **缓存（cache）**：为了解决速度问题，把热点数据保存到更快的存储介质中，核心目标是提升访问速度。
- **缓冲（buffer）**：为了解决速度不匹配问题，临时存放数据，核心目标是平滑数据流。

### 例子

- CPU L1/L2/L3 Cache 是缓存。
- 磁盘读写缓冲区、网络发送缓冲区是缓冲。
- Redis 更接近缓存。

### Python 结合点

- 文件对象默认有用户态缓冲。
- Web 服务会使用本地缓存、Redis 缓存。
- `functools.lru_cache` 是典型缓存。

## 21 什么是 CPU 密集型和 I/O 密集型任务

### 标准回答

- **CPU 密集型**：任务主要时间花在计算上，CPU 利用率高。
- **I/O 密集型**：任务主要时间花在等待磁盘、网络、数据库等 I/O 上。

### 常见例子

- I/O 密集型：爬虫、API 聚合、日志写入、数据库读写。

## 22 什么是写时复制（Copy-on-Write）

### 标准回答

写时复制指的是：多个进程最开始共享同一份物理内存页，只有某个进程真正写入时，操作系统才复制出新的页给它使用。

### 优势

- 减少初始内存复制成本
- 提升 `fork()` 性能

### Python 结合点

- Gunicorn、uWSGI 等预 fork 模型都会利用这个特性。
- 父进程先加载应用和部分数据，再 fork 子进程，可以节省内存并加快启动。
- 但如果子进程频繁修改共享数据，仍然会发生大量实际复制。

### 面试追问

## 24 mmap 是什么，有什么优缺点

### 标准回答

`mmap` 是内存映射文件机制，它把文件内容映射到进程虚拟地址空间，程序可以像访问内存一样访问文件数据。

### 优点

- 减少用户态和内核态数据拷贝
- 适合随机访问大文件
- 可用于进程间共享内存

### 缺点

- 映射管理复杂
- 不适合所有场景
- 大量随机缺页时性能可能波动

### Python 结合点

```python
import mmap
```

常用于：

- 大文件读取
- 日志分析
- 高性能 IPC
