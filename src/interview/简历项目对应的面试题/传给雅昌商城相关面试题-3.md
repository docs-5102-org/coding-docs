# Dubbo 与 Zookeeper 面试题解答

## 36. 为什么选择 Dubbo 作为 RPC 框架？相比 Spring Cloud 有什么区别?

### 选择 Dubbo 的理由

Dubbo 是一个高性能的 RPC 框架,在以下场景特别适用:

**性能优势**: Dubbo 基于 TCP 长连接和二进制序列化(如 Hessian2),性能比基于 HTTP 的 REST 调用高出很多,适合对性能要求严苛的场景。

**服务治理成熟**: 提供了丰富的服务治理功能,包括负载均衡、服务降级、限流、容错等,这些都是框架内置的。

**适合大规模微服务**: 在服务数量庞大、调用频繁的场景下,Dubbo 的性能和资源占用优势明显。

### Dubbo vs Spring Cloud 核心区别

**通信协议**: Dubbo 默认使用 Dubbo 协议(TCP + 二进制序列化),Spring Cloud 使用 HTTP/REST(基于 Feign)。Dubbo 性能更高但跨语言支持较弱。

**架构理念**: Dubbo 是 RPC 框架,强调高性能远程调用;Spring Cloud 是微服务全家桶,提供配置中心、网关、链路追踪等完整生态。

**服务注册中心**: Dubbo 常用 Zookeeper、Nacos;Spring Cloud 使用 Eureka、Consul 或 Nacos。

**社区生态**: Spring Cloud 与 Spring 生态无缝集成,学习曲线平缓;Dubbo 更专注于 RPC 性能,阿里系公司使用较多。

**适用场景**: 如果追求极致性能、内部系统调用,选 Dubbo;如果需要完整微服务解决方案、跨语言调用,选 Spring Cloud。

## 37. Dubbo 的服务注册与发现流程是怎样的？Zookeeper 在其中扮演什么角色?

### 服务注册与发现流程

**服务启动阶段**: Provider 启动时,将服务接口、IP、端口、协议等信息注册到 Zookeeper 的特定节点路径(如 `/dubbo/com.example.UserService/providers`)。

**订阅服务**: Consumer 启动时,向 Zookeeper 订阅所需服务,获取 Provider 列表,并在本地缓存。

**动态感知**: Zookeeper 通过 Watcher 机制,当 Provider 上下线时,实时通知 Consumer 更新本地缓存的服务列表。

**服务调用**: Consumer 根据负载均衡策略从本地缓存的 Provider 列表中选择一个发起 RPC 调用。

**监控统计**: Monitor 监控中心可以订阅所有服务,统计调用次数和调用时间。

### Zookeeper 的角色

**注册中心**: 存储服务元数据,提供服务注册和查询功能。Zookeeper 的 ZNode 结构天然适合表达服务的层级关系。

**配置中心**: 存储 Dubbo 的动态配置,如路由规则、降级策略等。

**协调服务**: 利用临时节点特性,Provider 断开连接时节点自动删除,实现服务自动下线。

**通知机制**: 通过 Watcher 机制实现服务变更的实时推送,无需轮询。

## 38. Dubbo 的负载均衡策略有哪些？你们使用的是哪种？为什么?

### Dubbo 内置负载均衡策略

**Random LoadBalance(随机,默认)**: 按权重随机选择,权重相同则完全随机。优点是简单高效,在调用量大时表现稳定。

**RoundRobin LoadBalance(轮询)**: 按权重轮询,但可能存在慢提供者累积请求的问题。

**LeastActive LoadBalance(最少活跃调用数)**: 优先调用活跃数最少的提供者,使慢提供者收到更少请求,适合响应时间差异大的场景。

**ConsistentHash LoadBalance(一致性哈希)**: 相同参数的请求总是发到同一提供者,适合有状态服务或需要利用本地缓存的场景。

### 实际使用建议

**常规场景**: 使用默认的 Random 策略,配合权重配置,简单有效。

**响应时间差异大**: 使用 LeastActive,避免慢节点成为瓶颈。

**需要会话保持**: 使用 ConsistentHash,但要注意提供者变化时的数据倾斜问题。

**配置示例**: 可以在服务、方法级别单独配置,如 `@Reference(loadbalance = "leastactive")`

## 39. 如果 Zookeeper 集群出现脑裂,会对服务调用产生什么影响？如何预防?

### 脑裂现象及影响

**什么是脑裂**: 网络分区导致 Zookeeper 集群分裂成多个子集群,每个子集群都认为自己是完整集群,可能产生多个 Leader。

**对 Dubbo 的影响**: 

- 不同分区的 Consumer 可能看到不同的 Provider 列表,导致部分服务调用失败
- Provider 在某个分区注册成功,但其他分区的 Consumer 无法发现
- 可能出现服务重复注册或注册丢失的情况

**实际影响有限**: Dubbo Consumer 有本地缓存机制,即使注册中心不可用,仍可使用缓存的 Provider 列表继续调用,所以短时间脑裂影响较小。

### 预防措施

**部署奇数节点**: Zookeeper 使用过半机制,部署 3、5、7 个节点,确保只有一个分区能达到过半数形成有效集群。

**网络隔离**: 将 Zookeeper 节点部署在不同机房或可用区,避免单点网络故障导致分区。

**监控告警**: 实时监控 Zookeeper 集群状态,发现节点失联或选举异常及时告警。

**直连降级**: 配置 Dubbo 直连模式作为降级方案,绕过注册中心直接调用。

**多注册中心**: 使用 Dubbo 多注册中心特性,同时注册到 Zookeeper 和 Nacos,提高可用性。

## 40. Dubbo 接口的超时时间、重试次数是如何配置的？如何避免服务雪崩?

### 超时和重试配置

**超时时间配置**:

```java
// Provider 端配置
@Service(timeout = 3000)
public class UserServiceImpl implements UserService {}

// Consumer 端配置(优先级更高)
@Reference(timeout = 2000)
private UserService userService;

// 方法级别配置(优先级最高)
@Reference(methods = {@Method(name = "queryUser", timeout = 1000)})
```

**重试次数配置**:

```java
// retries 不包含第一次调用,retries=2 表示最多调用 3 次
@Reference(retries = 2)
private UserService userService;

// 幂等方法可以重试,非幂等方法建议 retries=0
@Reference(methods = {
    @Method(name = "queryUser", retries = 2),
    @Method(name = "createUser", retries = 0)
})
```

**配置优先级**: 方法级 > 接口级 > 全局配置,Consumer 端配置优先于 Provider 端。

### 避免服务雪崩的措施

**合理设置超时**: 根据接口响应时间设置合理超时,避免过长超时占用线程资源。快速失败优于长时间等待。

**限流保护**: 使用 Dubbo 的 TPS Limiter 或接入 Sentinel,限制每个服务的最大并发数,防止突发流量压垮服务。

**熔断降级**: 集成 Hystrix 或 Sentinel,当错误率达到阈值时自动熔断,避免持续调用失败的服务。

**线程隔离**: Consumer 端使用独立线程池处理不同服务调用,避免一个服务故障影响其他服务。

**优雅降级**: 提供降级方案,如返回缓存数据、默认值或友好提示,而不是直接抛异常。

**集群容错**: 合理配置 Dubbo 的 Cluster 容错策略,如 Failfast(快速失败)、Failsafe(失败安全)、Failback(失败自动恢复)等。

**监控预警**: 实时监控接口调用成功率、响应时间、超时次数,及时发现问题并预警。
