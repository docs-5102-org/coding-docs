## 21. ELK 日志采集架构搭建与配置

---

#### ✅ **1. Application（业务应用）**

你的应用程序（Java / Go / PHP / Node 等）会产生日志，比如：

* 访问日志
* 错误日志
* 调试日志
* 业务日志

这些日志通常写到文件里：

```
/var/logs/app.log
```

这些 log files 就是整个 ELK 流程的 **源头**。

---

#### ✅ **2. Filebeat（轻量级日志采集器）**

Filebeat 的作用：
**负责实时采集日志文件，并把日志发送到 Kafka（或 Logstash）中。**

特点：

* 占用非常少的资源（比 Logstash 轻量得多）
* 自动追踪文件末尾（tail -f）
* 自动断点续传（不会丢日志）
* 发送到 Kafka、Logstash、Elasticsearch 都可以

你可以理解成：

> Filebeat = 日志搬运工

---

#### ✅ **3. Kafka（日志缓冲队列）**

Kafka 在日志系统中的作用非常关键：

* **削峰填谷**（日志暴增时保证不丢）
* **持久化消息**（异地恢复方便）
* **多消费者模型**（一个日志可同时给多个系统消费）
* **解耦** Filebeat ↔ Logstash

为什么要加 Kafka？

因为：

> Logstash 性能一般，但 Filebeat 非常快；
> Kafka 用来做缓冲区，防止 Logstash 撑爆。

---

#### ✅ **4. Logstash（日志解析与加工）**

Logstash 的作用：

* 解析日志文本（如 Nginx / 应用 / JSON）
* 日志格式化（提取字段）
* 数据清洗（过滤无用内容）
* 添加字段（IP 解析、地理位置等）
* 最终结构化输出到 Elasticsearch

可以理解成：

> Logstash = 日志处理器（清洗→解析→格式化）

举例：
原始日志：

```
2024-12-01 12:10:22 ERROR productId=1234 user=5678
```

Logstash 可以解析出结构化数据：

```json
{
  "timestamp": "2024-12-01 12:10:22",
  "level": "ERROR",
  "productId": 1234,
  "user": 5678
}
```

---

#### ✅ **5. Elasticsearch（日志存储 + 搜索引擎）**

Elasticsearch 是 ELK 的核心。

作用：

* **存储结构化日志数据（分布式集群）**
* **提供全文搜索、聚合分析**
* **高并发写入、高速查询**

你所有的日志、数据分析、监控告警都会从 ES 读取。

可以搜索：

* 某用户今天的所有操作
* 某服务的报错情况
* 某类接口的耗时分布
* 全链路日志信息

> ES 就是日志的大仓库 + 搜索引擎。

---

#### ✅ **6. Kibana（可视化界面）**

Kibana 负责展示 Elasticsearch 的数据：

* 日志搜索 UI
* 服务健康监控
* 自定义 Dashboard
* 实时图表（柱状图、折线图、饼图）
* 报错分析
* 异常告警

也就是你看到所有日志分析图表、Dashboard 的地方。

> Kibana = 日志可视化界面

---

#### 📌 最终流程总结

按图的顺序：

```
Application → 产生日志文件
       ↓
Filebeat → 读取日志并发送
       ↓
Kafka → 消息缓冲、解耦
       ↓
Logstash → 日志解析、过滤、处理
       ↓
Elasticsearch → 存储 + 检索
       ↓
Kibana → 展示和分析
```

一句话概括：

> Filebeat 负责采集
> Kafka 负责缓冲
> Logstash 负责处理
> ES 负责存储和搜索
> Kibana 负责展示

### Logstash 配置详解

```ruby
# logstash.conf - 完整配置示例

# 输入配置
input {
  # 从 Kafka 消费日志
  kafka {
    bootstrap_servers => "kafka1:9092,kafka2:9092,kafka3:9092"
    topics => ["app-logs", "error-logs", "access-logs"]
    group_id => "logstash-consumer-group"
    consumer_threads => 3
    codec => json
    # 自动提交偏移量
    auto_offset_reset => "latest"
  }
  
  # 直接从 Beats 接收
  beats {
    port => 5044
    ssl => true
    ssl_certificate => "/etc/logstash/certs/logstash.crt"
    ssl_key => "/etc/logstash/certs/logstash.key"
  }
}

# 过滤配置
filter {
  # 解析 JSON 格式日志
  if [type] == "app-log" {
    json {
      source => "message"
      target => "log_data"
    }
    
    # 时间戳解析
    date {
      match => ["timestamp", "yyyy-MM-dd HH:mm:ss.SSS", "ISO8601"]
      target => "@timestamp"
    }
    
    # 提取字段
    grok {
      match => {
        "message" => "%{TIMESTAMP_ISO8601:timestamp} \[%{DATA:thread}\] %{LOGLEVEL:level} %{DATA:logger} - %{GREEDYDATA:msg}"
      }
    }
  }
  
  # 处理异常堆栈
  if [level] == "ERROR" {
    mutate {
      add_tag => ["error"]
    }
    
    # 提取异常类型
    grok {
      match => {
        "msg" => "(?<exception_type>[a-zA-Z.]+Exception)"
      }
      tag_on_failure => []
    }
  }
  
  # 添加地理位置信息
  if [client_ip] {
    geoip {
      source => "client_ip"
      target => "geoip"
    }
  }
  
  # 字段类型转换
  mutate {
    convert => {
      "response_time" => "integer"
      "status_code" => "integer"
    }
    remove_field => ["message", "host"]
  }
  
  # UA 解析
  if [user_agent] {
    useragent {
      source => "user_agent"
      target => "ua"
    }
  }
}

# 输出配置
output {
  # 根据日志类型路由到不同索引
  if [type] == "app-log" {
    elasticsearch {
      hosts => ["es1:9200", "es2:9200", "es3:9200"]
      index => "app-logs-%{+YYYY.MM.dd}"
      user => "elastic"
      password => "${ES_PASSWORD}"
      # 批量配置优化
      flush_size => 500
      idle_flush_time => 5
    }
  }
  
  if [level] == "ERROR" {
    elasticsearch {
      hosts => ["es1:9200", "es2:9200", "es3:9200"]
      index => "error-logs-%{+YYYY.MM.dd}"
    }
    
    # 错误日志同时发送告警
    http {
      url => "http://alert-service/api/alert"
      http_method => "post"
      format => "json"
    }
  }
  
  # 调试输出
  # stdout { codec => rubydebug }
}
```

```java
import org.apache.skywalking.apm.toolkit.trace.*;
import org.springframework.stereotype.Service;

@Service
public class OrderService {
    
    // 自定义 Trace
    @Trace
    @Tag(key = "order_id", value = "arg[0]")
    public OrderDTO createOrder(String orderId, OrderRequest request) {
        // TraceContext 获取链路信息
        String traceId = TraceContext.traceId();
        log.info("Processing order, traceId: {}", traceId);
        
        // 添加自定义标签
        Tags.ofKey("user_id").set(request.getUserId());
        Tags.ofKey("amount").set(String.valueOf(request.getAmount()));
        
        // 业务逻辑
        validateOrder(request);
        OrderDTO order = saveOrder(orderId, request);
        notifyInventory(order);
        
        return order;
    }
    
    // 子跨度
    @Trace
    @Tag(key = "operation", value = "returnedObj")
    private void validateOrder(OrderRequest request) {
        // 创建本地跨度
        ActiveSpan.tag("validation_type", "stock_check");
        
        if (request.getQuantity() > 100) {
            // 记录异常
            ActiveSpan.error(new IllegalArgumentException("Quantity exceeds limit"));
        }
    }
    
    // 异步调用追踪
    @Trace
    public CompletableFuture<Void> notifyInventory(OrderDTO order) {
        // 获取当前上下文
        ContextSnapshot snapshot = ContextManager.capture();
        
        return CompletableFuture.runAsync(() -> {
            // 在异步线程中继续追踪
            ContextManager.continued(snapshot);
            
            try {
                inventoryClient.deductStock(order);
            } finally {
                ContextManager.stopSpan();
            }
        });
    }
}
```

```java
// 跨线程追踪
@Component
public class AsyncTraceExecutor {
    
    @Bean
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(10);
        executor.setMaxPoolSize(20);
        executor.setQueueCapacity(200);
        executor.setThreadNamePrefix("async-");
        
        // 包装以支持跨线程追踪
        return new TracingExecutor(executor);
    }
}

class TracingExecutor implements Executor {
    private final Executor delegate;
    
    public TracingExecutor(Executor delegate) {
        this.delegate = delegate;
    }
    
    @Override
    public void execute(Runnable command) {
        ContextSnapshot snapshot = ContextManager.capture();
        delegate.execute(() -> {
            ContextManager.continued(snapshot);
            try {
                command.run();
            } finally {
                ContextManager.stopSpan();
            }
        });
    }
}
```

```java
// 自定义插件开发
@Component
public class CustomSpanHandler {
    
    @Around("@annotation(customTrace)")
    public Object handleCustomTrace(ProceedingJoinPoint pjp, CustomTrace customTrace) 
            throws Throwable {
        
        AbstractSpan span = ContextManager.createLocalSpan("custom-operation");
        span.tag("business_type", customTrace.businessType());
        
        try {
            long start = System.currentTimeMillis();
            Object result = pjp.proceed();
            long duration = System.currentTimeMillis() - start;
            
            span.tag("duration_ms", String.valueOf(duration));
            
            // 超过阈值告警
            if (duration > customTrace.slowThreshold()) {
                span.log(System.currentTimeMillis(), 
                        Map.of("event", "slow_operation", "threshold", customTrace.slowThreshold()));
            }
            
            return result;
        } catch (Exception e) {
            span.errorOccurred().log(e);
            throw e;
        } finally {
            ContextManager.stopSpan();
        }
    }
}
```

## 23. 慢 SQL 问题分析与优化

### 典型慢 SQL 案例

```sql
-- 案例1: 未使用索引导致的慢查询
-- 问题SQL：查询订单列表（执行时间：3.5s）
SELECT o.*, u.username, u.phone
FROM orders o
LEFT JOIN users u ON o.user_id = u.id
WHERE o.status = 'PENDING'
  AND DATE(o.create_time) = '2024-12-01'
  AND o.amount > 100
ORDER BY o.create_time DESC
LIMIT 20;

-- 问题分析
EXPLAIN SELECT ...;
/*
+----+-------------+-------+------+---------------+------+---------+------+--------+-------------+
| id | select_type | table | type | possible_keys | key  | key_len | ref  | rows   | Extra       |
+----+-------------+-------+------+---------------+------+---------+------+--------+-------------+
|  1 | SIMPLE      | o     | ALL  | NULL          | NULL | NULL    | NULL | 500000 | Using where; Using filesort |
|  1 | SIMPLE      | u     | eq_ref| PRIMARY      | PRIMARY | 8    | o.user_id | 1 | NULL |
+----+-------------+-------+------+---------------+------+---------+------+--------+-------------+

问题点：
1. type = ALL：全表扫描 50 万行
2. Using filesort：需要额外排序
3. DATE(o.create_time) 导致索引失效
4. 多个条件未建立合适索引
*/

-- 优化方案
-- 1. 创建复合索引
CREATE INDEX idx_orders_status_time_amount 
ON orders(status, create_time, amount);

-- 2. 优化SQL - 避免函数破坏索引
SELECT o.*, u.username, u.phone
FROM orders o
LEFT JOIN users u ON o.user_id = u.id
WHERE o.status = 'PENDING'
  AND o.create_time >= '2024-12-01 00:00:00'
  AND o.create_time < '2024-12-02 00:00:00'
  AND o.amount > 100
ORDER BY o.create_time DESC
LIMIT 20;

-- 优化后执行计划
/*
+----+-------------+-------+-------+--------------------------------+-------------------------------+---------+-------------+------+-----------------------+
| id | select_type | table | type  | possible_keys                  | key                           | key_len | ref         | rows | Extra                 |
+----+-------------+-------+-------+--------------------------------+-------------------------------+---------+-------------+------+-----------------------+
|  1 | SIMPLE      | o     | range | idx_orders_status_time_amount  | idx_orders_status_time_amount | 15      | NULL        | 150  | Using index condition |
|  1 | SIMPLE      | u     | eq_ref| PRIMARY                        | PRIMARY                       | 8       | o.user_id   | 1    | NULL                  |
+----+-------------+-------+-------+--------------------------------+-------------------------------+---------+-------------+------+-----------------------+

优化效果：3.5s -> 45ms
*/
```

### 深入分析与优化

```sql
-- 案例2: 深度分页问题
-- 问题SQL：翻页到 10000 页时非常慢（执行时间：8s）
SELECT * FROM orders
WHERE status = 'COMPLETED'
ORDER BY id DESC
LIMIT 200000, 20;

-- 问题：即使有索引，MySQL 也需要扫描前 200020 行然后丢弃前 200000 行

-- 优化方案1：使用子查询优化
SELECT o.*
FROM orders o
INNER JOIN (
    SELECT id 
    FROM orders
    WHERE status = 'COMPLETED'
    ORDER BY id DESC
    LIMIT 200000, 20
) tmp ON o.id = tmp.id;

-- 优化方案2：记录上次查询位置（推荐）
SELECT * FROM orders
WHERE status = 'COMPLETED'
```

### 核心原理与计算公式

```java
/**
 * 线程池参数调优指南
 */
public class ThreadPoolTuningGuide {
    
    /**
     * 核心参数说明：
     * 
     * 1. corePoolSize（核心线程数）
     *    - 线程池维持的最小线程数
     *    - 即使空闲也不会销毁
     *    - 除非设置 allowCoreThreadTimeOut
     * 
     * 2. maximumPoolSize（最大线程数）
     *    - 线程池允许的最大线程数
     *    - 当队列满时，创建新线程直到达到此值
     * 
     * 3. keepAliveTime（空闲线程存活时间）
     *    - 超过核心线程数的线程空闲多久后销毁
     * 
     * 4. workQueue（工作队列）
     *    - ArrayBlockingQueue: 有界队列，防止内存溢出
     *    - LinkedBlockingQueue: 近似无界，可能导致OOM
     *    - SynchronousQueue: 不存储元素，直接传递
     *    - PriorityBlockingQueue: 优先级队列
     * 
     * 5. threadFactory（线程工厂）
     *    - 创建线程的方式
     *    - 建议自定义，设置有意义的线程名
     * 
     * 6. rejectedExecutionHandler（拒绝策略）
     *    - AbortPolicy: 抛异常（默认）
     *    - CallerRunsPolicy: 调用者执行
     *    - DiscardPolicy: 丢弃任务
     *    - DiscardOldestPolicy: 丢弃最老任务
     */
    
    /**
     * 参数计算公式
     */
    public void calculateThreadPoolSize() {
        /**
         * 1. CPU 密集型任务
         * 
         * 最优线程数 = CPU核心数 + 1
         * 
         * 原因：
         * - CPU密集型任务主要消耗CPU资源
         * - 过多线程会导致上下文切换开销
         * - +1是为了在某个线程偶尔暂停时保持CPU利用率
         */
        int cpuCores = Runtime.getRuntime().availableProcessors();
        int cpuIntensiveThreads = cpuCores + 1;
        
        /**
         * 2. IO 密集型任务（常用）
         * 
         * 最优线程数 = CPU核心数 * (1 + IO耗时/CPU耗时)
         * 或简化为：最优线程数 = CPU核心数 * 2
         * 
         * 更精确的公式（Little's Law）：
         * 线程数 = QPS * 平均响应时间
         * 
         * 例如：
         * - QPS = 1000
         * - 平均响应时间 = 100ms = 0.1s
         * - 线程数 = 1000 * 0.1 = 100
         */
        
        // 实际案例：调用外部API
        double qps = 1000;           // 每秒请求数
        double avgResponseTime = 0.1; // 100ms
        int ioIntensiveThreads = (int) (qps * avgResponseTime);
        
        /**
         * 3. 混合型任务
         * 
         * 线程数 = CPU核心数 * CPU利用率 * (1 + IO等待时间/CPU计算时间)
         * 
         * 假设：
         * - 8核CPU
         * - 目标CPU利用率 80%
         * - IO等待300ms，CPU
         * 计算100ms
         * 
         * 线程数 = 8 * 0.8 * (1 + 300/100) = 8 * 0.8 * 4 = 25.6 ≈ 26
         */
        int cores = 8;
        double targetCpuUtilization = 0.8;
        double ioWaitTime = 300;
        double cpuComputeTime = 100;
        int mixedThreads = (int) (cores * targetCpuUtilization * 
                                  (1 + ioWaitTime / cpuComputeTime));
    }
}
```

```java
            String message = record.value();
            log.info("Received message: key={}, value={}, partition={}, offset={}",
                    record.key(), message, record.partition(), record.offset());
            
            // 业务处理
            processOrder(message);
            
            // 手动提交offset（确保业务处理成功后再提交）
            ack.acknowledge();
            
        } catch (Exception e) {
            log.error("Failed to process message: {}", record.value(), e);
            
            // 消息处理失败的策略
            handleFailedMessage(record, e);
            
            // 注意：这里不提交offset，消息会重新被消费
            // 需要配合重试策略，防止死循环
        }
    }
    
    /**
     * 失败消息处理
     */
    private void handleFailedMessage(ConsumerRecord<String, String> record, Exception e) {
        // 策略1：重试次数限制
        String retryKey = "kafka:retry:" + record.topic() + ":" + record.offset();
        int retryCount = getRetryCount(retryKey);
        
        if (retryCount < 3) {
            // 增加重试计数
            incrementRetryCount(retryKey);
            // 不提交offset，等待重新消费
            log.warn("Will retry, count={}", retryCount + 1);
        } else {
            // 策略2：超过重试次数，转入死信队列
            sendToDeadLetterQueue(record);
            // 提交offset，避免阻塞后续消息
            log.error("Max retry reached, sent to DLQ");
        }
    }
    
    /**
     * 死信队列
     */
    private void sendToDeadLetterQueue(ConsumerRecord<String, String> record) {
        DeadLetterMessage dlqMessage = DeadLetterMessage.builder()
            .originalTopic(record.topic())
            .originalKey(record.key())
            .originalValue(record.value())
            .originalPartition(record.partition())
            .originalOffset(record.offset())
            .errorTime(LocalDateTime.now())
            .build();
        
        kafkaTemplate.send("dlq-topic", JSON.toJSONString(dlqMessage));
    }
}
```

```java
/**
 * Kafka 消息顺序性保证方案
 */
@Service
public class OrderedKafkaService {
    
    /**
     * 方案1：单分区保证全局顺序
     * 
     * 适用场景：消息量不大，且必须全局有序
     * 缺点：无法并行消费，吞吐量受限
     */
    public void sendWithGlobalOrder(String message) {
        // Topic只有1个分区，所有消息按顺序写入
        kafkaTemplate.send("global-order-topic", message);
    }
    
    /**
     * 方案2：按Key分区保证局部顺序（推荐）
     * 
     * 适用场景：同一个实体的消息需要有序（如同一个订单的状态变更）
     * 优点：可以并行消费不同Key的消息
     */
    public void sendWithPartialOrder(String orderId, OrderEvent event) {
        // 相同orderId的消息会路由到同一个分区
        kafkaTemplate.send("order-event-topic", orderId, JSON.toJSONString(event));
        
        /*
         * 原理：
         * - Kafka使用Key的hash值决定分区：partition = hash(key) % partition_count
         * - 相同Key的消息一定在同一个分区
         * - 单个分区内消息是有序的
         * 
         * 注意事项：
         * 1. 消费者数量 <= 分区数（保证单个分区只被一个消费者消费）
         * 2. 不要动态增加分区数（会改变hash算法，破坏顺序）
         */
    }
    
    /**
     * 消费端保证顺序性
     */
    @KafkaListener(
        topics = "order-event-topic",
        groupId = "order-event-consumer",
        concurrency = "3"  // 3个消费者实例，对应3个分区
    )
    public void consumeOrdered(ConsumerRecord<String, String> record) {
        String orderId = record.key();
        
        // 方案1：同步处理（简单但慢）
        processOrderEventSync(orderId, record.value());
        
        // 方案2：异步处理但保证顺序（复杂但快）
        // processOrderEventAsync(orderId, record.value());
    }
    
    /**
     * 方案3：使用消息时间戳保证顺序（处理乱序问题）
     * 
     * 场景：由于网络延迟、重试等原因，消息可能乱序到达
     */
    @Service
    public class OrderEventProcessor {
        
        // 为每个订单维护最后处理的时间戳
        private final ConcurrentHashMap<String, Long> lastProcessedTimestamp = 
            new ConcurrentHashMap<>();
        
        public void processWithTimestamp(String orderId, OrderEvent event) {
            long eventTimestamp = event.getTimestamp();
            
            // 获取该订单上次处理的时间戳
            Long lastTimestamp = lastProcessedTimestamp.get(orderId);
            
            if (lastTimestamp != null && eventTimestamp <= lastTimestamp) {
                // 乱序消息，丢弃或特殊处理
                log.warn("Out-of-order message ignored: orderId={}, " +
                        "eventTimestamp={}, lastTimestamp={}",
                        orderId, eventTimestamp, lastTimestamp);
                return;
            }
            
            // 处理消息
            doProcess(event);
            
            // 更新时间戳
            lastProcessedTimestamp.put(orderId, eventTimestamp);
        }
    }
    
    /**
     * 方案4：使用版本号保证顺序
     */
    @Service
    public class OrderVersionProcessor {
        
        private final ConcurrentHashMap<String, Integer> orderVersions = 
            new ConcurrentHashMap<>();
        
        public void processWithVersion(String orderId, OrderEvent event) {
            int eventVersion = event.getVersion();
            
            // 使用computeIfAbsent保证原子性
            orderVersions.compute(orderId, (key, currentVersion) -> {
                if (currentVersion == null) {
                    currentVersion = 0;
                }
                
                if (eventVersion == currentVersion + 1) {
                    // 版本号连续，正常处理
                    doProcess(event);
                    return eventVersion;
                } else if (eventVersion <= currentVersion) {
                    // 重复或过期消息
                    log.warn("Duplicate or outdated message: orderId={}, " +
                            "eventVersion={}, currentVersion={}",
                            orderId, eventVersion, currentVersion);
                    return currentVersion;
                } else {
                    // 版本号跳跃，可能有消息丢失
                    log.error("Version gap detected: orderId={}, " +
                            "eventVersion={}, currentVersion={}",
                            orderId, eventVersion, currentVersion);
                    // 触发补偿机制
                    return currentVersion;
                }
            });
        }
    }
    
    /**
     * 生产者配置保证顺序
     */
    @Bean
    public ProducerFactory<String, String> orderedProducerFactory() {
        Map<String, Object> configProps = new HashMap<>();
        
        // === 顺序性关键配置 ===
        
        // 1. 同时只能有1个请求发送（牺牲吞吐量）
        configProps.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 1);
        
        // 2. 开启幂等性（防止重试导致重复）
        configProps.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
        
        // 3. 重试次数
        configProps.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);
        
        // 4. ACK机制
        configProps.put(ProducerConfig.ACKS_CONFIG, "all");
        
        // ... 其他配置
        
        return new DefaultKafkaProducerFactory<>(configProps);
    }
}
```
