# Java 垃圾回收器完整指南 (2025版)

## 概述

垃圾回收器是 Java 内存管理的核心组件。如果说收集算法是内存回收的方法论，那么垃圾收集器就是内存回收的具体实现。**没有万能的垃圾收集器**，我们需要根据具体应用场景选择最适合的垃圾收集器。

---

## 一、分代垃圾回收器（区分新生代和老年代）

### 新生代垃圾回收器

#### 1. Serial（/ˈsɪəriəl/） 收集器（串行）

**适用场景**: 客户端模式、单核 CPU、小内存应用（堆内存小于 100MB）

**核心特点**:
- 最基本、历史最悠久的**单线程**收集器
- 新生代采用**复制算法**（Copying）
- 进行垃圾收集时会暂停所有工作线程（**Stop The World**）
- 简单高效，无线程交互开销
- 在资源受限环境（RAM < 2GB，CPU 核心 < 2）下会被自动选择

**优点**:
- 实现简单，内存占用小
- 单线程环境下效率最高（无线程切换开销）

**缺点**:
- STW 时间较长，影响用户体验

**启用方式**: `-XX:+UseSerialGC`

**当前状态**: ✅ 仍然支持，适用于资源受限的嵌入式设备

---

#### 2. ParNew（/ˈpɑːr njuː/） 收集器（并行）

**适用场景**: 多核 CPU、Server 模式、配合 CMS 使用（已废弃）

**核心特点**:
- Serial 收集器的**多线程版本**
- 新生代采用**复制算法**
- 除了多线程外，其他行为与 Serial 完全一致
- 曾是 CMS 收集器的默认新生代搭档

**优点**:
- 多线程并行收集，减少 STW 时间
- 在多核 CPU 上性能优于 Serial

**缺点**:
- 在单核 CPU 上性能不如 Serial
- 随着 CMS 的废弃，ParNew 也逐渐被淘汰

**启用方式**: `-XX:+UseParNewGC`（需配合 `-XX:+UseConcMarkSweepGC`）

**当前状态**: ⚠️ Java 9 标记为废弃，Java 14 随 CMS 一起移除

---

#### 3. Parallel（/ˈpærəlel/） Scavenge （/ˈskævɪndʒ/）收集器（并行）

**适用场景**: 后台计算任务、批处理应用、注重吞吐量的系统

**核心特点**:
- 关注点是**高吞吐量**（CPU 用于运行用户代码的时间与总时间的比值）
- 新生代采用**复制算法**
- 提供了自适应调节策略（GC Ergonomics）
- 与 ParNew 类似但关注点不同（吞吐量 vs 低延迟）

**优点**:
- 高吞吐量，适合后台计算
- 自适应调节，减少手动调优
- 提供丰富的参数控制吞吐量和停顿时间

**缺点**:
- STW 时间可能较长
- 不适合交互性强的应用

**相关参数**:
- `-XX:MaxGCPauseMillis`: 最大垃圾收集停顿时间（毫秒）
- `-XX:GCTimeRatio`: 吞吐量大小（默认 99，即 1% 时间用于 GC）
- `-XX:+UseAdaptiveSizePolicy`: 自适应调节策略

**启用方式**: `-XX:+UseParallelGC`

**当前状态**: ✅ 仍然支持并持续优化，Java 23 改进了 Full GC 算法

---

### 老年代垃圾回收器

#### 1. Serial Old 收集器（串行）

**适用场景**: Client 模式、作为 CMS 的后备方案

**核心特点**:
- Serial 收集器的老年代版本
- 老年代采用**标记-整理算法**（Mark-Compact）
- 单线程收集，会发生 STW

**优点**:
- 实现简单，资源占用少
- 适合小内存、单核环境

**缺点**:
- STW 时间长，不适合大内存应用

**启用方式**: `-XX:+UseSerialGC`（同时启用 Serial + Serial Old）

**当前状态**: ✅ 仍然支持

---

#### 2. Parallel Old 收集器（并行）

**适用场景**: 注重吞吐量的应用、与 Parallel Scavenge 配合使用

**核心特点**:
- Parallel Scavenge 的老年代版本
- 老年代采用**标记-整理算法**
- 多线程并行收集

**优点**:
- 多线程提高收集效率
- 高吞吐量
- 适合大内存环境

**缺点**:
- STW 时间较长
- 不适合低延迟需求

**启用方式**: `-XX:+UseParallelOldGC` 或 `-XX:+UseParallelGC`（Java 8+ 自动启用）

**当前状态**: ✅ 仍然支持，Java 8 默认组合

---

#### 3. CMS 收集器（Concurrent Mark Sweep）❌ 已移除

**历史地位**: 第一款真正意义上的并发收集器

**核心特点**:
- 以获取**最短回收停顿时间**为目标
- 老年代采用**标记-清除算法**（Mark-Sweep）
- 大部分收集工作与用户线程并发执行

**工作流程**:
1. **初始标记**（STW）：标记 GC Roots 直接关联的对象，速度很快
2. **并发标记**：与用户线程同时运行，标记所有可达对象
3. **重新标记**（STW）：修正并发标记期间因用户程序运行而导致的标记变动
4. **并发清除**：与用户线程同时运行，清除未标记对象

**优点**:
- 并发收集，停顿时间短
- 适合互联网应用、Web 服务

**缺点**:
- **对 CPU 资源敏感**：并发阶段会占用部分 CPU 资源
- **无法处理浮动垃圾**：并发清除阶段产生的垃圾无法在本次收集中处理
- **产生内存碎片**：标记-清除算法会产生大量碎片，可能触发 Full GC
- **Concurrent Mode Failure**：并发收集期间预留内存不足，退化为 Serial Old

**启用方式**: `-XX:+UseConcMarkSweepGC`

**当前状态**: ❌ Java 9 标记为废弃，Java 14 完全移除

**替代方案**: 使用 G1 GC 或 ZGC

---

### 常见组合搭配

| 新生代收集器 | 老年代收集器 | 适用场景 | 状态 |
|------------|------------|---------|------|
| Serial | Serial Old | 单核、小内存、Client 模式 | ✅ 支持 |
| ParNew | CMS | 低延迟、互联网应用 | ❌ 已移除 |
| Parallel Scavenge | Parallel Old | 高吞吐量、后台计算 | ✅ 支持 |

## 二、不区分新生代/老年代的垃圾回收器

### 1. G1 收集器（Garbage-First）⭐ 推荐

**适用场景**: 大内存应用（4GB 以上）、需要可预测停顿时间的服务端应用

**核心特点**:
- 自 **Java 9** 起成为**默认垃圾收集器**
- 将堆划分为多个大小相等的 **Region**（默认 2048 个）
- 面向服务器的垃圾收集器，支持多核处理器
- **并行与并发**：充分利用多核 CPU，部分操作可与应用线程并发执行
- **分代收集**：保留了新生代和老年代的概念，但不是物理隔离
- **空间整合**：整体基于**标记-整理**算法，局部（Region 之间）基于**复制**算法，减少碎片
- **可预测的停顿**：可以指定在 M 毫秒时间片段内的停顿时间目标
- 维护优先列表，优先回收价值最大的 Region（Garbage First）

**运作步骤**:
1. **初始标记**（Initial Mark，STW）：标记 GC Roots 直接关联对象
2. **并发标记**（Concurrent Mark）：从 GC Roots 开始遍历整个堆
3. **最终标记**（Final Mark，STW）：处理并发标记阶段遗留的少量 SATB 记录
4. **筛选回收**（Live Data Counting and Evacuation，STW）：更新 Region 统计数据，按价值排序并回收

**优点**:
- 可预测的停顿时间（通过 `-XX:MaxGCPauseMillis` 设置）
- 不会产生内存碎片
- 并发与并行结合
- 适合大内存应用

**缺点**:
- 内存占用较高（需要额外的 Remembered Set）
- 程序运行时额外负载较大
- 小堆内存下表现不如 Parallel GC

**相关参数**:
- `-XX:MaxGCPauseMillis=200`: 期望的最大停顿时间（默认 200ms）
- `-XX:G1HeapRegionSize=n`: 设置 Region 大小（1MB-32MB，必须是 2 的幂）
- `-XX:InitiatingHeapOccupancyPercent=45`: 触发并发标记的堆占用阈值

**启用方式**: `-XX:+UseG1GC`（Java 9+ 默认无需指定）

**当前状态**: ✅ 默认收集器，持续优化中。Java 23 改进了记忆集存储效率和写屏障性能

---

### 2. ZGC 收集器（Z Garbage Collector）⭐ 超低延迟

**适用场景**: 超大堆内存应用（TB 级）、对延迟极度敏感的应用

**核心特点**:
- 首次在 **Java 11** 中作为实验性特性引入，在 **Java 15** 中成为生产就绪版本
- 可扩展的**超低延迟**垃圾收集器
- **停顿时间不超过 10 毫秒**，且不随堆大小增加而增加
- 支持 **TB 级别**的堆内存（最大支持 16TB）
- 所有耗时操作都**并发执行**，不停止应用线程
- 使用**着色指针**（Colored Pointers）和**读屏障**（Load Barriers）技术
- **Java 21** 引入了**分代 ZGC**（Generational ZGC），区分年轻代和老年代对象

**运作模式**:
- **非分代模式**: Java 11-20 可用，在 Java 23 中默认废弃
- **分代模式**: Java 21 引入，成为默认模式（推荐）

**优点**:
- 极低的停顿时间（< 10ms）
- 支持超大堆内存（16TB）
- 停顿时间不随堆大小增长
- 并发程度极高

**缺点**:
- 吞吐量相对较低（比 G1 低 10-15%）
- 内存占用较大
- CPU 占用较高

**启用方式**:
- Java 21+: `-XX:+UseZGC -XX:+ZGenerational`（分代模式，推荐）
- Java 15-20: `-XX:+UseZGC`
- Java 11-14: `-XX:+UnlockExperimentalVMOptions -XX:+UseZGC`

**性能表现**: Netflix 在生产环境中使用分代 ZGC 后，显著降低了尾延迟，超过一半的关键流媒体服务已迁移到 Java 21 的分代 ZGC

**当前状态**: ✅ 生产就绪，Java 23 中分代模式成为默认，非分代模式计划在未来版本中移除

---

### 3. Shenandoah GC

**适用场景**: 大堆内存（> 32GB）、低延迟要求的应用

**核心特点**:
- 由 Red Hat 在 **Java 12** 中引入
- 大部分工作与应用线程**并发执行**，包括**并发压缩**
- 停顿时间不与堆大小成正比
- 将堆划分为多个区域
- 使用**转发指针**（Forwarding Pointers）和**读写屏障**技术
- 使用连接矩阵（Connection Matrix）技术

**优点**:
- 停顿时间短且稳定
- 并发压缩，减少 STW 时间
- 适合大堆内存

**缺点**:
- 吞吐量低于 G1
- 仅在 OpenJDK 发行版中可用（Oracle JDK 不包含）
- 内存占用较高

**启用方式**: `-XX:+UseShenandoahGC`

**当前状态**: ✅ 仍然支持，适用于 OpenJDK 发行版

---

### 4. Epsilon GC（无操作垃圾收集器）

**适用场景**: 性能测试、极短生命周期应用、几乎不产生垃圾的应用

**核心特点**:
- 只分配内存，**不执行任何垃圾回收**
- 用于性能基准测试
- 内存耗尽时应用会终止
- 永久保持实验性特性状态，防止意外用于生产环境

**优点**:
- 零开销，无 GC 停顿
- 适合性能基准测试
- 可用于验证应用是否存在内存泄漏

**缺点**:
- 内存耗尽即崩溃
- 不适合任何生产环境

**启用方式**: `-XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC`

**当前状态**: ✅ 实验性特性，仅用于特定测试场景

## 三、并行与并发的概念

### 并行（Parallel）
- 多条垃圾收集线程**并行工作**
- 用户线程处于**等待状态**（STW）
- 强调多线程协作，提高收集效率
- 例如：Parallel Scavenge、Parallel Old

### 并发（Concurrent）
- 用户线程与垃圾收集线程**同时工作**（可能交替执行）
- 用户程序继续运行，减少停顿时间
- 强调用户线程与 GC 线程共存
- 例如：CMS、G1、ZGC、Shenandoah

### 关系图示
```
并行（Parallel）：
用户线程: ████████ [等待] ████████
GC 线程:   [等待]   ⚡⚡⚡⚡   [等待]

并发（Concurrent）：
用户线程: ████████████████████████
GC 线程:   ⚡⚡⚡⚡⚡⚡⚡⚡⚡⚡⚡⚡
```

## 四、如何选择合适的垃圾收集器？

### 决策树

```
应用类型？
│
├─ 客户端/嵌入式设备（小内存 < 100MB）
│   └─ Serial GC
│
├─ 批处理/后台计算（注重吞吐量）
│   └─ Parallel GC
│
├─ 服务端应用（平衡延迟和吞吐量）
│   ├─ 堆内存 < 32GB → G1 GC（默认推荐）
│   └─ 堆内存 > 32GB → ZGC 或 Shenandoah
│
├─ 延迟敏感型应用（金融交易、实时系统）
│   ├─ 要求停顿 < 10ms → ZGC（分代模式）
│   ├─ 堆内存 > 32GB → Shenandoah GC
│   └─ 堆内存适中 → G1 GC
│
└─ 性能测试/基准测试
    └─ Epsilon GC
```

### 关键考虑因素

| 优先级 | 推荐收集器 | 说明 |
|-------|----------|------|
| **吞吐量优先** | Parallel GC | 适合批处理、后台计算 |
| **低延迟优先** | ZGC（分代）> Shenandoah > G1 | 适合实时系统、交互应用 |
| **内存占用优先** | G1 GC | Java 20+ 内存效率显著提升 |
| **平衡性能** | G1 GC | 默认推荐，适合大多数场景 |
| **超大堆（TB 级）** | ZGC | 停顿时间不随堆大小增长 |
| **小内存应用** | Serial GC | 资源受限环境 |

## 六、2025 年推荐配置

### 1. 通用服务端应用（推荐）
```bash
# 使用默认 G1 GC，适用于大多数场景
# 堆内存 4GB-32GB
java -Xmx8g -Xms8g \
     -XX:MaxGCPauseMillis=200 \
     -jar application.jar
```

### 2. 低延迟应用（Java 21+）
```bash
# 使用分代 ZGC，停顿时间 < 10ms
# 堆内存 > 8GB
java -Xmx16g -Xms16g \
     -XX:+UseZGC \
     -XX:+ZGenerational \
     -jar application.jar
```

### 3. 高吞吐量批处理
```bash
# 使用 Parallel GC，最大化吞吐量
java -Xmx8g -Xms8g \
     -XX:+UseParallelGC \
     -XX:ParallelGCThreads=8 \
     -jar batch-job.jar
```

### 4. 超大堆应用（TB 级）
```bash
# ZGC 支持超大堆，停顿时间稳定
java -Xmx128g -Xms128g \
     -XX:+UseZGC \
     -XX:+ZGenerational \
     -jar large-heap-app.jar
```

### 5. 嵌入式/小内存设备
```bash
# Serial GC，资源占用最小
java -Xmx128m -Xms128m \
     -XX:+UseSerialGC \
     -jar embedded-app.jar
```

## 七、常见 GC 调优参数

### 通用参数
```bash
-Xms<size>[unit]           # 初始堆大小
-Xmx<size>[unit]           # 最大堆大小
-Xmn<size>[unit]           # 新生代大小
-Xss<size>[unit]           # 每个线程分配（栈帧）的内存大小，防止Stack overflow
-XX:+PrintGCDetails  # 打印 GC 详细信息
-XX:+PrintGCDateStamps # 打印 GC 时间戳
-Xloggc:<file>       # GC 日志文件路径
-XX:NewRatio=4       # 设置年轻的和老年代的内存比例为 1:4，这也是默认值
-XX:SurvivorRatio=8  # 设置新生代 Eden 和 Survivor 比例为 8:1:1 ，这也是默认值
-XX:MaxTenuringThreshold=15  # 最大年龄阈值为15（默认值）
```

### G1 特有参数
```bash
-XX:+UseG1GC                        # 启用 G1
-XX:MaxGCPauseMillis=200            # 期望最大停顿时间（毫秒）
-XX:G1HeapRegionSize=16m            # Region 大小（1-32MB）
-XX:InitiatingHeapOccupancyPercent=45 # 触发并发标记的堆占用阈值
-XX:ConcGCThreads=4                 # 并发 GC 线程数
```

### ZGC 特有参数
```bash
-XX:+UseZGC              # 启用 ZGC
-XX:+ZGenerational       # 启用分代模式（Java 21+）
-XX:ConcGCThreads=4      # 并发 GC 线程数
-XX:ZAllocationSpikeTolerance=2 # 内存分配峰值容忍度
```

### Parallel GC 特有参数
```bash
-XX:+UseParallelGC          # 启用 Parallel GC
-XX:ParallelGCThreads=8     # 并行 GC 线程数
-XX:MaxGCPauseMillis=100    # 最大停顿时间目标
-XX:GCTimeRatio=99          # 吞吐量目标（1% 时间用于 GC）
```

## 八、总结

### 快速选择指南

| 场景 | 推荐收集器 | 理由 |
|------|----------|------|
| **默认选择** | G1 GC | 平衡性能，适用于大多数应用 |
| **极低延迟** | ZGC（分代） | 停顿 < 10ms，不随堆大小增长 |
| **最高吞吐量** | Parallel GC | 适合批处理、科学计算 |
| **超大堆** | ZGC | 支持 TB 级堆，停顿时间稳定 |
| **资源受限** | Serial GC | 单核、小内存环境 |

### 关键要点

1. **Java 9+** 默认使用 **G1 GC**，适合大多数场景
2. **CMS 已移除**，请迁移到 G1 或 ZGC
3. **ZGC（分代模式）** 是低延迟应用的最佳选择（Java 21+）
4. **Parallel GC** 仍然是高吞吐量场景的首选
5. 根据应用特点选择合适的 GC，不要盲目追求新技术

### 迁移建议

- **从 CMS 迁移**: 使用 G1 GC（平衡）或 ZGC（低延迟）
- **从 Parallel 迁移**: 如果需要更低延迟，考虑 G1 或 ZGC
- **升级到 Java 21**: 评估 ZGC 分代模式，显著降低尾延迟
