## 概念

### 什么是线程？

现代操作系统调度的最小单元是线程，也叫轻量级进程（LightWeight Process），在一个进程里可以创建多个线程，这些线程都拥有各自的计数器、堆栈和局部变量等属性，并且能够访问共享的内存变量。处理器在这些线程上高速切换，让使用者感觉到这些线程在同时执行

### 为什么要使用多线程/线程使用的好处？

- 更多的处理器核心
- 更快的响应时间
- 更好的编程模型

### 线程的状态？

初始状态、运行状态、阻塞状态、等待状态、超时等待状态、终止状态

#### Java 线程中 的 start()方法为什么可以启动一个线程，直接执行run()方法会有什么区别？

这是 Java 多线程的一个很重要的概念，我来给你详细解释。

**start() 方法的作用**：当你调用 `start()` 时，Java 虚拟机会创建一个新的线程，然后在这个新线程中执行 `run()` 方法。这样你的程序就有了两个线程并发执行。

**直接调用 run() 的问题**：如果你直接调用 `run()` 方法，比如 `thread.run()`，它并不会创建新线程。`run()` 方法会在**当前线程**（通常是主线程）中同步执行，就像调用普通方法一样。这样就没有并发效果了。

**具体区别**：

假设你有这样的代码：
```java
Thread thread = new Thread(() -> {
    System.out.println("线程执行");
});
```

如果你调用 `thread.start()`，会创建新线程，主线程和新线程会并发运行。

如果你调用 `thread.run()`，主线程会直接执行这段代码，然后才继续往下。没有并发。

**为什么这样设计**：`start()` 方法内部会调用本地代码创建操作系统级别的线程，然后由操作系统调度这个新线程去执行 `run()` 方法。而 `run()` 只是一个普通方法，直接调用它不会触发线程创建的过程。

**总结**：`start()` = 创建新线程 + 执行 `run()`；`run()` = 仅执行方法体。这是使用多线程时必须记住的一个重要细节。
:::

### 如何安全地终止线程？

在中断线程节中提到的中断状态是线程的一个标识位，而中断操作是一种简便的线程间交互方式，而这种交互方式最适合用来取消或停止任务。除了中断以外，还可以利用一个boolean变量来控制是否需要停止任务并终止该线程。在代码清单1所示的例子中，创建了一个线程CountThread，它不断地进行变量累加，而主线程尝试对其进行中断操作和停止操作

```java
package com.ise.api.thread;

import java.util.concurrent.TimeUnit;

public class Shutdown {
    public static void main(String[] args) throws Exception {
        Runner one = new Runner();
        Thread countThread = new Thread(one, "CountThread");
        countThread.start();
        // 睡眠1秒，main线程对CountThread进行中断，使CountThread能够感知中断而结束
        TimeUnit.SECONDS.sleep(1);
        countThread.interrupt();
        Runner two = new Runner();
        countThread = new Thread(two, "CountThread");
        countThread.start();
        // 睡眠1秒，main线程对Runner two进行取消，使CountThread能够感知on为false而结束
        TimeUnit.SECONDS.sleep(1);
        two.cancel();
    }

    private static class Runner implements Runnable {
        private long i;
        private volatile boolean on = true;

        @Override
        public void run() {
            while (on && !Thread.currentThread().isInterrupted()) {
                i++;
            }
            System.out.println("Count i = " + i);
        }

        public void cancel() {
            on = false;
        }
    }
}
```

:::tip
**volatile 修饰 on 变量的分析**

合理性 ✅

`volatile boolean on` 在这里**合理**，原因：

- `on` 变量只做**单次写（cancel 写 false）、多次读（run 读）** 的操作
- 不存在"先读后写"的复合操作（如 `on++`），所以不需要原子性保证
- `volatile` 的**可见性**保证恰好满足需求：主线程写 `false`，工作线程立即可见

---

**安全性分析**

```
主线程               CountThread
two.cancel()    →    写 on=false（volatile写，刷入主存）
                →    while(on ...) 读到 false（volatile读，从主存取）
                →    退出循环 ✅
```

**是安全的**，因为：
- `volatile` 禁止指令重排序，保证写操作的**happens-before**关系
- 单个布尔值的读/写本身是原子的，`volatile` 只需额外保证可见性即可

> ⚠️ 如果是 `on = !on` 这种复合操作，则 volatile **不够**，需要 `AtomicBoolean`

---

**`volatile on` vs `interrupt()` 哪个更准确？**

| 对比维度 | `volatile boolean on` | `Thread.interrupt()` |
|---|---|---|
| **语义准确性** | 业务级开关，语义自定义 | JDK 标准线程中断协议 |
| **响应阻塞** | ❌ 无法唤醒 sleep/wait/IO | ✅ 抛出 InterruptedException |
| **可见性保证** | volatile 手动保证 | JDK 内部保证 |
| **与阻塞API配合** | ❌ 不兼容 | ✅ 原生兼容 |
| **标准化程度** | 私有约定 | 通用规范 |

---

**关键差异：遇到阻塞时**

```java
// ❌ volatile on 无法中断阻塞中的线程
while (on) {
    TimeUnit.SECONDS.sleep(100); // on=false 了，但线程还在睡！
}

// ✅ interrupt() 可以
while (!Thread.currentThread().isInterrupted()) {
    TimeUnit.SECONDS.sleep(100); // 立即抛出 InterruptedException，线程醒来
}
```

---

**结论**

```
纯计算循环（无阻塞）     → volatile on 够用，语义清晰
涉及 sleep/wait/IO      → 必须用 interrupt()
最佳实践（两者结合）     → 如本例，同时检查 on && !isInterrupted()
```

本例代码同时使用两者是**正确且推荐的写法**——`volatile on` 负责正常退出逻辑，`interrupt` 负责处理阻塞唤醒，各司其职，互为补充。
:::

### 创建线程有哪几种方式？

创建线程有三种方式：
- 继承 Thread 重写 run 方法
- 实现 Runnable 接口  
- 实现 Callable 接口

> 补充：说一下 runnable 和 callable 有什么区别？
> runnable 没有返回值，callable 可以拿到有返回值，可以在从线程执行的时候使用 future 来接收返回值！

### 多线程环境下，局部变量和全局变量都会共享吗？

- 局部变量不会受多线程影响
- 成员变量会受到多线程影响

多个线程调用的同一个对象的同一个方法：
- 如果方法里无成员变量，不受任何影响
- 如果方法里有成员变量，只有读操作，不受影响
- 如果方法里有成员变量，存在赋值操作，有影响

### 线程优先级

每个线程都有优先级属性。一般情况下，高优先级线程会获得更多的执行机会，但这取决于底层线程调度器的实现，而线程调度器是操作系统相关的（OS-dependent）。

**关键点：**
- 可以通过API设置线程优先级（范围1-10，1最低，10最高）
- 高优先级**不保证**一定先于低优先级线程执行
- 优先级只是给调度器的建议，实际执行顺序由JVM和操作系统共同决定

```java
Thread thread = new Thread(() -> {
    System.out.println("运行中...");
});

// 设置优先级（1-10 之间）
thread.setPriority(Thread.MAX_PRIORITY);  // 设置为最高优先级 10
thread.setPriority(8);                    // 直接写数字
thread.setPriority(Thread.NORM_PRIORITY + 2);  // 7

thread.start();
```

### 什么是线程安全？

当多个线程同时访问同一段代码时，如果满足以下条件，则认为是线程安全的：
- 每次执行的结果与单线程执行结果一致
- 共享变量的值符合预期
- 不会出现数据竞争或不一致的状态

**示例：** 一个线程安全的计数器类，即使被多个线程同时使用，也不会出现计数错误。

### Vector是线程安全的吗？

**是的。** Vector通过在方法上使用`synchronized`关键字实现线程安全。

**对比：** ArrayList与Vector功能相似，但ArrayList不是线程安全的，性能更好，适合单线程环境。

### 如何停止线程？

Java没有提供强制停止线程的安全API。早期版本（JDK 1.0）中的`stop()`、`suspend()`和`resume()`方法因存在死锁风险已被废弃。

#### 推荐的停止方式：

1. **自然结束：** 让`run()`或`call()`方法正常执行完毕

2. **使用标志位：** 通过[volatile](https://coding.dzspace.top/java-concurrent/thread/volatile.html)布尔变量控制循环退出
```java
private volatile boolean running = true;

public void run() {
    while (running) {
        // 执行任务
    }
}

public void stop() {
    running = false;
}
```

3. **中断机制：** 使用`Thread.interrupt()`配合中断检查

### Java 中 interrupted() 和 isInterrupted() 方法的区别？**

这两个方法都用于检查线程的中断状态，但在是否清除中断标志、方法类型和使用场景上存在重要区别。

#### 核心区别

| 特性 | interrupted() | isInterrupted() |
|------|--------------|-----------------|
| **方法类型** | 静态方法 | 实例方法 |
| **作用对象** | 当前线程 | 调用此方法的线程对象 |
| **清除中断标志** | ✓ 会清除 | ✗ 不会清除 |
| **调用方式** | `Thread.interrupted()` | `thread.isInterrupted()` |

#### 详细说明

**1. Thread.interrupted()（静态方法）**
```java
// 检查当前线程的中断状态，并清除中断标志
public static boolean interrupted() {
    return currentThread().isInterrupted(true);  // 参数true表示清除
}
```

特点：
- 检查**当前正在执行的线程**的中断状态
- 返回中断状态后，**自动将中断标志重置为 false**
- 连续调用两次，第二次通常返回 false（除非期间再次被中断）

**2. isInterrupted()（实例方法）**
```java
// 检查指定线程的中断状态，不清除中断标志
public boolean isInterrupted() {
    return isInterrupted(false);  // 参数false表示不清除
}
```

特点：
- 检查**指定线程对象**的中断状态
- **不会改变**中断标志的状态
- 可以多次调用，返回值保持一致

## 使用示例
```java
public class InterruptExample {
    public static void main(String[] args) throws Exception {
        Thread thread = new Thread(() -> {
            // 示例1：interrupted() 会清除标志
            Thread.currentThread().interrupt();  // 设置中断标志
            System.out.println("第1次 interrupted(): " + Thread.interrupted());  // true
            System.out.println("第2次 interrupted(): " + Thread.interrupted());  // false（已被清除）
            
            // 示例2：isInterrupted() 不会清除标志
            Thread.currentThread().interrupt();  // 再次设置中断标志
            System.out.println("第1次 isInterrupted(): " + Thread.currentThread().isInterrupted());  // true
            System.out.println("第2次 isInterrupted(): " + Thread.currentThread().isInterrupted());  // true（未被清除）
        });
        
        thread.start();
        thread.join();
    }
}
```

**输出结果**：
```
第1次 interrupted(): true
第2次 interrupted(): false
第1次 isInterrupted(): true
第2次 isInterrupted(): true
```

#### 中断机制的其他要点

**1. 中断标志的设置**
```java
thread.interrupt();  // 设置线程的中断标志为 true
```

**2. 抛出 InterruptedException 会清除中断标志**
```java
try {
    Thread.sleep(1000);  // 响应中断的阻塞方法
} catch (InterruptedException e) {
    // 异常抛出时，中断标志已被自动清除
    System.out.println(Thread.interrupted());  // false
    
    // 如果需要保留中断状态，应该重新设置
    Thread.currentThread().interrupt();
}
```

**3. 中断状态可被其他线程修改**
```java
Thread t = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        // 执行任务
    }
});
t.start();
t.interrupt();  // 主线程中断工作线程
```

#### 使用建议

- **检查当前线程中断状态**：使用 `Thread.interrupted()`，适合在循环中检查并重置
- **检查其他线程中断状态**：使用 `thread.isInterrupted()`，适合监控线程状态
- **捕获 InterruptedException 后**：根据需要决定是否调用 `Thread.currentThread().interrupt()` 恢复中断状态
- **处理中断的标准模式**：
```java
  public void run() {
      try {
          while (!Thread.currentThread().isInterrupted()) {
              // 执行任务
          }
      } catch (InterruptedException e) {
          // 恢复中断状态，让上层调用者知道线程被中断
          Thread.currentThread().interrupt();
      }
  }
```

#### 总结

- `interrupted()` 用于检查并清除当前线程的中断状态，适合需要"**消费**"中断信号的场景
- `isInterrupted()` 用于查询线程的中断状态而不影响标志，适合**单纯检查**的场景
- 所有会抛出 `InterruptedException` 的方法都会自动清除中断标志
- 合理处理中断是编写可响应、可取消线程代码的关键

### 守护线程是什么？

守护线程是运行在后台的一种特殊进程。它独立于控制终端并且周期性地执行某种任务或等待处理某些发生的事件。在Java 中垃圾回收线程就是特殊的守护线程。

### notify()和notifyAll()有什么区别？

* notify()和notifyAll()都是Object对象用于通知处在等待该对象的线程的方法。
* void notify(): 唤醒一个正在等待该对象的线程。
* void notifyAll(): 唤醒所有正在等待该对象的线程。

### wait() 和 sleep() 的区别

1. sleep 来自 Thread 类，和 wait 来自 Object 类
2. 最主要是 sleep 方法没有释放锁，而 wait 方法释放了锁，使得其他线程可以使用同步控制块或者方法
3. wait，notify 和 notifyAll 只能在同步控制方法或者同步控制块里面使用，而 sleep 可以在任何地方使用
4. sleep 必须捕获异常，而 wait，notify 和 notifyAll 不需要捕获异常

sleep() 方法表示让一个线程进入睡眠状态，等待一定的时间之后，自动醒来进入到可运行状态。一个线程对象调用了 sleep 方法之后，并不会释放他所持有的所有对象锁。

wait() 属于 Object 的成员方法，一旦一个对象调用了 wait 方法，必须要采用 notify() 和 notifyAll() 方法唤醒该进程；如果线程拥有某个或某些对象的同步锁，那么在调用了 wait() 后，这个线程就会释放它持有的所有同步资源。


## 二、线程同步与锁机制

### volatile、ThreadLocal、synchronized 等关键字区别？

#### volatile

volatile 主要是用来在多线程中同步变量。在一般情况下，为了提升性能，每个线程在运行时都会将主内存中的变量保存一份在自己的内存中作为变量副本，但是这样就很容易出现多个线程中保存的副本变量不一致，或与主内存的中的变量值不一致的情况。

当一个变量被 volatile 修饰后，该变量就不能被缓存到线程的内存中，它会告诉编译器不要进行任何移出读取和写入操作的优化，换句话说就是不允许有不同于"主"内存区域的变量拷贝，所以当该变量有变化时，所有调用该变量的线程都会获得相同的值，这就确保了该变量在应用中的可视性。

**注意**：volatile 只能确保操作的是同一块内存，并不能保证操作的原子性。所以 volatile 一般用于声明简单类型变量，使得这些变量具有原子性。但是当该变量的值由自身的上一个决定时，volatile 的作用就将失效。

#### ThreadLocal

**概念：** ThreadLocal 提供了线程隔离的存储机制，每个线程都有一个独立的变量副本。

**工作原理：**
- 每个 Thread 对象内部维护一个 ThreadLocalMap
- ThreadLocal 作为 key，线程的变量副本作为 value 存储在这个 map 中
- 不同线程访问同一个 ThreadLocal 对象时，获取到的是各自的值

**使用场景：**
- 用户会话信息存储（每个请求一个线程）
- 数据库连接管理
- 事务管理

**简单示例：**
```java
ThreadLocal<String> threadLocal = new ThreadLocal<>();

// 线程1
new Thread(() -> {
    threadLocal.set("线程1的数据");
    System.out.println(threadLocal.get()); // 输出：线程1的数据
}).start();

// 线程2
new Thread(() -> {
    threadLocal.set("线程2的数据");
    System.out.println(threadLocal.get()); // 输出：线程2的数据
}).start();
```

**优缺点：**
- 优点：避免线程竞争，无需同步
- 缺点：需要手动清理（调用 remove()），否则会造成内存泄漏

**`ThreadLocalMap` 源码深度解析**

`ThreadLocalMap` 是 `ThreadLocal` 的静态内部类，是整个机制的核心。它不继承 `HashMap`，是完全独立实现的一套专用哈希表。`ThreadLocalMap` 几个最关键的设计决策：

**开放寻址法而非链表**。普通 `HashMap` 用链表处理哈希冲突，`ThreadLocalMap` 用线性探测——冲突时往后找下一个空槽。这样做的原因是 `ThreadLocal` 变量在一个线程内数量很少，线性探测在小表上缓存局部性更好，而且配合 `WeakReference` 的清理逻辑也更简单。

**魔数 `0x61c88647`（黄金分割哈希）**。每个 `ThreadLocal` 实例的 `threadLocalHashCode` 通过原子递增 `0x61c88647` 得到。这个数是 `2^32 × (1 - 黄金比例)`，能让哈希值在 2 的幂次大小的数组中均匀散布，极大减少冲突。

**`expungeStaleEntry` 清理机制**。当 key 被 GC 回收后，slot 里的 key 变为 `null`（stale），但 value 是强引用仍然存活。`expungeStaleEntry` 在探测路径上发现 stale slot 时，不仅清除当前 slot，还会对后续连续 slot 做 rehash，把可能因为之前线性探测位移的 entry 移回更靠近哈希原始位置的地方，防止表越来越碎。

**ThreadLocal 中的 Key 是什么？**

`threadLocal.set("线程1的数据")` 调用时，数据并**不是存在 ThreadLocal 对象里**，而是存在**当前线程自己的 `ThreadLocalMap`** 中。好，现在来画一张图直观展示 ThreadLocal 的存储结构。## 核心答案：Key 是 **ThreadLocal 对象本身**（以弱引用形式）

调用 `threadLocal.set("线程1的数据")` 时，底层逻辑是这样的：

**数据不存在 ThreadLocal 里，而是存在当前线程对象的 `threadLocals` 字段中。** 这个字段是一个 `ThreadLocalMap`，它是 `Thread` 类内部维护的一个特殊 HashMap。

存储时的 Key/Value 分别是：
- **Key** = 当前 `ThreadLocal` 实例本身（被包装成 `WeakReference` 弱引用）
- **Value** = 你传入的数据，如 `"线程1的数据"`

**为什么 Key 要用弱引用？**

这是防止内存泄漏的设计。当外部对 `ThreadLocal` 对象的强引用消失后（例如方法结束、变量被置为 null），弱引用不会阻止 GC 回收它。Key 被回收后变为 `null`，程序（或下次操作时的探测逻辑）可以清理掉对应的 Entry。

但这里有一个经典陷阱：**Key 是弱引用，但 Value 是强引用**。如果线程一直存活（比如线程池中的线程），Key 被 GC 后 Value 仍然存在，就会造成内存泄漏。因此使用完后应该手动调用 `threadLocal.remove()`。

:::

#### synchronized

**概念：** synchronized 是 Java 提供的互斥锁机制，用于控制多个线程对共享资源的访问。

**工作原理：**
- 每个对象都有一个监视器锁（monitor lock）
- 线程执行 synchronized 代码块前必须获得锁，执行完后释放锁
- 其他线程在获得锁前会被阻塞

**使用方式：**

1. **同步方法：**
```java
public synchronized void method() {
    // 锁定的是 this 对象
    // 临界区代码
}

public static synchronized void staticMethod() {
    // 锁定的是 Class 对象
}
```

2. **同步代码块：**
```java
public void method() {
    synchronized(this) {
        // 锁定 this 对象
    }
    
    synchronized(object) {
        // 锁定指定对象
    }
}
```

**简单示例：**
```java
class Counter {
    private int count = 0;
    
    public synchronized void increment() {
        count++;
    }
    
    public synchronized int getCount() {
        return count;
    }
}

// 多个线程安全地访问
Counter counter = new Counter();
new Thread(() -> counter.increment()).start();
new Thread(() -> counter.increment()).start();
```

**优缺点：**
- 优点：简单易用，JVM 自动释放锁，可重入
- 缺点：性能较低，不灵活，无法中断等待的线程

---

#### 对比

| 特性 | ThreadLocal | synchronized |
|------|-----------|--------------|
| 作用 | 线程隔离 | 互斥访问 |
| 锁竞争 | 无竞争 | 有竞争 |
| 适用场景 | 数据隔离 | 共享资源保护 |
| 性能 | 较高 | 较低 |
| 内存风险 | 内存泄漏 | 无 |

**总结：** ThreadLocal 解决的是线程间的数据隔离问题，synchronized 解决的是线程安全的共享资源访问问题。两者应用场景不同，根据具体需求选择。

### 同步方法和同步块，哪个是更好的选择？

**同步块是更好的选择**，原因：

1. 同步块不会锁住整个对象（当然你也可以让它锁住整个对象）。同步方法会锁住整个对象，哪怕这个类中有多个不相关联的同步块，这通常会导致他们停止执行并需要等待获得这个对象上的锁。

2. 同步是高开销的操作，因此尽量减少同步的内容。通常没有必要同步整个方法，同步部分代码块即可。

3. 同步方法默认用 this 或者当前类 class 对象作为锁。同步代码块可以选择以什么来加锁，比同步方法要更颗粒化，我们可以选择只同步会发生问题的部分代码而不是整个方法。

> 代码示例介绍和区别：https://blog.csdn.net/guyue35/article/details/85052537


### 为什么说 Synchronized 是非公平锁？

非公平主要表现在获取锁的行为上，并非是按照申请锁的时间前后给等待线程分配锁的，每当锁被释放后，任何一个线程都有机会竞争到锁，这样做的目的是为了提高执行性能，缺点是可能会产生**线程饥饿**现象。

### 什么是锁消除和锁粗化？

**锁消除**：指虚拟机即时编译器在运行时，对一些代码上要求同步，但被检测到不可能存在共享数据竞争的锁进行消除。主要根据逃逸分析。

**锁粗化**：原则上，同步块的作用范围要尽量小。但是如果一系列的连续操作都对同一个对象反复加锁和解锁，甚至加锁操作在循环体内，频繁地进行互斥同步操作也会导致不必要的性能损耗。锁粗化就是增大锁的作用域。

### Synchronized 用过吗，其原理是什么？

**原理：** Synchronized 是 JVM 实现的互斥同步机制，用于保证多线程环境下的线程安全，依赖对象的 Monitor（监视器锁）。

**实现方式：**

1. **同步代码块**
   - 字节码：`monitorenter` / `monitorexit` 指令
   - 编译器生成两个 `monitorexit`（正常/异常退出）

2. **同步方法**
   - 字节码：`ACC_SYNCHRONIZED` 访问标志
   - 实例方法锁 `this`，静态方法锁 `Class` 对象

**底层机制：**
- 基于对象头的 Mark Word 存储锁状态
- 线程获取 Monitor 所有权 → 计数器 +1 → 执行同步代码 → 计数器 -1 → 释放锁

**锁优化（Java 6+）：**
- 偏向锁 → 轻量级锁 → 重量级锁（自动升级）
- 自旋锁、锁消除、锁粗化等优化技术

**关键点：** 现代 JVM 的 Synchronized 性能已接近显式锁（ReentrantLock），推荐优先使用。

### monitorenter 和 monitorexit 这两个指令是什么意思？

在虚拟机执行到 monitorenter 指令时，首先要尝试获取对象的锁：
- 如果这个对象没有锁定，或者当前线程已经拥有了这个对象的锁，把锁的计数器 +1
- 当执行 monitorexit 指令时将锁计数器 -1
- 当计数器为 0 时，锁就被释放了

如果获取对象失败了，那当前线程就要阻塞等待，直到对象锁被另外一个线程释放为止。Java 中 Synchronize 通过在对象头设置标记，达到了获取锁和释放锁的目的。

### 获取对象的锁，这个"锁"到底是什么？如何确定对象的锁？

**一、锁的本质**

"锁"本质上是 **Monitor（监视器）的引用**，存储在 Java 对象头的 Mark Word 中。

- **同步代码块**：`monitorenter`/`monitorexit` 指令的 Reference 参数指向要锁定的对象
- **同步方法**：隐式锁定 `this`（实例方法）或 `Class` 对象（静态方法）

---

**二、锁对象的确定规则**

| 修饰类型 | 锁对象 | 示例 |
|---------|--------|------|
| **同步代码块** | 括号内指定的对象 | `synchronized(obj)` → 锁 `obj` |
| **实例方法** | 当前实例（`this`） | `synchronized void method()` → 锁 `this` |
| **静态方法** | 类的 Class 对象 | `static synchronized void method()` → 锁 `XXX.class` |

**关键原则：**
- ✅ 同一锁对象的 synchronized 代码互斥执行
- ✅ 非 synchronized 方法不受锁影响，可并发执行
- ✅ 不同锁对象之间互不影响

#### 示例 1：对象锁（实例锁）

```java

    private int count = 0;
    
    // 方式1：同步实例方法 - 锁对象是 this
    public synchronized void method1() {
        count++;
        System.out.println(Thread.currentThread().getName() + " method1: " + count);
    }
    
    // 方式2：同步代码块 - 显式锁定 this
    public void method2() {
        synchronized (this) {
            count++;
            System.out.println(Thread.currentThread().getName() + " method2: " + count);
        }
    }
    
    // 方式3：同步代码块 - 锁定指定对象
    private final Object lock = new Object();
    public void method3() {
        synchronized (lock) {
            count++;
            System.out.println(Thread.currentThread().getName() + " method3: " + count);
        }
    }
    
    // 非同步方法 - 不受锁影响
    public void method4() {
        System.out.println(Thread.currentThread().getName() + " method4 - 无需等待锁");
    }
}

// 测试

}
```

### 什么是可重入性，为什么说 Synchronized 是可重入锁？

可重入性是锁的一个基本要求，是为了解决自己锁死自己的情况。

对 Synchronized 来说，可重入性是显而易见的，在执行 monitorenter 指令时，如果这个对象没有锁定，或者当前线程已经拥有了这个对象的锁，就把锁的计数器 +1，其实本质上就通过这种方式实现了可重入性。

### 什么是可重入锁（ReentrantLock）？

Java.util.concurrent.lock 中的 Lock 框架是锁定的一个抽象，它允许把锁定的实现作为Java 类，而不是作为语言的特性来实现。这就为Lock 的多种实现留下了空间，各种实现可能有不同的调度算法、性能特性或者锁定语义。 ReentrantLock 类实现了Lock ，它拥有与synchronized 相同的并发性和内存语义，但是添加了类似锁投票、定时锁等候和可中断锁等候的一些特性。此外，它还提供了在激烈争用情况下更佳的性能。（换句话说，当许多线程都想访问共享资源时，JVM可以花更少的时候来调度线程，把更多时间用在执行线程上。）

Reentrant 锁意味着什么呢？简单来说，它有一个与锁相关的获取计数器，如果拥有锁的某个线程再次得到锁，那么获取计数器就加1，然后锁需要被释放两次才能获得真正释放。这模仿了synchronized 的语义；如果线程进入由线程已经拥有的监控器保护的synchronized 块，就允许线程继续进行，当线程退出第二个（或者后续）synchronized块的时候，不释放锁，只有线程退出它进入的监控器保护的第一个synchronized 块时，才释放锁

> ReentrantLock类中有很多的方法：
>
> * getHoldCount()：当前线程调用 lock() 方法的次数
> * getQueueLength()：当前正在等待获取 Lock 锁的线程的估计数
> * getWaitQueueLength(Condition condition)：当前正在等待状态的线程的估计数，需要传入 Condition 对象
> * hasWaiters(Condition condition)：查询是否有线程正在等待与 Lock 锁有关的 Condition 条件
> * hasQueuedThread(Thread thread)：查询指定的线程是否正在等待获取 Lock 锁
> * hasQueuedThreads()：查询是否有线程正在等待获取此锁定
> * isFair()：判断当前 Lock 锁是不是公平锁
> * isHeldByCurrentThread()：查询当前线程是否保持此锁定
> * isLocked()：查询此锁定是否由任意线程保持
> * tryLock()：线程尝试获取锁，如果获取成功，则返回 true，如果获取失败（即锁已被其他线程获取），则返回 false
> * tryLock(long timeout，TimeUnit unit)：线程如果在指定等待时间内获得了锁，就返回true，否则返回 false
> * lockInterruptibly()：如果当前线程未被中断，则获取该锁定，如果已经被中断则出现异常


### JVM 对 Java 的原生锁做了哪些优化？锁优化机制

**一、历史演进**

**Java 6 之前：重量级锁时代**
- Monitor 完全依赖操作系统的互斥锁（Mutex Lock）
- 线程阻塞/唤醒需要**用户态 ↔ 内核态**频繁切换
- 切换代价高昂，性能开销大

**Java 6 之后：锁优化时代**
- JVM 引入多种锁优化技术
- 根据竞争情况自动选择最优锁实现
- 大幅提升 `synchronized` 性能

---

**二、核心优化技术**

**1. 自旋锁（Spin Lock）**
```
线程请求锁 → 锁被占用 → 不立即阻塞 → 自旋等待（循环检查）
                              ↓
                      其他线程释放锁 → 获取锁成功
                              ↓
                      超过自旋次数 → 阻塞挂起
```
- **优势**：避免线程挂起/唤醒的开销，适用于短时间锁竞争
- **适用场景**：锁持有时间短、竞争不激烈

**2. 锁升级机制（Lock Escalation）**

JVM 提供三种锁实现，根据竞争情况自动升级/降级：

| 锁类型 | 竞争情况 | 特点 | 性能 |
|--------|---------|------|------|
| **偏向锁** | 无竞争（始终由同一线程访问） | 无需同步操作 | ⭐⭐⭐⭐⭐ 最快 |
| **轻量级锁** | 轻度竞争（交替执行，无实际冲突） | CAS 操作，无需阻塞 | ⭐⭐⭐⭐ 较快 |
| **重量级锁** | 激烈竞争（多线程同时竞争） | 操作系统 Mutex，线程阻塞 | ⭐⭐ 较慢 |

---

**三、锁升级流程**
```
无锁状态
  │
  ↓ 线程首次访问
偏向锁（默认）─────────┐
  │                    │
  ↓ 其他线程尝试获取    │ 无其他线程竞争
轻量级锁               │ 一直保持偏向锁
  │                    │
  ↓ 自旋失败/竞争激烈   │
重量级锁 ←─────────────┘
```

**锁升级示例：**
1. **偏向锁阶段**：线程 A 首次获取锁 → 对象头记录线程 A ID → 后续 A 重入无需同步
2. **升级为轻量级锁**：线程 B 尝试获取 → 撤销偏向 → 使用 CAS 竞争
3. **升级为重量级锁**：竞争激烈/自旋失败 → 升级为 OS 互斥锁 → 线程阻塞等待

---

**四、关键特性**

✅ **偏向锁默认开启**：无竞争时性能最优  
✅ **自动升级**：JVM 根据运行时状态动态调整  
✅ **不可降级**：锁只能升级，不会降级（JDK 15+ 默认禁用偏向锁）  
✅ **透明优化**：开发者无需关心，JVM 自动处理

**性能对比：**
```
偏向锁 > 轻量级锁 > 重量级锁
（无同步开销）（CAS）（线程阻塞）
```

**五、实际应用建议**

| 场景 | 推荐锁类型 | 说明 |
|------|-----------|------|
| 单线程频繁访问 | 偏向锁 | 几乎无性能损耗 |
| 交替执行，无冲突 | 轻量级锁 | CAS 操作，性能较好 |
| 高并发、长时间持锁 | 重量级锁 | 避免自旋浪费 CPU |

### 为什么说 Synchronized 是一个悲观锁？乐观锁的实现原理又是什么？什么是 CAS，它有什么特性？

Synchronized 显然是一个悲观锁，因为它的并发策略是悲观的：不管是否会产生竞争，任何的数据操作都必须要加锁、用户态核心态转换、维护锁计数器和检查是否有被阻塞的线程需要被唤醒等操作。

乐观锁的核心算法是 **CAS（Compare and Swap，比较并交换）**，它涉及到三个操作数：内存值、预期值、新值。当且仅当预期值和内存值相等时才将内存值修改为新值。

CAS 具有原子性，它的原子性由 CPU 硬件指令实现保证，即使用 JNI 调用 Native 方法调用由 C++ 编写的硬件级别指令，JDK 中提供了 Unsafe 类执行这些操作。

### 乐观锁一定就是好的吗？

乐观锁避免了悲观锁独占对象的现象，同时也提高了并发性能，但它也有缺点：

1. 乐观锁只能保证一个共享变量的原子操作。如果多一个或几个变量，乐观锁将变得力不从心
2. 长时间自旋可能导致开销大。假如 CAS 长时间不成功而一直自旋，会给 CPU 带来很大的开销
3. ABA 问题。CAS 的核心思想是通过比对内存值与预期值是否一样而判断内存值是否被改过，但这个判断逻辑不严谨

### 那么请谈谈 AQS 框架是怎么回事儿？

AQS（AbstractQueuedSynchronizer 类）是一个用来构建锁和同步器的框架，各种 Lock 包中的锁（常用的有 ReentrantLock、ReadWriteLock），以及其他如 Semaphore、CountDownLatch，甚至是早期的 FutureTask 等，都是基于 AQS 来构建。

1. AQS 在内部定义了一个 volatile int state 变量，表示同步状态
2. AQS 通过 Node 内部类构成的一个双向链表结构的同步队列，来完成线程获取锁的排队工作
3. AQS 通过内部类 ConditionObject 构建等待队列（可有多个）
4. AQS 和 Condition 各自维护了不同的队列

### ReentrantLock 是如何实现可重入性的？

ReentrantLock 内部自定义了同步器 Sync，其实就是加锁的时候通过 CAS 算法，将线程对象放到一个双向链表中，每次获取锁的时候，看下当前维护的那个线程 ID 和当前请求的线程 ID 是否一样，一样就可重入了。

### 活锁（Livelock）

**定义：** 线程或任务没有被阻塞，但由于某些条件始终不满足，导致不断重复"尝试→失败→尝试→失败"的循环。

**特点：**
- 线程处于运行状态（"活"的状态），持续改变状态
- 会消耗CPU资源
- 有可能自行解开（与死锁的关键区别）

### 活锁 vs 死锁

| 特性 | 活锁 | 死锁 |
|------|------|------|
| 线程状态 | 运行中，不断变化 | 阻塞，等待状态 |
| CPU消耗 | 持续消耗 | 不消耗 |
| 自行解开 | 可能 | 不可能 |

### Java中的活锁场景

1. **无限等待：** 所有线程执行`Object.wait(0)`，且没有线程调用`notify()`或`notifyAll()`

2. **无限循环：** 所有线程陷入无法退出的循环逻辑

3. **互相谦让：** 两个线程检测到冲突后都释放资源并重试，形成循环

### 线程饥饿（Starvation）

线程因无法获得所需资源而长期无法执行。例如：低优先级线程在高优先级线程不断到来时，可能永远得不到执行机会。

---

**注意：** 活锁可以视为一种特殊的饥饿现象，但强调的是"持续活动但无进展"的特征。

### 死锁

#### 什么是死锁？引起死锁的原因是什么？

[维基百科](https://zh.wikipedia.org/wiki/%E6%AD%BB%E9%94%81)

由于多个进程竞争共享资源而引起的进程不能向前推进的僵死状态称为死锁。

引起死锁的原因：竞争共享资源且分配资源的顺序不当。

死锁的发生必须满足以下四个条件：
- 互斥条件：一个资源每次只能被一个进程使用
- 请求与保持条件：一个进程因请求资源而阻塞时，对已获得的资源保持不放
- 不剥夺条件：进程已获得的资源，在末使用完之前，不能强行剥夺
- 循环等待条件：若干进程之间形成一种头尾相接的循环等待资源关系

#### 怎么防止死锁？

- 尽量使用 tryLock(long timeout, TimeUnit unit) 的方法，设置超时时间
- 尽量使用 Java.util.concurrent 并发类代替自己手写锁
- 尽量降低锁的使用粒度，尽量不要几个功能用同一把锁
- 尽量减少同步的代码块


### 多线程中的忙循环是什么?

忙循环就是程序员用循环让一个线程等待，不像传统方法wait(), sleep() 或 yield() 它们都放弃了CPU控制，而忙循环不会放弃CPU，它就是在运行一个空循环。这么做的目的是为了保留CPU缓存。

在多核系统中，一个等待线程醒来的时候可能会在另一个内核运行，这样会重建缓存。为了避免重建缓存和减少等待重建的时间就可以使用它了。

**2. 锁的作用范围**
- **synchronized**：可以修饰实例方法、静态方法、代码块
- **Lock**：只能对代码块加锁

**3. 锁的获取状态**
- **synchronized**：无法判断是否成功获取锁，线程会一直阻塞等待
- **Lock**：提供 `tryLock()` 方法，可以尝试获取锁并返回是否成功

  - 可以绑定多个条件：`newCondition()` 实现精确的线程通信

**5. 实现层面**
- **synchronized**：JVM 层面实现，基于监视器（Monitor）机制
- **Lock**：API 层面实现，基于 AQS（AbstractQueuedSynchronizer）框架

**6. 性能表现**
- **synchronized**：Java 6 之后经过大量优化（偏向锁、轻量级锁、自旋锁等），在大多数场景下性能已接近 Lock
- **Lock**：在高并发、需要特殊功能的场景下可能更有优势

### 如何让 Java 的线程彼此同步？你了解过哪些同步器？请分别介绍下

#### 概述

JUC（java.util.concurrent）中提供了三个主要的同步器：**CountDownLatch**、**CyclicBarrier** 和 **Semaphore**，它们可以方便地实现线程之间的协作。

---

#### 1. CountDownLatch（倒计数器）

**作用**：允许一个或多个线程等待其他线程完成一组操作后再继续执行。

**应用场景**：
- **跑步比赛**：裁判需要等待所有运动员跑到终点，才能统计排名和颁奖
- **并发测试**：启动 100 个线程同时访问某个接口，确保它们真正并发执行，而不是顺序执行

**核心方法**：
- `CountDownLatch(int count)`：构造方法，指定计数器初始值
- `countDown()`：计数器减 1（由工作线程调用）
- `await()`：阻塞等待，直到计数器归零（由主线程调用）

**示例代码**：
```java
CountDownLatch latch = new CountDownLatch(5);

// 5个工作线程
for (int i = 0; i < 5; i++) {
    new Thread(() -> {
        System.out.println(Thread.currentThread().getName() + " 完成任务");
        latch.countDown();  // 计数器减1
    }).start();
}

// 主线程等待
latch.await();  // 阻塞直到计数器归零
System.out.println("所有任务完成，继续执行");
```

#### 2. CyclicBarrier（循环栅栏）

**作用**：让一组线程相互等待，直到所有线程都到达某个屏障点，然后同时继续执行。且可以重复使用（Cyclic 的含义）。

**与 CountDownLatch 的区别**：
- CountDownLatch 是一次性的，CyclicBarrier 可以重复使用
- CountDownLatch 是一个或多个线程等待其他线程，CyclicBarrier 是多个线程相互等待

**核心方法**：
- `CyclicBarrier(int parties)`：构造方法，指定等待的线程数量
- `await()`：每调用一次计数减 1，并阻塞当前线程；当计数归零时，所有线程同时被唤醒
- `await()` 返回值：表示当前线程是第几个到达屏障的

**示例代码**：
```java
CyclicBarrier barrier = new CyclicBarrier(3, () -> {
    System.out.println("所有线程到达屏障，开始执行汇总任务");
});

for (int i = 0; i < 3; i++) {
    new Thread(() -> {
        System.out.println(Thread.currentThread().getName() + " 到达屏障");
        try {
            barrier.await();  // 等待其他线程
            System.out.println(Thread.currentThread().getName() + " 冲破屏障，继续执行");
        } catch (Exception e) {
            e.printStackTrace();
        }
    }).start();
}
```

#### 3. Semaphore（信号量）

**作用**：控制同时访问特定资源的线程数量，用于限流和资源访问控制。

**核心方法**：
- `Semaphore(int permits)`：构造方法，指定许可证数量
- `acquire()`：获取一个许可证，如果没有可用许可证则阻塞等待
- `release()`：释放一个许可证

**示例代码**：
```java
Semaphore semaphore = new Semaphore(3);  // 最多3个线程同时访问

for (int i = 0; i < 10; i++) {
    new Thread(() -> {
        try {
            semaphore.acquire();  // 获取许可证
            System.out.println(Thread.currentThread().getName() + " 获得许可，开始执行");
            Thread.sleep(2000);   // 模拟业务操作
            System.out.println(Thread.currentThread().getName() + " 释放许可");
        } catch (InterruptedException e) {
            e.printStackTrace();
        } finally {
            semaphore.release();  // 释放许可证
        }
    }).start();
}
```

**特殊用法**：
- 当 `Semaphore(1)` 时，可以实现类似互斥锁的效果
- 但与真正的互斥锁不同：Semaphore 没有"持有者"的概念，任何线程都可以调用 `release()`，而互斥锁只能由持有锁的线程释放

|--------|------|------------|----------|
| **CountDownLatch** | 一个/多个线程等待其他线程完成 | 否 | 主线程等待子任务完成 |
| **CyclicBarrier** | 多个线程相互等待到达屏障点 | 是 | 多线程分阶段协作 |
| **Semaphore** | 控制同时访问资源的线程数 | 是 | 资源池、限流 |

### 如何让 Java 的线程彼此同步？了解过哪些同步器？

JUC 中的同步器三个主要的成员：CountDownLatch、CyclicBarrier 和 Semaphore。

**CountDownLatch**（倒计数）：允许一个或多个线程等待某些操作完成。
- 跑步比赛，裁判需要等到所有的运动员（"其他线程"）都跑到终点（达到目标），才能去算排名和颁奖
- 模拟并发，需要启动 100 个线程去同时访问某一个地址，希望它们能同时并发

用法：CountDownLatch 构造方法指明计数数量，被等待线程调用 countDown 将计数器减 1，等待线程使用 await 进行线程等待。

**CyclicBarrier**（循环栅栏）：让一组线程互相等待直到所有的都达到某个状态，然后这 N 个线程再继续执行各自后续。
- 典型应用场景是用来等待并发线程结束

用法：CyclicBarrier 的主要方法是 await()，await() 每被调用一次，计数便会减少 1，并阻塞住当前线程。当计数减至 0 时，阻塞解除，所有在此 CyclicBarrier 上面阻塞的线程开始运行。

**Semaphore**（信号量）：用于控制同时访问的线程个数，来达到限制通用资源访问的目的。
- 原理是通过 acquire() 获取一个许可，如果没有就等待，而 release() 释放一个许可

### CyclicBarrier 和 CountDownLatch 看起来很相似，请对比下？

它们的行为有一定相似度，区别主要在于：

- CountDownLatch 是不可以重置的，所以无法重用；CyclicBarrier 没有这种限制，可以重用
- CountDownLatch 的基本操作组合是 countDown/await；CyclicBarrier 的基本操作组合就是 await
- CountDownLatch 的目的是让一个线程等待其他 N 个线程达到某个条件后，自己再去做某个事；而 CyclicBarrier 的目的是让 N 多线程互相等待直到所有的都达到某个状态


### synchronized 和 ReentrantLock 的区别是什么？

synchronized 在早期版本中性能较低，与 ReentrantLock 相比存在明显差距。但从 Java 6 开始，synchronized 经过大量优化（如偏向锁、轻量级锁、自适应自旋等），性能已大幅提升，在大多数场景下与 ReentrantLock 相当。

#### 主要区别

**1. 使用方式**
- **synchronized**：自动加锁和释放锁，使用简单，代码简洁
- **ReentrantLock**：需要手动调用 `lock()` 和 `unlock()`，必须在 finally 块中释放锁

**2. 锁的灵活性**
- **synchronized**：功能相对固定，无法中断等待锁的线程
- **ReentrantLock**：提供更丰富的功能
  - 可中断等锁：`lockInterruptibly()`
  - 可设置超时：`tryLock(timeout)`
  - 可实现公平锁：`new ReentrantLock(true)`
  - 可绑定多个条件：`newCondition()`

**3. 适用范围**
- **synchronized**：可修饰实例方法、静态方法、代码块
- **ReentrantLock**：只能用于代码块

**4. 锁的类型**
- **synchronized**：非公平锁（无法更改）
- **ReentrantLock**：默认非公平锁，可选择公平锁

**5. 性能特点**
- **synchronized**：JVM 层面实现，经过优化后性能优秀，适合简单场景
- **ReentrantLock**：API 层面实现，在高竞争或需要特殊功能时更有优势

#### 选择建议

- **优先使用 synchronized**：代码简洁，不易出错，性能已足够好
- **使用 ReentrantLock 的场景**：需要可中断、超时、公平锁或多条件等高级功能时

### 说一下 Atomic 的原理

Atomic 原子类（如 AtomicInteger、AtomicLong 等）是 Java 并发包中用于实现线程安全的轻量级解决方案，主要通过 **CAS（Compare And Swap）** + **volatile** + **native 方法**来保证原子操作，避免了 synchronized 的重量级锁开销，性能更优。

#### 核心原理

**1. CAS（Compare And Swap）机制**
- CAS 是一种乐观锁策略，包含三个操作数：
  - **内存位置 V**：要更新的变量
  - **预期值 A**：期望的旧值
  - **新值 B**：要设置的新值
- 操作逻辑：仅当 V 的值等于 A 时，才将 V 更新为 B，否则不做任何操作
- CAS 是一个原子操作，由 CPU 指令保证（如 x86 的 `CMPXCHG` 指令）

**2. volatile 关键字**
- 保证变量的**可见性**：一个线程修改后，其他线程立即可见
- 禁止**指令重排序**：确保操作的有序性
- Atomic 类中的 value 字段都用 volatile 修饰

**3. Unsafe 类的 native 方法**
- 底层调用 `Unsafe` 类提供的 native 方法，直接操作内存
- 常用方法：`compareAndSwapInt()`、`compareAndSwapLong()` 等
- 这些方法由 JVM 实现，最终映射到 CPU 的原子指令

#### 工作流程示例

以 `AtomicInteger.incrementAndGet()` 为例：

```java
public final int incrementAndGet() {
    return unsafe.getAndAddInt(this, valueOffset, 1) + 1;
}

// Unsafe 类中的实现
public final int getAndAddInt(Object o, long offset, int delta) {
    int v;
    do {
        v = getIntVolatile(o, offset);  // 获取当前值
    } while (!compareAndSwapInt(o, offset, v, v + delta));  // CAS 操作
    return v;
}
```

**流程说明**：
1. 读取当前值 v
2. 计算新值 v + delta
3. 使用 CAS 尝试更新：如果当前值仍是 v，则更新成功
4. 如果 CAS 失败（其他线程已修改），则循环重试（自旋）

#### 优缺点

**优点**：
- 无锁机制，避免线程阻塞和上下文切换
- 性能高，适合低并发冲突场景
- 代码简洁，易于使用

**缺点**：
- **ABA 问题**：值从 A 变为 B 再变回 A，CAS 无法察觉（可用 `AtomicStampedReference` 解决）
- **自旋开销**：高并发冲突时，CAS 频繁失败导致大量自旋，消耗 CPU
- **只能保证单个变量的原子性**：多个变量需要用锁或 `AtomicReference`

#### 适用场景

- 计数器、序列号生成器
- 状态标志位的更新
- 低到中等并发的原子操作
- 不适合高竞争场景（此时 synchronized 或 Lock 可能更合适）

### 什么是 CopyOnWriteArrayList？

- 实现了 List 接口
- 内部持有一个 ReentrantLock lock = new ReentrantLock()
- 底层是用 volatile transient 声明的数组 array
- 读写分离，写时复制出一个新的数组，完成插入、修改或者移除操作后将新数组赋值给 array


### CopyOnWriteArrayList 为什么并发安全且性能比 Vector 好？

#### Vector 的问题
Vector 在所有方法（增删改查）上都使用 `synchronized` 关键字来保证线程安全：
- **读操作也需要加锁**，即使多个线程同时读取也会相互阻塞
- 每次方法调用都要竞争锁，高并发下性能严重下降
- 适用场景有限，读写混合场景下效率低下

#### CopyOnWriteArrayList 的优势

**1. 读写分离策略**
- **读操作**：完全无锁，多线程可并发读取，性能极高
- **写操作**：采用 Copy-On-Write（写时复制）机制
  - 加锁后复制一份新数组
  - 在新数组上进行修改
  - 修改完成后替换原数组引用

**2. 性能对比**
| 操作类型 | Vector | CopyOnWriteArrayList |
|---------|--------|---------------------|
| 读操作 | 需要加锁 | 无锁，性能优秀 |
| 写操作 | 需要加锁 | 需要加锁 + 复制数组 |
| 并发读 | 相互阻塞 | 完全并发 |

**3. 适用场景**
- ✅ **读多写少**的场景（如配置列表、黑白名单）
- ✅ 遍历操作远多于修改操作
- ✅ 对数据实时一致性要求不高（允许短暂的数据不一致）

#### 核心原理

```java
// 读操作 - 无锁
public E get(int index) {
    return get(getArray(), index);  // 直接读取，无需同步
}

// 写操作 - 写时复制
public boolean add(E e) {
    final ReentrantLock lock = this.lock;
    lock.lock();  // 加锁
    try {
        Object[] elements = getArray();
        int len = elements.length;
        Object[] newElements = Arrays.copyOf(elements, len + 1);  // 复制
        newElements[len] = e;  // 在副本上修改
        setArray(newElements);  // 替换原数组
        return true;
    } finally {
        lock.unlock();
    }
}
```

#### 注意事项

**优点：**
- 读操作性能极高，完全无锁
- 不会出现 `ConcurrentModificationException`
- 线程安全，无需额外同步

**缺点：**
- 写操作开销大（需要复制整个数组）
- 内存占用较高（写时会存在两份数组）
- 数据一致性是最终一致性（读取的可能是旧数据）

#### 总结
CopyOnWriteArrayList 通过**读写分离 + 写时复制**的策略，在读多写少的场景下性能远超 Vector，适合配置管理、监听器列表等应用场景。但如果写操作频繁，建议使用 `Collections.synchronizedList()` 或其他并发集合。

### 为什么 HashTable、ConcurrentHashMap 的 key 和 value 不能为 null？

ConcurrentHashMap 和 HashTable 都是支持并发的，二者规定 key，value 均不能为 null，null 的话，会抛出空指针异常。

**原因**：当通过 get(k) 获取对应的 value 时，如果获取到的是 null 时，无法判断它是 put(k,v) 的时候 value 为 null，还是这个 key 从来没有做过映射。这会导致多线程安全问题。

HashMap 允许 key 和 value 为 null，在单线程时不会出现问题，但是多线程下就是线程不安全的。

## 四、线程池

### 什么是线程池？

线程池是一种多线程处理形式，处理过程中将任务添加到队列，然后在创建线程后自动启动这些任务。

### 创建线程池有哪几种方式？

线程池创建有七种方式，最核心的是最后一种：

#### 1. **newSingleThreadExecutor()**：单线程线程池

单线程线程池,保证所有任务按照提交顺序串行执行。

**主要特性:**

* 线程池中只有一个工作线程(核心线程数 = 最大线程数 = 1)
* 所有任务按照提交顺序依次执行(FIFO)
* 使用无界 LinkedBlockingQueue 作为工作队列
* keepAliveTime = 0(线程永不超时)
* 如果该线程异常终止,会自动创建一个新线程替代

**与直接使用单线程的区别:**

* 提供任务队列和线程管理机制
* 线程意外终止时会自动重建,保证任务继续执行
* 统一的生命周期管理(shutdown/shutdownNow)

**典型使用场景:**

* 需要保证任务执行顺序的场景
* 需要串行执行任务,避免并发问题
* 简单的后台任务处理(如日志写入、文件操作)

> 注意:
> - 使用无界队列,任务积压可能导致 OOM
> - 所有任务串行执行,不适合高并发或耗时任务场景
> - 与 `Executors.newFixedThreadPool(1)` 不同,SingleThreadExecutor 返回的线程池无法通过配置修改线程数量

---

**线程池选择建议:**

根据《Thinking in Java》第四版的建议:

* **首选 CachedThreadPool**: 适用于执行大量短期异步任务的场景。它会根据需要创建线程,并在线程空闲时回收,通常能自动优化到合理的线程数量。

* **考虑 FixedThreadPool**: 当 CachedThreadPool 可能引发问题时使用,特别是:
  - 需要限制并发线程数量,避免资源耗尽
  - 执行大量长时间运行的任务
  - 需要稳定可控的线程数量(如服务器环境)

* **使用 ScheduledThreadPool**: 需要定时或周期性执行任务时

* **使用 SingleThreadExecutor**: 需要保证任务按顺序串行执行时

#### 2. **newCachedThreadPool()**：可缓存线程池 

缓存型线程池,优先复用池中空闲的线程。如果有可用的空闲线程,就复用它;如果没有,则创建一个新线程加入池中。

缓存型线程池通常用于执行大量生存期很短的异步任务。因此在一些面向长连接的 daemon 型 SERVER 中用得不多。但对于生存期短、任务数量多的异步场景,它是 Executor 的首选。

能够被复用的线程必须是在空闲超时时间(keepAliveTime)内的线程,默认超时时间是 60 秒。超过这个空闲时长,线程实例将被终止并从池中移除。

> 注意:
> - 放入 CachedThreadPool 的线程不必担心资源泄漏,超过 60 秒不活动会自动被终止
> - 这是一个无界线程池(核心线程数为 0,最大线程数为 Integer.MAX_VALUE),可以根据需要自动创建和回收线程
> - 适用于执行很多短期异步任务的场景,但不适合长时间运行的任务,否则可能创建过多线程导致系统资源耗尽

#### 3. **newFixedThreadPool(int nThreads)**：固定大小线程池

固定大小线程池,与 CachedThreadPool 类似也会复用线程,但不能动态创建新线程。

其独特之处:线程池中始终维持固定数量的线程。如果所有线程都在执行任务,新提交的任务会被放入无界阻塞队列(LinkedBlockingQueue)中等待,直到有线程空闲出来。

和 CachedThreadPool 不同,FixedThreadPool 的线程不会因为空闲而被回收(keepAliveTime 为 0,意味着核心线程永不超时)。因此,FixedThreadPool 适用于负载较重的服务器场景,可以限制并发线程数量,避免资源耗尽。

从源代码实现来看,CachedThreadPool 和 FixedThreadPool 都是基于 ThreadPoolExecutor 实现,只是参数配置不同:

* **FixedThreadPool**:
  - 核心线程数 = 最大线程数 = nThreads(固定值)
  - keepAliveTime = 0(核心线程永不超时)
  - 工作队列:无界 LinkedBlockingQueue

* **CachedThreadPool**:
  - 核心线程数 = 0
  - 最大线程数 = Integer.MAX_VALUE(理论上无限制,未考虑系统资源限制)
  - keepAliveTime = 60 秒
  - 工作队列:SynchronousQueue(无容量,直接传递任务)

> 注意:
> - FixedThreadPool 使用无界队列,如果任务提交速度持续大于处理速度,可能导致队列无限增长,引发 OOM
> - 适合执行长期任务或需要严格控制并发数的场景


#### 4. **newSingleThreadScheduledExecutor()**：单线程调度池

单线程调度池,结合了 SingleThreadExecutor 和 ScheduledThreadPool 的特性。

**主要特性:**

* 线程池中只有一个工作线程(核心线程数 = 1)
* 支持定时和周期性任务执行
* 所有任务按照指定的延迟时间或周期串行执行
* 使用 DelayedWorkQueue 作为工作队列,按延迟时间排序
* 如果该线程异常终止,会自动创建新线程替代,保证调度任务继续执行

**核心方法:**

* `schedule(Runnable, delay, TimeUnit)` - 延迟执行一次
* `scheduleAtFixedRate(Runnable, initialDelay, period, TimeUnit)` - 固定频率周期执行
* `scheduleWithFixedDelay(Runnable, initialDelay, delay, TimeUnit)` - 固定延迟周期执行

**典型使用场景:**

* 需要定时执行且保证任务串行的场景
* 单线程的定时任务调度(如定时数据清理、状态检查)
* 替代 Timer,提供更可靠的单线程调度机制
* 避免多个定时任务并发执行导致的资源竞争

**与其他线程池的对比:**

| 特性 | SingleThreadScheduledExecutor | ScheduledThreadPool | SingleThreadExecutor |
|------|------------------------------|---------------------|---------------------|
| 线程数 | 1 | 指定数量 | 1 |
| 定时任务 | ✓ | ✓ | ✗ |
| 周期任务 | ✓ | ✓ | ✗ |
| 任务执行 | 串行 | 可并发 | 串行 |

> 注意:
> - 所有任务串行执行,如果某个任务执行时间过长,会影响后续任务的调度精度
> - 适合轻量级的定时任务,不适合耗时的周期性任务
> - 与 Timer 相比,线程异常不会导致整个调度终止,更加健壮
> - 返回的 ScheduledExecutorService 不能重新配置线程数量

**使用示例:**

```java
ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();

// 延迟5秒执行一次
scheduler.schedule(() -> System.out.println("延迟任务"), 5, TimeUnit.SECONDS);

// 初始延迟1秒,之后每3秒执行一次
scheduler.scheduleAtFixedRate(() -> System.out.println("周期任务"), 1, 3, TimeUnit.SECONDS);

// 使用完毕后关闭
scheduler.shutdown();
```

#### 5. **newScheduledThreadPool(int corePoolSize)**

调度型线程池,支持定时及周期性任务执行。

**主要特性:**

* 线程池大小固定(核心线程数由参数指定,最大线程数为 Integer.MAX_VALUE)
* 支持延迟执行任务(scheduleWithFixedDelay/schedule)
* 支持周期性执行任务(scheduleAtFixedRate)
* 使用 `DelayedWorkQueue` 作为工作队列,按照延迟时间排序任务

**典型使用场景:**

* 定时任务:延迟一段时间后执行一次
* 周期任务:每隔固定时间执行一次(如心跳检测、数据同步)
* 替代 Timer/TimerTask,提供更强大和灵活的调度能力

**核心方法:**

* `schedule(Runnable, delay, TimeUnit)` - 延迟执行一次
* `scheduleAtFixedRate(Runnable, initialDelay, period, TimeUnit)` - 固定频率周期执行
* `scheduleWithFixedDelay(Runnable, initialDelay, delay, TimeUnit)` - 固定延迟周期执行

> 注意:
> - scheduleAtFixedRate 以固定的频率执行,不考虑任务执行时间
> - scheduleWithFixedDelay 在上次任务完成后,再等待指定延迟时间才开始下次执行
> - 如果任务执行时间超过周期时间,下次任务会立即执行,不会并发执行

#### 6. **newWorkStealingPool(int parallelism)**：工作窃取线程池（Java 8+）

#### 7. **ThreadPoolExecutor()**：最原始、最灵活的构造方法

### 线程池都有哪些状态？

- **RUNNING**：接受新的任务，处理等待队列中的任务
- **SHUTDOWN**：不接受新的任务提交，但是会继续处理等待队列中的任务
- **STOP**：不接受新的任务提交，不再处理等待队列中的任务，中断正在执行任务的线程
- **TIDYING**：所有的任务都销毁了，workCount 为 0
- **TERMINATED**：terminated() 方法结束后，线程池的状态就会变成这个

### 创建线程池的几个核心构造参数？

- **corePoolSize**：线程池的核心线程数
- **maximumPoolSize**：线程池允许的最大线程数  
- **keepAliveTime**：超过核心线程数时闲置线程的存活时间
- **workQueue**：任务执行前保存任务的队列

### 线程池中 submit() 和 execute() 方法有什么区别？

- execute()：只能执行 Runnable 类型的任务。
- submit()：可以执行 Runnable 和 Callable 类型的任务。

Callable 类型的任务可以获取执行的返回值，而 Runnable 执行无返回值。

### 线程池中的线程是怎么创建的？是一开始就随着线程池的启动创建好的吗？

**答案：不是。** 线程池采用**懒加载（延迟初始化）**策略，默认初始化后不创建任何 Worker 线程，等待任务提交时才按需创建。

---

**线程创建时机（execute() 方法执行流程）：**

1. **当前线程数 < corePoolSize**
   - ✅ **立即创建核心线程**执行任务
   - 即使有空闲线程，也会创建新线程

2. **当前线程数 ≥ corePoolSize**
   - ✅ **任务加入 workQueue** 等待执行
   - 由已有线程从队列中获取任务

3. **队列已满 且 当前线程数 < maximumPoolSize**
   - ✅ **创建非核心线程**立即执行任务
   - 突发流量时的应急处理

4. **队列已满 且 当前线程数 ≥ maximumPoolSize**
   - ❌ **触发拒绝策略**（RejectedExecutionHandler）
   - 默认抛出 `RejectedExecutionException`

---

**流程图：**
```
提交任务
  │
  ├─ 线程数 < corePoolSize？
  │   └─ 是 → 创建核心线程执行
  │
  ├─ 否 → workQueue 未满？
  │   └─ 是 → 加入队列等待
  │
  ├─ 否 → 线程数 < maximumPoolSize？
  │   └─ 是 → 创建非核心线程执行
  │
  └─ 否 → 执行拒绝策略
```

---

**特殊情况：**
- 可通过 `prestartAllCoreThreads()` 方法提前创建所有核心线程
- 适用于任务密集型场景，避免首次执行的延迟

**示例代码：**
```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(...);

// 预热：提前创建所有核心线程
pool.prestartAllCoreThreads();
```

### Java 中的线程池是如何实现的？

**核心实现原理：**

1. **线程抽象（Worker）**
   - 线程池中的"线程"被抽象为静态内部类 `Worker`
   - `Worker` 基于 AQS（AbstractQueuedSynchronizer）实现
   - 所有 Worker 存储在线程池的 `HashSet<Worker> workers` 成员变量中

2. **任务队列**
   - 待执行的任务存放在 `BlockingQueue<Runnable> workQueue` 中
   - 支持多种队列实现（ArrayBlockingQueue、LinkedBlockingQueue 等）

3. **工作机制**
   ```
   提交任务 → 核心线程满？
            ↓ 否              ↓ 是
         创建新线程      → 加入 workQueue
                              ↓ 队列满？
                              ↓ 是
                         创建非核心线程
                              ↓ 达到最大线程数？
                              ↓ 是
                         执行拒绝策略
   ```

**基本思想：** Worker 线程不断从 workQueue 中取出任务并执行，实现线程复用和任务调度。

**关键组件：**
- `workers`：管理工作线程
- `workQueue`：缓存待执行任务
- `ThreadFactory`：创建新线程
- `RejectedExecutionHandler`：处理任务拒绝策略

**核心优势**
- **线程复用**：避免频繁创建/销毁线程的开销
- **任务缓冲**：通过 BlockingQueue 解耦任务提交和执行
- **资源控制**：限制最大线程数，防止资源耗尽

### 什么是Java Timer类？如何创建一个有特定时间间隔的任务？

### Java中的同步集合与并发集合有什么区别？

同步集合与并发集合都为多线程和并发提供了合适的线程安全的集合，不过并发集合的可扩展性更高。在Java1.5之前程序员们只有同步集合来用且在多线程并发的时候会导致争用，阻碍了系统的扩展性。Java5介绍了并发集合像ConcurrentHashMap，不仅提供线程安全还用锁分离和内部分区等现代技术提高了可扩展性。

不管是同步集合还是并发集合他们都支持线程安全，他们之间主要的区别体现在性能和可扩展性，还有他们如何实现的线程安全上。

同步HashMap, Hashtable, HashSet, Vector, ArrayList 相比他们并发的实现（ConcurrentHashMap, CopyOnWriteArrayList, CopyOnWriteHashSet）会慢得多。造成如此慢的主要原因是锁， 同步集合会把整个Map或List锁起来，而并发集合不会。并发集合实现线程安全是通过使用先进的和成熟的技术像锁剥离。

比如ConcurrentHashMap 会把整个Map 划分成几个片段，只对相关的几个片段上锁，同时允许多线程访问其他未上锁的片段。

同样的，CopyOnWriteArrayList 允许多个线程以非同步的方式读，当有线程写的时候它会将整个List复制一个副本给它。

如果在读多写少这种对并发集合有利的条件下使用并发集合，这会比使用同步集合更具有可伸缩性。


### Java中invokeAndWait 和 invokeLater有什么区别？

这两个方法是Swing API 提供给Java开发者用来从当前线程而不是事件派发线程更新GUI组件用的。InvokeAndWait()同步更新GUI组件，比如一个进度条，一旦进度更新了，进度条也要做出相应改变。如果进度被多个线程跟踪，那么就调用invokeAndWait()方法请求事件派发线程对组件进行相应更新。而invokeLater()方法是异步调用更新组件的。

### 读写锁可以用于什么应用场景？

读写锁（ReadWriteLock）是一种特殊的锁机制，适用于**"读多写少"**的并发场景。它允许多个线程同时进行读操作，但写操作是独占的，能够在保证线程安全的前提下显著提升并发性能。

#### 核心特性

**读锁（共享锁）**：
- 多个线程可以同时持有读锁
- 读锁之间不互斥，可并发执行
- 当有线程持有写锁时，读锁会被阻塞

**写锁（独占锁）**：
- 同一时刻只能有一个线程持有写锁
- 写锁与读锁、写锁之间都互斥
- 持有写锁时，其他线程无法获取读锁或写锁
- 核心实现：通过 `Sync.tryAcquire()` 方法判断，当 `state != 0`（存在任何锁）且不满足重入条件时，获取失败并阻塞
 > 参考: ReentrantReadWriteLock->tryAcquire 源码

#### 典型应用场景

1. **缓存系统**：频繁读取缓存数据，偶尔更新缓存
2. **配置中心**：应用频繁读取配置，配置变更较少
3. **统计数据**：多线程读取统计结果，定期更新统计数据
4. **数据字典**：大量查询操作，少量增删改操作
5. **白名单/黑名单**：高频检查，低频更新

#### 使用示例

```java
public class CacheExample {
    private final Map<String, Object> cache = new HashMap<>();
    private final ReadWriteLock rwLock = new ReentrantReadWriteLock();
    private final Lock readLock = rwLock.readLock();
    private final Lock writeLock = rwLock.writeLock();
    
    // 读操作：多个线程可同时执行
    public Object get(String key) {
        readLock.lock();
        try {
            return cache.get(key);
        } finally {
            readLock.unlock();
        }
    }
    
    // 写操作：独占执行
    public void put(String key, Object value) {
        writeLock.lock();
        try {
            cache.put(key, value);
        } finally {
            writeLock.unlock();
        }
    }
}
```

```java
class Test {
    private static final ReadWriteLock rwLock = new ReentrantReadWriteLock();
    private static final Lock readLock = rwLock.readLock();
    
    public static void main(String[] args) throws Exception {
        // 线程1：获取读锁
        Thread t1 = new Thread(() -> {
            System.out.println("线程1：尝试获取读锁");
            readLock.lock();
            System.out.println("线程1：成功获取读锁");
            try {
                Thread.sleep(3000); // 持有读锁3秒
                System.out.println("线程1：持有读锁中...");
            } catch (InterruptedException e) {
                e.printStackTrace();
            } finally {
                System.out.println("线程1：释放读锁");
                readLock.unlock();
            }
        });
        
        // 线程2：也获取读锁
        Thread t2 = new Thread(() -> {
            try {
                Thread.sleep(500); // 延迟500ms启动
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
            System.out.println("线程2：尝试获取读锁");
            readLock.lock();
            System.out.println("线程2：成功获取读锁（线程1还没释放！）");
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                e.printStackTrace();
            } finally {
                System.out.println("线程2：释放读锁");
                readLock.unlock();
            }
        });
        
        t1.start();
        t2.start();
        t1.join();
        t2.join();
    }
}
```

#### 性能影响因素

读写锁能否显著提升性能，取决于以下因素：

**1. 读写频率比**
- 读操作远多于写操作时，性能提升明显
- 如果写操作频繁，可能不如使用普通的 synchronized 或 ReentrantLock

**2. 持锁时间**
- 读操作耗时较长时，读写锁优势更明显（多个读操作可并发执行）
- 如果读写操作都很快，锁竞争本身的开销可能抵消收益

**3. 竞争程度**
- 并发线程数较多时，读写锁的并发读能力优势突出
- 低并发场景下，收益不明显

**4. 硬件环境**
- 多核 CPU 环境下，读写锁的并发读特性能充分发挥
- 单核环境下优势有限

#### 注意事项

- **锁降级**：ReentrantReadWriteLock 支持锁降级（写锁降为读锁），但不支持锁升级
- **公平性**：可选择公平或非公平模式，公平模式可避免线程饥饿，但性能略低
- **写锁饥饿**：大量读操作可能导致写线程长时间等待，需根据场景权衡
- **不适用场景**：写操作频繁、读写耗时都很短、低并发的场景不适合使用读写锁

#### 总结

读写锁是针对**读多写少、读操作耗时较长、高并发**场景的优化方案。合理使用可以大幅提升系统吞吐量，但需要根据实际业务特点评估是否适用。


### 并行和并发有什么区别？

- 并行：多个处理器或多核处理器同时处理多个任务。（是真正的物理上的同时发生）
- 并发：多个任务在同一个

  CPU 核上，按细分的时间片轮流(交替)执行，从逻辑上来看那些任务是同时执行。（逻辑上的同时发生）

举个例子：排队打饭，当只有一个窗口可以打饭的时候，我们排成了两排，那么这两排只能一边一个来，这就是并发；\
如果有两个窗口可以打饭的话，一个队一个窗口，那么这两排可以同时进行打饭，这就是并行了。
