## 1. Zookeeper 是什么?

Zookeeper 是一个开源的分布式应用程序协调服务框架，由 Apache 开发，是 Google Chubby 的开源实现。它是 Hadoop 和 HBase 等分布式系统的重要组件。

**核心定位**：为分布式应用提供一致性服务的中间件

**主要功能**：
- 配置管理
- 命名服务
- 分布式同步
- 集群管理
- 分布式协调

---

## 2. Zookeeper 的核心功能有哪些?

### 2.1 集群管理
- 监控节点的存活状态
- 实时感知节点的上线/下线
- 统一管理集群配置信息

### 2.2 Leader 选举
当主节点宕机后，可以从备用节点中自动选举出新的 Leader。Zookeeper 通过 ZAB 协议协助完成选举过程，保证集群的高可用性。

### 2.3 分布式锁
Zookeeper 提供两种类型的分布式锁：

- **独占锁（排他锁）**：同一时刻只允许一个客户端持有锁
- **共享锁（读写锁）**：
  - 读锁可以被多个客户端同时持有
  - 写锁是独占的，与读锁和写锁都互斥

### 2.4 命名服务
在分布式系统中，通过统一的命名服务，客户端可以根据指定的名称获取资源或服务的地址、提供者等信息，类似于 DNS 的功能。

## 3. Zookeeper 有哪些部署模式?

### 3.1 单机模式（Standalone）
- 单台服务器运行 Zookeeper
- 适用于开发和测试环境
- **不具备高可用性**

### 3.2 集群模式（Cluster）
- 多台服务器组成 Zookeeper 集群
- 生产环境推荐使用
- 提供高可用和容错能力
- **建议使用奇数台服务器**（如 3、5、7 台）

### 3.3 伪集群模式（Pseudo-Cluster）
- 在一台物理机上启动多个 Zookeeper 实例
- 主要用于学习和测试
- 不适合生产环境

## 4. Zookeeper 如何保证主从节点的状态同步?

Zookeeper 使用 **ZAB 协议**（Zookeeper Atomic Broadcast，原子广播协议）来保证集群节点间的数据一致性。

### ZAB 协议的两种模式

#### 4.1 恢复模式（Recovery Mode）
**触发条件**：
- 服务启动时
- Leader 节点崩溃时

**工作流程**：
1. 进行 Leader 选举
2. 新 Leader 被选出后，等待大多数 Follower 完成数据同步
3. 同步完成后，退出恢复模式

#### 4.2 广播模式（Broadcast Mode）
**触发条件**：集群正常运行，Leader 已选出且数据已同步

**工作流程**：

1. Leader 接收客户端的写请求
2. Leader 生成提案（Proposal）并分配全局唯一的事务 ID（ZXID）
3. Leader 将提案广播给所有 Follower
4. Follower 接收提案并写入本地事务日志，然后向 Leader 发送 ACK
5. 当 Leader 收到超过半数的 ACK 后，发送 Commit 消息
6. Follower 收到 Commit 后，将事务应用到内存数据库

**核心机制**：通过过半机制（Quorum）保证数据的一致性和可靠性

## 5. 集群中为什么需要 Leader 节点?

### 主要原因

#### 5.1 避免重复计算
某些业务逻辑只需要在集群中的一台机器上执行，其他节点共享执行结果，避免资源浪费。

#### 5.2 保证数据一致性
通过 Leader 统一协调写操作，避免多个节点同时写入造成的数据冲突。

#### 5.3 简化分布式协调
Leader 作为协调者，简化了分布式系统中的复杂协调逻辑。

#### 5.4 提高性能
集中处理写请求，减少节点间的通信开销，提升整体性能。

## 6. 集群中有 3 台服务器，其中一台宕机，Zookeeper 还能正常工作吗?

**答案：可以继续正常工作**

### 原理说明

Zookeeper 采用**过半存活机制**（Quorum）：
- 集群中只要有超过半数的节点存活，集群就能正常提供服务
- 3 台服务器的集群，允许最多 1 台宕机（3/2 = 1.5，向下取整为 1）

### 容错能力计算

**建议**：生产环境推荐使用奇数台服务器（如 3、5、7）。

| 集群规模 | 最多允许宕机数 | 计算公式 |
|---------|--------------|---------|
| 3 台    | 1 台         | (3-1)/2 = 1 |
| 5 台    | 2 台         | (5-1)/2 = 2 |
| 7 台    | 3 台         | (7-1)/2 = 3 |

**原因**：
- 3 台和 4 台都最多允许 1 台宕机，4 台多余
- 5 台和 6 台都最多允许 2 台宕机，6 台多余
- 偶数台不仅增加成本，容错能力却没有提升

**对比示例**：

| 集群规模 | 最多允许宕机数 | 说明 |
|---------|--------------|------|
| 3 台    | 1 台         | 推荐 ✓ |
| 4 台    | 1 台         | 浪费资源，不推荐 ✗ |
| 5 台    | 2 台         | 推荐 ✓ |
| 6 台    | 2 台         | 浪费资源，不推荐 ✗ |
| 7 台    | 3 台         | 推荐 ✓ |

**结论**：使用奇数台服务器能以最低成本获得最优容错能力。

## 7. Zookeeper 的 Watcher 通知机制是什么?

### 工作原理

Watcher（观察者）是 Zookeeper 实现分布式协调的核心机制之一。

**流程**：
1. 客户端在某个 ZNode 上注册 Watcher
2. 当该 ZNode 发生变化时（数据修改、节点删除、子节点变化等）
3. Zookeeper 服务端触发 Watcher 事件
4. 客户端收到通知并执行相应的回调逻辑
5. 客户端根据变化做出业务响应

### 特性

- **一次性触发**：Watcher 触发一次后会被自动移除，需要重新注册
- **异步通知**：客户端异步接收事件通知
- **轻量级**：通知只包含事件类型和路径，不包含数据内容

### 典型应用场景

- 配置中心：监听配置变化，实时更新应用配置
- 服务发现：监听服务节点变化，动态感知服务上下线
- 分布式锁：监听锁节点的删除事件

## 8. Zookeeper 分布式锁的实现原理

### 实现步骤

#### 8.1 获取锁
1. 客户端在指定的锁节点目录下，创建一个**临时顺序节点**（EPHEMERAL_SEQUENTIAL）
2. 客户端获取该目录下的所有子节点列表
3. 判断自己创建的节点序号是否最小：
   - **是**：获取锁成功，执行业务逻辑
   - **否**：监听（Watch）比自己序号小的前一个节点，进入等待状态

#### 8.2 等待锁
当监听的节点被删除时（前一个客户端释放锁），重新检查自己是否是序号最小的节点。

#### 8.3 释放锁
业务逻辑执行完毕后，删除自己创建的临时节点，锁自动释放。

### 示例流程

假设三个客户端 A、B、C 同时竞争锁：

```
1. 客户端 A 创建节点：/lock/0000000001
2. 客户端 B 创建节点：/lock/0000000002
3. 客户端 C 创建节点：/lock/0000000003

4. A 发现自己是最小节点，获取锁
5. B 监听节点 0000000001
6. C 监听节点 0000000002

7. A 执行完业务，删除节点 0000000001
8. B 收到通知,发现自己是最小节点,获取锁
9. C 继续等待...
```

### 优势

- **公平性**：按照请求顺序获取锁，避免饥饿
- **高可用**：临时节点在客户端宕机后自动删除,防止死锁
- **羊群效应优化**：每个客户端只监听前一个节点,而非所有节点

### 适用场景

- 分布式任务调度
- 资源互斥访问
- 集群主备切换

## ZooKeeper 的过半机制如何防止脑裂？

### 什么是集群脑裂？

**脑裂（Split-Brain）** 是指在分布式集群中，由于网络分区故障，导致集群被分割成多个独立的子集群，每个子集群都选举出自己的 Leader，从而出现多个 Leader 同时存在的异常情况。

### 典型场景

在实际部署中，为了提高可用性，集群通常会跨机房部署。当机房间的网络发生故障时，就可能引发脑裂问题。

### 案例分析

假设有一个由 6 台服务器组成的 ZooKeeper 集群，跨 2 个机房部署，每个机房 3 台服务器。

**正常情况**：
- 集群中只有 1 个 Leader
- 所有节点数据保持一致

**网络分区后（未采用过半机制）**：
1. 两个机房之间的网络连接中断
2. 机房 A 的 3 台服务器认为机房 B 的服务器已下线
3. 机房 B 的 3 台服务器认为机房 A 的服务器已下线
4. **两个机房各自选举出自己的 Leader**
5. 两个子集群同时对外提供服务

**网络恢复后的问题**：
- 集群中存在 2 个 Leader（脑裂）
- 两个 Leader 可能接收了不同的写请求
- 导致数据不一致、数据冲突等严重问题

---

### 过半机制如何防止脑裂？

ZooKeeper 通过 **Quorum（过半）机制** 从根本上杜绝了脑裂现象的发生。

#### 核心原则

**只有获得超过半数节点支持的候选者才能成为 Leader**

#### 防脑裂原理

在任何网络分区场景下，集群最多只能有一个子集群的节点数量超过半数，因此：

- **大分区**：节点数 > 总数/2，可以选举出 Leader
- **小分区**：节点数 < 总数/2，无法选举出 Leader

这确保了**同一时刻最多只有一个 Leader 存在**。

过半票数 = ⌊总节点数 / 2⌋ + 1

> 其中 ⌊ ⌋ 表示向下取整。


#### 实例分析

##### 场景 1：6 台服务器，平均分配（3 + 3）

```
机房 A: 3 台服务器  |  网络断开  |  机房 B: 3 台服务器
需要 4 票才能选出 Leader

结果：
- 机房 A：3 票 < 4 票，无法选出 Leader ✗
- 机房 B：3 票 < 4 票，无法选出 Leader ✗
- 整个集群暂时不可用，但避免了脑裂
```

##### 场景 2：5 台服务器，不均匀分配（3 + 2）

```
机房 A: 3 台服务器  |  网络断开  |  机房 B: 2 台服务器
需要 3 票才能选出 Leader

结果：
- 机房 A：3 票 = 3 票，可以选出 Leader ✓
- 机房 B：2 票 < 3 票，无法选出 Leader ✗
- 只有机房 A 对外提供服务，避免了脑裂
```

#### 场景 3：7 台服务器，不均匀分配（4 + 3）

```
机房 A: 4 台服务器  |  网络断开  |  机房 B: 3 台服务器
需要 4 票才能选出 Leader

结果：
- 机房 A：4 票 = 4 票，可以选出 Leader ✓
- 机房 B：3 票 < 4 票，无法选出 Leader ✗
- 只有机房 A 对外提供服务，避免了脑裂
```

## ZooKeeper 集群为什么最好奇数台？

### 1. 为什么推荐奇数台服务器？

| 集群规模 | 过半要求 | 最多允许宕机 | 平均分区情况 |
|---------|---------|-------------|-------------|
| 3 台    | 需要 2 票 | 1 台 | 2+2 均无法选主 |
| 4 台    | 需要 3 票 | 1 台 | 2+2 均无法选主 |
| 5 台    | 需要 3 票 | 2 台 | 3+2 只有一方可选主 |
| 6 台    | 需要 4 票 | 2 台 | 3+3 均无法选主 |
| 7 台    | 需要 4 票 | 3 台 | 4+3 只有一方可选主 |

**结论**：奇数台服务器在容错能力相同的情况下，更容易在网络分区时保持服务可用性。

### 2. 过半机制的优势

- **防止脑裂**：数学上保证了不可能同时存在两个获得过半支持的 Leader
- **保证一致性**：确保只有一个权威的数据写入源
- **自动恢复**：网络恢复后，少数分区会自动同步数据并加入多数分区

#### 3. 权衡考虑

过半机制在防止脑裂的同时，也意味着：
- 如果超过半数的节点不可用，整个集群将无法提供服务
- 这是 **CAP 理论**中选择 CP（一致性 + 分区容错性）而牺牲部分可用性的体现

## ZooKeeper 集群角色

但是，在 ZooKeeper 中没有选择传统的 Master/Slave 概念，而是引入了 Leader、Follower 和 Observer 三种角色。如下图所示

![ZooKeeper 集群中角色](https://oss.javaguide.cn/github/javaguide/distributed-system/zookeeper/zookeeper-cluser-roles.png)

ZooKeeper 集群中的所有机器通过一个 **Leader 选举过程** 来选定一台称为 “**Leader**” 的机器，Leader 既可以为客户端提供写服务又能提供读服务。除了 Leader 外，**Follower** 和 **Observer** 都只能提供读服务。Follower 和 Observer 唯一的区别在于 Observer 机器不参与 Leader 的选举过程，也不参与写操作的“过半写成功”策略，因此 Observer 机器可以在不影响写性能的情况下提升集群的读性能。

| 角色     | 说明                                                                                                                                                                              |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Leader   | 为客户端提供读和写的服务，负责投票的发起和决议，更新系统状态。                                                                                                                    |
| Follower | 为客户端提供读服务，如果是写服务则转发给 Leader。参与选举过程中的投票。                                                                                                           |
| Observer | 为客户端提供读服务，如果是写服务则转发给 Leader。不参与选举过程中的投票，也不参与“过半写成功”策略。在不影响写性能的情况下提升集群的读性能。此角色于 ZooKeeper3.3 系列新增的角色。 |

## ZooKeeper 集群 Leader 选举机制详解

### 选举触发场景

Leader 选举在以下情况下触发：
- **集群启动**：所有节点初始状态为 LOOKING，需要选举出 Leader
- **Leader 故障**：网络中断、进程崩溃、长时间无响应等
- **Follower 与 Leader 失联**：超过 Session Timeout 未收到心跳

### 选举核心流程

#### 1. Leader Election（选举阶段）
- 每个节点投票给自己，投票信息包含：(myid, ZXID)
- myid：服务器 ID，配置文件中指定，全局唯一
- ZXID：最新事务 ID，越大表示数据越新
- **投票比较规则**：
  1. 优先选择 ZXID 最大的节点（数据最新）
  2. ZXID 相同时，选择 myid 最大的节点
- 当某个节点获得**超过半数**投票时，成为准 Leader（Candidate Leader）

#### 2. Discovery（发现阶段）
- Followers 与准 Leader 建立连接
- Followers 发送自己的最新 ZXID 和历史事务日志
- 准 Leader 收集所有 Follower 的事务信息，确定集群最新数据版本

#### 3. Synchronization（同步阶段）
- 准 Leader 基于收集到的最新提议历史，向 Followers 同步数据
- 确保所有节点数据一致后，准 Leader 正式升级为 Leader
- 完成同步的 Followers 转为 FOLLOWING 状态

#### 4. Broadcast（广播阶段）
- Leader 正式对外提供服务
- 使用 ZAB 协议（原子广播协议）处理客户端事务请求
- 新加入的节点会先进行数据同步再参与服务

### 节点状态类型

| 状态 | 说明 | 特点 |
|------|------|------|
| **LOOKING** | 寻找 Leader 状态 | 节点不确定 Leader，正在参与选举 |
| **LEADING** | Leader 状态 | 处理写请求，协调事务，广播状态 |
| **FOLLOWING** | Follower 状态 | 参与投票、事务提议，可处理读请求 |
| **OBSERVING** | Observer 状态 | 不参与投票，只同步数据，提升读性能 |

### 关键机制保障

#### 过半机制（Quorum）
- 选举需要超过半数节点同意（N/2 + 1）
- 防止脑裂：网络分区时最多只有一个分区满足过半条件
- 推荐奇数个节点（3、5、7），偶数节点不增加容错能力

#### 数据一致性保证
- **ZXID 结构**：高 32 位为 epoch（选举轮次），低 32 位为计数器
- 每次选举 epoch 递增，保证新 Leader 的事务 ID 一定大于旧 Leader
- 通过两阶段提交（2PC）保证事务原子性

### 选举示例

假设集群有 5 个节点（myid: 1~5），初始状态：
```
节点1: (1, 100)  节点2: (2, 99)  节点3: (3, 100)  
节点4: (4, 98)   节点5: (5, 100)
```

**选举过程**：
1. 所有节点初始投自己
2. 交换投票信息后，比较 (myid, ZXID)
3. 节点 1、3、5 的 ZXID 都是 100（最大），比较 myid
4. 所有节点最终投票给节点 5（ZXID=100, myid=5）
5. 节点 5 获得 5 票（超过半数 3 票），当选 Leader

## 数据模型（Data Model）

### 树形结构

ZooKeeper 采用**层次化树形结构**来组织数据，类似于 Unix 文件系统：

- 使用斜杠 `/` 分割路径
- 根节点用 `/` 表示
- 每个节点可以存储数据（数字、字符串、二进制序列）
- 每个节点可以拥有多个子节点

![ZooKeeper 数据模型](https://oss.javaguide.cn/github/javaguide/distributed-system/zookeeper/znode-structure.png)

### 重要限制

> ⚠️ **核心原则**：ZooKeeper 是用来**协调服务**的,不是用来存储业务数据的!
> 
> - 每个节点数据大小上限：**1MB**
> - 建议存储配置信息、状态标识等轻量级数据

##  ZNode（数据节点）

### ZNode 定义

**znode** 是 ZooKeeper 中数据的最小单元，具有唯一路径标识。

### ZNode 类型（4种）

| 类型 | 特性 | 适用场景 |
|------|------|---------|
| **持久节点**<br>(PERSISTENT) | • 创建后一直存在<br>• 需手动删除<br>• 即使集群宕机也会保留 | 存储配置信息、元数据 |
| **临时节点**<br>(EPHEMERAL) | • 生命周期绑定客户端会话<br>• 会话断开则自动删除<br>• **只能作为叶子节点** | 服务注册与发现、分布式锁 |
| **持久顺序节点**<br>(PERSISTENT_SEQUENTIAL) | • 持久节点特性<br>• 子节点名称自动编号<br>• 如 `/node1/app0000000001` | 分布式队列 |
| **临时顺序节点**<br>(EPHEMERAL_SEQUENTIAL) | • 临时节点特性<br>• 子节点名称自动编号 | 分布式锁的公平实现 |

### ZNode 结构

每个 znode 由两部分组成：

```
znode
├── data: 节点存储的实际数据
└── stat: 节点状态信息
```

**示例**：查看 znode 信息

```shell
[zk: 127.0.0.1:2181(CONNECTED) 6] get /dubbo
null                          # 数据内容
cZxid = 0x2                   # 创建时的事务ID
ctime = Tue Nov 27 11:05:34 CST 2018
mZxid = 0x2                   # 最后修改的事务ID
mtime = Tue Nov 27 11:05:34 CST 2018
pZxid = 0x3                   # 子节点列表最后修改的事务ID
cversion = 1                  # 子节点版本号
dataVersion = 0               # 数据版本号
aclVersion = 0                # ACL版本号
ephemeralOwner = 0x0          # 临时节点的sessionId(0表示持久节点)
dataLength = 0                # 数据长度
numChildren = 1               # 子节点个数
```

###  Stat 状态信息详解

| 字段 | 说明 | 更新时机 |
|------|------|---------|
| **cZxid** | 创建时的事务ID | 节点创建时 |
| **ctime** | 创建时间 | 节点创建时 |
| **mZxid** | 最后修改的事务ID | 节点数据更新时 |
| **mtime** | 最后修改时间 | 节点数据更新时 |
| **pZxid** | 子节点列表最后修改的事务ID | 子节点增删时（内容变更不算） |
| **cversion** | 子节点版本号 | 子节点列表变化时 +1 |
| **dataVersion** | 数据版本号 | 每次更新数据时 +1（即使内容未变） |
| **aclVersion** | ACL版本号 | ACL权限变更时 +1 |
| **ephemeralOwner** | 临时节点的 sessionId | 持久节点为 0 |
| **dataLength** | 数据内容长度（字节） | - |
| **numChildren** | 直接子节点个数 | - |

## 版本机制（Version）

ZooKeeper 为每个 znode 维护 **3 个版本号**（用于实现乐观锁）：

| 版本类型 | 作用 |
|---------|------|
| **dataVersion** | 数据内容版本号 |
| **cversion** | 子节点列表版本号 |
| **aclVersion** | ACL权限版本号 |

**应用场景**：防止并发修改冲突
```java
// 更新数据时可指定期望的版本号
zk.setData("/path", data, expectedVersion); 
// 版本不匹配会抛出异常
```

## 权限控制（ACL）

### 权限类型（5种）

| 权限 | 说明 | 注意事项 |
|------|------|---------|
| **CREATE** | 创建子节点 | 针对**子节点** |
| **READ** | 读取节点数据、列出子节点 | - |
| **WRITE** | 更新节点数据 | - |
| **DELETE** | 删除子节点 | 针对**子节点** |
| **ADMIN** | 设置节点ACL权限 | - |

> 💡 **重点**：CREATE 和 DELETE 权限都是针对**子节点**的操作

### 认证方式（4种）

| 方式 | 说明 | 示例 |
|------|------|------|
| **world** | 默认方式，所有人可访问 | `world:anyone` |
| **auth** | 已认证用户可访问 | 不需要指定ID |
| **digest** | 用户名密码认证 | `digest:username:password` |
| **ip** | IP白名单 | `ip:192.168.1.100` |

## 事件监听器（Watcher）

### 核心机制

Watcher 是 ZooKeeper 实现**分布式协调**的关键特性：

```
客户端                    ZooKeeper服务端
  |                            |
  |----(1)注册Watcher--------->|
  |                            |
  |                       (2)数据变化
  |                            |
  |<---(3)触发事件通知---------|
  |                            |
  |----(4)处理事件------------>|
```

![ZooKeeper Watcher 机制](https://oss.javaguide.cn/github/javaguide/distributed-system/zookeeper/zookeeper-watcher.png)

### 特点

- **一次性触发**：Watcher 触发后自动移除，需重新注册
- **异步回调**：事件通知是异步的
- **轻量级**：只通知事件发生，不包含数据变更内容

### 应用场景

- 配置中心：监听配置变化
- 服务发现：监听服务上下线
- 分布式锁：监听锁释放事件
- 集群管理：监听节点状态

## 会话（Session）

### 定义

Session 是客户端与服务器之间的 **TCP 长连接**，用于：

- 心跳检测保持连接
- 发送请求和接收响应
- 接收 Watcher 事件通知

### 核心属性

| 属性 | 说明 |
|------|------|
| **sessionId** | 会话唯一标识（全局唯一） |
| **sessionTimeout** | 会话超时时间 |

### 会话保持机制

```
客户端断开 → 在 sessionTimeout 内重连 → 会话保持有效
             ↓
        超过 sessionTimeout → 会话失效 → 临时节点被删除
```

**关键点**：
- 断线后可重连到集群中**任意一台**服务器
- 只要在超时时间内恢复连接，会话仍然有效
- sessionId 在整个集群中全局唯一

---

### 典型应用场景

| 场景 | 使用的特性 | 实现要点 |
|------|-----------|---------|
| **配置管理** | 持久节点 + Watcher | 配置存储在 znode，客户端监听变化 |
| **服务注册与发现** | 临时节点 + Watcher | 服务上线创建临时节点，下线自动删除 |
| **分布式锁** | 临时顺序节点 | 最小序号获得锁，监听前一个节点 |
| **Master选举** | 临时节点 | 第一个创建成功的成为 Master |
| **分布式队列** | 持久顺序节点 | 按序号顺序消费 |

## 总结

Zookeeper 作为分布式协调服务的基石，通过 ZAB 协议保证数据一致性，通过 Watcher 机制实现事件通知，为分布式系统提供了可靠的配置管理、命名服务、分布式锁等核心功能。理解其工作原理对于构建高可用分布式系统至关重要。
