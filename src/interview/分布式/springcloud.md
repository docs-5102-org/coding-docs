# Spring Cloud 与微服务面试题汇总

## 1. 什么情况下需要使用分布式事务，有哪些方案？（中等）

### 需要使用分布式事务的场景：
- 跨数据库操作：一个业务流程需要操作多个数据库
- 跨服务调用：订单服务、库存服务、支付服务等多个服务需要保证数据一致性
- 跨系统交互：与第三方系统交互时需要保证事务一致性

### 常见方案：
1. **2PC（两阶段提交）**：强一致性，性能较差，适合对一致性要求极高的场景
2. **3PC（三阶段提交）**：2PC的改进版，增加超时机制
3. **TCC（Try-Confirm-Cancel）**：补偿型事务，性能较好，业务侵入性强
4. **Saga模式**：长事务解决方案，通过事件驱动的补偿机制
5. **本地消息表**：基于消息的最终一致性方案
6. **MQ事务消息**：如RocketMQ的事务消息
7. **Seata**：阿里开源的分布式事务框架

## 3. 分布式和微服务有什么区别？（中等）

### 分布式：
- 是一种架构模式，强调将系统部署在多个节点上
- 关注点：性能、可用性、扩展性
- 可以是单体应用的分布式部署

### 微服务：
- 是分布式架构的一种实现方式
- 强调服务的细粒度拆分和独立部署
- 每个服务独立开发、部署、扩展
- 服务间通过轻量级通信（HTTP/RPC）

### 关系：
微服务一定是分布式的，但分布式不一定是微服务架构。

## 4. 什么是分布式事务的阶段性，空回滚？（中等）

### 防悬挂（阶段性）：
Try阶段因网络问题超时，Cancel先于Try执行，导致Cancel无法找到Try的资源进行回滚。需要在Cancel中判断Try是否执行。

### 空回滚：
在未执行Try的情况下执行Cancel操作。原因是Try请求因网络延迟或故障未到达，但事务管理器认为超时而执行了Cancel。

### 解决方案：
- 记录事务状态表
- Cancel操作需要判断Try是否执行
- 使用幂等性设计

## 6. 你知道 Nacos 配置中心的实现原理吗？（困难）

### 核心原理：

#### 配置存储：
- 数据持久化到MySQL数据库
- 通过namespace、group、dataId三层结构管理配置

#### 配置推送：
1. **长轮询机制**：客户端发起长轮询请求（默认30秒）
2. **MD5校验**：服务端比对配置MD5值
3. **主动推送**：配置变更时，服务端主动通知客户端

#### 配置更新流程：
1. 客户端启动时拉取配置并保存到本地文件
2. 客户端发起长轮询请求监听配置变化
3. 服务端配置更新后，通知监听的客户端
4. 客户端收到通知后拉取最新配置

## 7. 为什么需要服务注册发现？（中等）

### 主要原因：

1. **动态性**：
   - 服务实例数量动态变化（弹性伸缩）
   - IP地址动态分配（容器化部署）

2. **解耦**：
   - 消费者无需关心提供者的具体地址
   - 提供者变更不影响消费者

3. **负载均衡**：
   - 自动发现所有可用实例
   - 实现客户端负载均衡

4. **健康检查**：
   - 自动剔除不健康的服务实例
   - 提高系统可用性

### Spring Cloud链路追踪方案：

   - CNCF项目

4. **Pinpoint**：
   - 韩国开源的APM工具
   - 功能强大，学习成本较高

### 关系：
Spring Cloud依赖于Spring Boot，Spring Boot可以独立使用。

## 11. 你是怎么理解微服务的？（中等）

### 核心理解：

#### 定义：
微服务是一种架构风格，将单一应用程序划分为一组小的服务，每个服务运行在独立进程中，服务间采用轻量级通信机制。

#### 特点：
1. **服务独立**：独立开发、部署、扩展
2. **技术异构**：可使用不同技术栈
3. **数据独立**：每个服务有独立的数据库
4. **去中心化**：去中心化的数据管理和治理
5. **容错性**：单个服务故障不影响整体

#### 优势：
- 灵活扩展
- 技术栈灵活
- 团队独立
- 快速迭代

#### 挑战：
- 运维复杂度增加
- 分布式系统的复杂性
- 数据一致性难以保证
- 测试难度增加

## 12. 单体应用、SOA、微服务架构有什么区别？（中等）

### 单体应用：
- 所有功能打包在一个应用中
- 优点：开发简单、部署简单、测试简单
- 缺点：扩展困难、技术栈单一、部署风险高

### SOA（面向服务架构）：
- 强调服务的重用和互操作性
- 使用ESB（企业服务总线）进行服务集成
- 服务粒度较粗
- 通常使用重量级协议（SOAP、WS-*）

### 微服务：
- SOA的演进和轻量化
- 服务粒度更细
- 去中心化治理
- 使用轻量级协议（REST、gRPC）
- 强调DevOps和持续交付

## 15. 说一下你对于 DDD 的了解？（困难）

### DDD（领域驱动设计）核心概念：

#### 战略设计：
1. **领域（Domain）**：业务范围
2. **子域（Subdomain）**：核心域、支撑域、通用域
3. **限界上下文（Bounded Context）**：明确的边界
4. **上下文映射（Context Mapping）**：上下文间的关系

#### 战术设计：
1. **实体（Entity）**：有唯一标识的对象
2. **值对象（Value Object）**：无唯一标识，不可变
3. **聚合（Aggregate）**：领域对象的聚合根
4. **聚合根（Aggregate Root）**：聚合的入口
5. **领域服务（Domain Service）**：领域逻辑
6. **仓储（Repository）**：持久化抽象
7. **工厂（Factory）**：复杂对象创建

#### 与微服务的关系：
- 限界上下文可对应微服务边界
- DDD帮助合理划分服务
- 避免服务拆分过细或过粗

## 16. 什么是 Seata？（中等）

### 定义：
Seata（Simple Extensible Autonomous Transaction Architecture）是阿里开源的分布式事务解决方案。

### 核心组件：
1. **TC（Transaction Coordinator）**：事务协调器
2. **TM（Transaction Manager）**：事务管理器
3. **RM（Resource Manager）**：资源管理器

### 工作流程：
1. TM向TC注册全局事务
2. RM向TC注册分支事务
3. TM向TC发起全局提交或回滚
4. TC协调各RM进行提交或回滚

---

## 17. Seata 支持哪些模式的分布式事务？（中等）

### 四种模式：

#### 1. AT模式（自动补偿）：
- 基于两阶段提交
- 自动生成反向SQL
- 业务无侵入
- 性能较好

#### 2. TCC模式：
- Try-Confirm-Cancel
- 业务侵入性强
- 性能最好
- 需要自己实现三个方法

#### 3. Saga模式：
- 长事务解决方案
- 正向服务和补偿服务
- 最终一致性
- 适合业务流程长的场景

#### 4. XA模式：
- 基于数据库XA协议
- 强一致性
- 性能较差
- 数据库需要支持XA

---

## 18. 了解 Seata 的实现原理吗？（中等）

### AT模式原理（最常用）：

#### 一阶段：
1. 解析SQL，获取SQL类型、表结构等信息
2. 查询前镜像：执行SQL前查询数据快照
3. 执行业务SQL
4. 查询后镜像：执行SQL后查询数据快照
5. 生成行锁（保证并发安全）
6. 提交本地事务，释放本地锁

#### 二阶段：
- **提交**：异步删除undolog，释放行锁
- **回滚**：通过前镜像和后镜像生成反向SQL，执行补偿

### 关键技术：
- **全局锁**：防止脏写
- **undolog**：存储数据快照
- **行锁**：保证数据一致性

---

## 19. Seata 的事务回滚是怎么实现的？（中等）

### 回滚流程：

1. **查询undolog**：
   - 获取该分支事务的前后镜像数据

2. **数据校验**：
   - 比对当前数据和后镜像
   - 如果一致，说明数据未被修改
   - 如果不一致，说明出现脏写，需要人工处理

3. **生成反向SQL**：
   - 根据前镜像生成回滚SQL
   - 例如：INSERT -> DELETE，UPDATE -> UPDATE（还原）

4. **执行回滚**：
   - 执行反向SQL
   - 删除undolog
   - 释放行锁

### 关键点：
- 必须保证业务SQL和undolog在同一个本地事务中
- 通过行锁防止其他事务修改数据
- 支持数据校验机制

## 20. Spring Cloud 有哪些注册中心？（中等）

### 常用注册中心：

#### 1. Eureka：
- Netflix开源
- AP模型（可用性优先）
- 已停止更新（2.x版本）

#### 2. Consul：
- HashiCorp开源
- CP模型（一致性优先）
- 支持多数据中心

#### 3. Zookeeper：
- Apache开源
- CP模型
- 性能好，但配置复杂

#### 4. Nacos：
- 阿里开源
- 支持AP和CP模式切换
- 同时支持服务发现和配置管理
- 功能最全面，推荐使用

#### 5. Etcd：
- CoreOS开源
- CP模型
- Go语言编写

### 选型建议：
- 新项目推荐：Nacos
- 已有Consul/Zookeeper基础设施：继续使用
- Eureka：不推荐（已停止维护）
