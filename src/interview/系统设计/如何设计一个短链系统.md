# 如何设计一个短链系统

## 什么是短链系统？

短链系统将长URL转换为简短的链接。例如：
- **原始链接**：https://time.geekbang.org/column/intro/100020801
- **短链**：http://gk.link/a/10q2I

## 为什么需要短链？

1. **更简洁，便于传播**：长链接不利于分享和记忆
2. **便于数据追踪**：可以统计访问量、访客数、来源等信息
3. **节省字符**：适用于短信、社交平台等有字数限制的场景
4. **提升用户体验**：短链更美观，更易识别

## 核心原理

短链的工作原理非常简单：**通过短链映射找到长链，然后重定向到长链地址**。

### 重定向状态码选择

短链系统通常使用 **302 临时重定向**，而不是 301 永久重定向。

**原因**：
- **301**：浏览器会缓存长链，后续直接访问缓存，无法进行数据统计分析
- **302**：每次都会请求短链服务器，可以追踪点击情况和用户行为

## 唯一短链生成方案

### 1. 哈希算法

使用哈希算法对长链进行哈希处理，推荐使用 **非加密型哈希算法**（如 MurmurHash），效率更高。

**生成步骤**：
1. 对长链使用 MurmurHash3 生成 32-bit 哈希值
2. 将 10 进制哈希值转换为 62 进制（使用 0-9, a-z, A-Z）
3. 示例：3394174629（10进制） → 3HHBS5（62进制）

### 2. 哈希冲突处理

**检测冲突**：
- 关系型数据库：为短链字段添加唯一索引
- 高并发场景：使用布隆过滤器判断短链是否已存在

**解决冲突**：
- 在长链后拼接随机字符串重新生成哈希
- 存储拼接后的字符串，用于还原原始长链

### 3. 长链与短链的映射关系

**建议**：一个长链可以对应多个短链

**优点**：
- 可以根据不同条件（用户、渠道、时间）生成不同短链
- 便于精细化数据分析和追踪
- 支持营销场景下的渠道效果评估

**实现方式**：
- 哈希时加入条件信息（如用户ID、渠道标识）
- 示例：hash(长链 + 用户ID) → 唯一短链

## 数据存储方案

### 关系型数据库（MySQL/PostgreSQL）

```
表结构示例：
- id: 主键
- short_url: 短链标识（唯一索引）
- long_url: 原始长链
- user_id: 创建用户
- created_at: 创建时间
- expire_at: 过期时间
- click_count: 点击次数
```

### KV 内存数据库（Redis）

**优势**：
- 性能更高，响应速度快
- 天然支持键值对存储
- 适合高并发访问场景

**架构建议**：
- 热点短链存储在 Redis 缓存
- 冷数据存储在关系型数据库
- 为缓存数据设置合理的过期时间

## 系统优化建议

1. **缓存策略**：将活跃短链缓存到 Redis，提升访问速度
2. **过期机制**：设置短链有效期，自动清理过期数据
3. **限流保护**：防止恶意请求和爬虫攻击
4. **数据分析**：记录访问日志，支持统计分析功能
5. **监控告警**：监控系统性能和异常情况

## 扩展功能

- 自定义短链：允许用户指定短链标识
- 访问统计：点击次数、访客数、地理位置、设备类型等
- 有效期控制：设置短链过期时间
- 访问限制：密码保护、访问次数限制
- 二维码生成：为短链自动生成二维码
