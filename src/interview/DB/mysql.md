# MySQL

## 数据库的三范式是什么？

### 第一范式 (1NF) 

- 每一列都是不可再分的基本数据项
- 同一列中不能有多个值
- 不能有重复的列

**举例**:
```
❌ 违反1NF:
学号 | 姓名 | 联系方式
001 | 张三 | 电话:123456,邮箱:abc@qq.com  (联系方式可再分)

✅ 符合1NF:
学号 | 姓名 | 电话    | 邮箱
001 | 张三 | 123456  | abc@qq.com
```

### 第二范式 (2NF) 

**准确描述**: 
- 满足1NF
- 消除**部分依赖**，即非主键列必须**完全依赖**于主键，而不能只依赖于主键的一部分
- 主要针对**联合主键**的情况

**举例**:
```
❌ 违反2NF (有部分依赖):
订单明细表
┌─────────┬─────────┬──────┬──────┬──────┐
│ 订单号  │ 商品号  │ 数量 │ 单价 │ 商品名│
│(主键1)  │(主键2)  │      │      │      │
└─────────┴─────────┴──────┴──────┴──────┘
问题: 
- 数量 完全依赖于 (订单号 + 商品号) ✅
- 单价 只依赖于 商品号 ❌ (部分依赖)
- 商品名 只依赖于 商品号 ❌ (部分依赖)

✅ 符合2NF (拆分表):
订单明细表
┌─────────┬─────────┬──────┐
│ 订单号  │ 商品号  │ 数量 │
└─────────┴─────────┴──────┘

商品表
┌─────────┬──────┬──────┐
│ 商品号  │ 单价 │ 商品名│
└─────────┴──────┴──────┘
```

### 第三范式 (3NF) 

- 满足2NF
- 消除**传递依赖**，即非主键列不能依赖于其他非主键列
- 非主键列必须直接依赖于主键

**举例**:
```
❌ 违反3NF (有传递依赖):
学生表
┌─────┬──────┬──────┬──────────┐
│学号 │ 姓名 │ 院系 │ 院系负责人│
│(主键)│      │      │          │
└─────┴──────┴──────┴──────────┘
问题: 
- 学号 → 院系 ✅
- 学号 → 院系 → 院系负责人 ❌ (传递依赖)

✅ 符合3NF (拆分表):
学生表
┌─────┬──────┬──────┐
│学号 │ 姓名 │ 院系 │
└─────┴──────┴──────┘

院系表
┌──────┬──────────┐
│ 院系 │ 院系负责人│
└──────┴──────────┘
```

### 总结

**第一范式 (1NF)**: 确保每列的原子性，列不可再分。

**第二范式 (2NF)**: 在1NF基础上，消除部分依赖。所有非主键列必须**完全依赖**于整个主键（主要针对联合主键）。

**第三范式 (3NF)**: 在2NF基础上，消除传递依赖。非主键列之间不能存在依赖关系，所有非主键列必须**直接依赖**于主键。

## 一张自增表里面总共有 7 条数据，删除了最后 2 条数据，重启 MySQL 数据库，又插入了一条数据，此时 id 是几？

### MySQL 8.0 之前

#### MyISAM 引擎 ✅ 正确
- **id 是 8**
- MyISAM 会把自增值持久化到数据文件中
- 重启后能记住之前的最大自增值

#### InnoDB 引擎 ✅ 正确（但仅限 MySQL 8.0 之前）
- **id 是 6**（MySQL 5.7 及之前版本）
- InnoDB 只在内存中维护自增值
- 重启后会执行类似 `SELECT MAX(id) FROM table` 来恢复自增值
- 所以会丢失已删除的自增值

### MySQL 8.0 及之后

#### InnoDB 引擎的重大变化
- **id 是 8**（MySQL 8.0+）
- MySQL 8.0 开始，InnoDB 的自增值会**持久化到 redo log** 中
- 重启后不会丢失自增值
- 这是一个重要的改进

### 结论

**MySQL 5.7 及之前版本:**
- MyISAM 引擎：id 是 8（自增值持久化到表文件）
- InnoDB 引擎：id 是 6（自增值只存内存，重启后通过 MAX(id)+1 恢复）

**MySQL 8.0 及之后版本:**
- MyISAM 引擎：id 是 8（同上）
- InnoDB 引擎：id 是 8（自增值持久化到 redo log，重启后不丢失）

**原因:**
- MySQL 8.0 之前，InnoDB 只在内存中维护自增计数器，重启后会扫描表找最大值
- MySQL 8.0 开始，InnoDB 将自增值持久化，解决了这个问题

## MyISAM 的数据文件

MyISAM 每张表对应 **3个文件**，以表名为前缀：

| 文件 | 全称 | 存储内容 |
|------|------|----------|
| `表名.frm` | Format | 表结构定义（字段、类型、索引定义等） |
| `表名.MYD` | MY Data | 实际的行数据 |
| `表名.MYI` | MY Index | 所有索引数据（含自增计数器） |

---

### 各文件格式详解

**`.frm`（表结构文件）**
- 二进制格式，MySQL 通用，所有引擎都有
- 存储列定义、字符集、默认值、AUTO_INCREMENT 当前值等元数据

**`.MYD`（数据文件）**
- 支持三种行格式：
  - `Fixed`（定长）：每行占用相同字节数，查找快，但 VARCHAR 会补空格浪费空间
  - `Dynamic`（动态）：变长行，节省空间，但容易产生碎片
  - `Compressed`：只读压缩格式，用 `myisampack` 工具生成
- 行之间可能有删除留下的"空洞"，需要 `OPTIMIZE TABLE` 整理

**`.MYI`（索引文件）**
- B-Tree 结构存储所有索引（主键 + 二级索引）
- **自增计数器就持久化在这里**，所以重启后不会丢失
- 索引叶子节点存的是**行的物理偏移量**（指向 .MYD 文件中的位置）

---

### 与 InnoDB 的对比

```
MyISAM：  表名.frm  +  表名.MYD  +  表名.MYI   （3个文件，索引与数据分离）
InnoDB：  表名.frm  +  表名.ibd                  （2个文件，索引与数据在一起）
```

InnoDB 的自增值在 MySQL 8.0 之前只存在内存中，重启会重新扫描最大值，这就是为什么 InnoDB 在 8.0 之前重启后自增 id 可能"复用"的根本原因。
:::

## 说一下 ACID 是什么？

* Atomicity（原子性）：一个事务（transaction）中的所有操作，或者全部完成，或者全部不完成，不会结束在中间某个环节。事务在执行过程中发生错误，会被恢复（Rollback）到事务开始前的状态，就像这个事务从来没有执行过一样。即，事务不可分割、不可约简。
* Consistency（一致性）：在事务开始之前和事务结束以后，数据库的完整性没有被破坏。这表示写入的资料必须完全符合所有的预设约束、触发器、级联回滚等。
* Isolation（隔离性）：数据库允许多个并发事务同时对其数据进行读写和修改的能力，隔离性可以防止多个事务并发执行时由于交叉执行而导致数据的不一致。事务隔离分为不同级别，包括读未提交（Read uncommitted）、读提交（read committed）、可重复读（repeatable read）和串行化（Serializable）。
* Durability（持久性）：事务处理结束后，对数据的修改就是永久的，即便系统故障也不会丢失。

## char 和 varchar 的区别是什么？

* **char(n)**：固定长度类型，比如 char(10)，当你输入 "abc" 三个字符时，实际占用的空间仍然是 10 个字节，剩余 7 个字节会用**空格填充**。char 的优点：存取效率高；缺点：固定占用空间，可能造成浪费；适用场景：存储长度固定的内容，比如密码的 md5 值（始终32位），使用 char 非常合适。
* **varchar(n)**：可变长度类型，实际占用空间为**内容本身的字节数**，再加上 **1到2个字节**的长度前缀（内容不超过255字节时用1字节，超过则用2字节）。

所以，从空间上考虑 varchar 比较合适；从效率上考虑 char 比较合适，二者使用需要根据场景权衡。

## float 和 double 的区别是什么？

* float 最多可以存储 8 位的十进制数，并在内存中占 4 字节。
* double 最可可以存储 16 位的十进制数，并在内存中占 8 字节。

## MySQL 的内连接、左连接、右连接有什么区别？

内连接关键字：inner join；左连接：left join；右连接：right join。

内连接是把匹配的关联数据显示出来；左连接是左边的表全部显示出来，右边的表显示出符合条件的数据；右连接正好相反。

## MySQL 索引是怎么实现的？

索引是满足某种特定查找算法的数据结构，而这些数据结构会以某种方式指向数据，从而实现高效查找数据。

具体来说MySQL 中的索引，不同的数据引擎实现有所不同，但目前主流的数据库引擎的索引都是 B+ 树实现的，B+ 树的搜索效率，可以到达二分法的性能，找到数据区域之后就找到了完整的数据结构了，所有索引的性能也是更好的。

##  说一下数据库的事务隔离？

MySQL 的事务隔离是在 MySQL. ini 配置文件里添加的，在文件的最后添加：transaction-isolation = REPEATABLE-READ

可用的配置值：READ-UNCOMMITTED、READ-COMMITTED、REPEATABLE-READ、SERIALIZABLE。

* READ-UNCOMMITTED：未提交读，最低隔离级别、事务未提交前，就可被其他事务读取（会出现幻读、脏读、不可重复读）。
* READ-COMMITTED：提交读，一个事务提交后才能被其他事务读取到（会造成幻读、不可重复读）。
* REPEATABLE-READ：可重复读，MySQL 默认级别，保证在同一事务内多次读取同一行数据结果一致（理论上会造成幻读）。InnoDB 通过 MVCC 和间隙锁在此级别下已基本避免幻读。
* SERIALIZABLE：序列化，最高隔离级别，事务串行执行，能完全防止脏读、不可重复读和幻读，但性能代价最高。

**脏读** ：一个事务读取到了另一个事务尚未提交的数据。若该事务最终回滚，读到的数据就是无效的"脏数据"。

**不可重复读**：同一事务内，对同一行数据进行两次查询，由于其他事务在此期间对该行执行了 UPDATE 或 DELETE 并提交，导致两次读取结果不一致。

**幻读**：同一事务内，执行两次相同的范围查询，由于其他事务在此期间执行了 INSERT 或 DELETE 并提交，导致两次返回的行数不同，如同出现了"幻觉"。

## 说一下 MySQL 常用的引擎？

* **InnoDB 引擎**：mysql 5.1 后默认的数据库引擎，提供了对数据库 acid 事务的支持，并且还提供了行级锁和外键的约束，它的设计的目标就是处理大数据容量的数据库系统。MySQL 运行的时候，InnoDB 会在内存中建立缓冲池，用于缓冲数据和索引。但是该引擎是不支持全文搜索，同时启动也比较的慢，它是不会保存表的行数的，所以当进行 `select count(\*) from table` 指令的时候，需要进行扫描全表。由于锁的粒度小，写操作是不会锁定全表的,所以在并发度较高的场景下使用会提升效率的。
* **MyIASM 引擎**：不提供事务的支持，也不支持行级锁和外键。因此当执行插入和更新语句时，即执行写操作的时候需要锁定这个表，所以会导致效率会降低。不过和 InnoDB 不同的是，MyIASM 引擎是保存了表的行数，于是当进行 select count(\*) from table 语句时，可以直接的读取已经保存的值而不需要进行扫描全表。所以，如果表的读操作远远多于写操作时，并且不需要事务的支持的，可以将 MyIASM 作为数据库引擎的首选。

## 说一下 MySQL 的行锁和表锁？

MyISAM 只支持表锁，InnoDB 支持表锁和行锁，默认为行锁。

* 表级锁：开销小，加锁快，不会出现死锁。锁定粒度大，发生锁冲突的概率最高，并发量最低。
* 行级锁：开销大，加锁慢，会出现死锁。锁力度小，发生锁冲突的概率小，并发度最高。

数据库的乐观锁需要自己实现，在表里面添加一个version 字段，每次修改成功值加 1，这样每次修改的时候先对比一下，自己拥有的 version 和数据库现在的 version 是否一致，如果不一致就不修改，这样就实现了乐观锁。

## 说一下乐观锁和悲观锁？

* 乐观锁：每次去拿数据的时候都认为别人不会修改，所以不会上锁，但是在提交更新的时候会判断一下在此期间别人有没有去更新这个数据。
* 悲观锁：每次去拿数据的时候都认为别人会修改，所以每次在拿数据的时候都会上锁，这样别人想拿这个数据就会阻止，直到这个锁被释放。

## 索引常见数据结构

1. 顺序查找: 最基本的查询算法-复杂度 O（n），大数据量此算法效率糟糕。
2. 二叉树查找（binary tree search）: O(log n)，数据本身的组织结构不可能完全满足各种数据结构。
3. hash索引 无法满足范围查找。哈希索引基于哈希表实现，只有精确匹配索引所有列的查询才有效。
4. 二叉树、红黑树 [复杂度O(h)]导致树高度非常高(平衡二叉树一个节点只能有左子树和右子树),逻辑上很近的节点（父子）物理上可能很远，无法利用局部性，IO次数多查找慢,效率低。todo 逻辑上相邻节点没法直接通过顺序指针关联，可能需要迭代回到上层节点重复向下遍历找到对应节点，效率低
5. B-Tree
   * B-TREE 每个节点都是一个二元数组: [key, data]，所有节点都可以存储数据。key为索引key,data为除key之外的数据。
   * 检索原理：首先从根节点进行二分查找，如果找到则返回对应节点的data，否则对相应区间的指针指向的节点递归进行查找，直到找到节点或未找到节点返回null指针。
   * 缺点：1.插入删除新的数据记录会破坏B-Tree的性质，因此在插入删除时，需要对树进行一个分裂、合并、转移等操作以保持B-Tree性质。造成IO操作频繁。2.区间查找可能需要返回上层节点重复遍历，IO操作繁琐。
6. B+Tree: B-Tree的变种
   * 与B-Tree相比，B+Tree有以下不同点：非叶子节点不存储data，只存储索引key；只有叶子节点才存储data
   * Mysql中B+Tree：在经典B+Tree的基础上进行了优化，增加了顺序访问指针。在B+Tree的每个叶子节点增加一个指向相邻叶子节点的指针，就形成了带有顺序访问指针的B+Tree。相比B-Tree来说，进行范围查找时只需要查找两个节点，进行遍历即可。而B-Tree需要获取所有节点，相比之下B+Tree效率更高，这样就提高了区间访问性能。

## 为什么索引结构默认使用B+Tree，而不是hash，二叉树，红黑树？

**Hash**：只支持精确匹配，不支持范围查询（>、<、BETWEEN）和排序，实际业务中范围查询场景很多，所以不适合作为默认索引结构。
**二叉树**：不能保证平衡，数据有序插入时会退化为链表，查询复杂度从 O(log n) 退化到 O(n)；且每个节点只有两个子节点，树的高度大，磁盘 IO 次数多。
**红黑树**：虽然能自平衡，但本质仍是二叉树，节点的分叉数最多为2，数据量大时树的高度依然很高，导致磁盘 IO 次数多，性能差。
**B+Tree**：每个节点可以存储多个键值，分叉数远大于2，相同数据量下树的高度远低于二叉树（通常只有3～4层），极大减少了磁盘 IO 次数，同时天然支持范围查询，因此成为默认索引结构。

## B+Tree 3～4 层能存多少数据？

先搞清楚两个关键参数：

**1. 非叶子节点能存多少指针？**

InnoDB 默认页大小是 **16KB**，非叶子节点存的是键值 + 指针：
- 主键用 bigint = 8 字节
- 指针 = 6 字节
- 每个键值对 = **14 字节**

```
每个非叶子节点的指针数 = 16KB / 14B = 16384 / 14 ≈ 1170 个指针
```

:::tip

**非叶子节点的结构可以理解为：**

```
[ key | ptr ] [ key | ptr ] [ key | ptr ] ... [ key | ptr ]
  8B    6B      8B    6B      8B    6B            8B    6B
```

每一个二元组 `(key, pointer)` = 8 + 6 = **14 字节**

然后用页的总空间除以每个二元组的大小：

```
16 × 1024 B ÷ 14 B ≈ 1170 个
```

---

不过严格来说，B+Tree 非叶子节点的结构比纯二元组数组稍微复杂一点点：

```
ptr0 | key1 | ptr1 | key2 | ptr2 | key3 | ptr3 ...
```

指针比键值**多一个**（n 个键值对应 n+1 个指针），但因为数量级差异不大，计算时通常忽略这个细节，直接用 14 字节估算，结果影响很小。
:::

**2. 叶子节点能存多少行数据？**

假设每行数据 **1KB**：

```
每个叶子节点存储行数 = 16KB / 1KB = 16 行
```

---

### 各层级的数据量

| 树的高度 | 计算方式 | 大约能存 |
|---|---|---|
| 2层 | 1170 × 16 | **约 1.9 万行** |
| 3层 | 1170 × 1170 × 16 | **约 2190 万行** |
| 4层 | 1170 × 1170 × 1170 × 16 | **约 256 亿行** |

---

### 结论

> **3层 B+Tree 就能支撑约 2000 万行数据，而只需要 3 次磁盘 IO。**

这也是为什么 MySQL 单表建议控制在 **2000 万行**以内，超过之后树的高度增加到4层，IO 次数增加，查询性能会明显下降。

## 为什么官方建议使用自增长主键作为索引?

“使用自增主键作为索引，对于 InnoDB 存储引擎的性能至关重要。这主要得益于它和 B+树索引（尤其是聚簇索引）的协同工作

* 顺序写入，减少页分裂：自增主键保证新插入的记录总是追加到主键索引的末尾。这种顺序写入模式能最大化利用数据页的空间，推迟页分裂的发生。而如果使用随机主键，插入操作可能随机打乱索引，频繁触发页分裂和数据移动，严重影响性能。
* 减少磁盘 I/O：顺序插入减少了随机磁盘 I/O，因为相关数据在物理存储上是连续的。这能提高缓存命中率，让数据库更高效地从磁盘读取数据。
* 提升查询效率：自增主键的连续性，使得基于主键的范围查询（WHERE id BETWEEN X AND Y）能快速访问相邻的数据页。此外，作为辅助索引的“书签”，小巧的自增主键能减少辅助索引的体积，进一步提升查询性能。”

## MySQL 中 InnoDB 引擎的行锁是通过加在什么上完成（或称实现）

InnoDB 行锁是通过给索引上的索引项加锁来实现的，这一点 MySQL 与 Oracle 不同，后者是通过在数据块中对相应数据行加锁来实现的。InnoDB 的行锁是通过给索引上的索引项加锁来实现的。这一实现意味着，只有通过索引条件检索数据，InnoDB 才能精准地锁定少数几行。如果 WHERE 条件中没有使用索引，InnoDB 将进行全表扫描，并为扫描到的每一行都加上行锁，其结果是锁住了整张表的所有数据行，从而严重影响并发性能。因此，在事务性操作中务必确保使用索引，才能真正发挥 InnoDB 行锁的高并发优势。

## HAVNG 子句 和 WHERE 的异同点?

4. where 后面不能使用聚集函数，having 是专门使用聚集函数的

## truncate delete drop 的区别。

drop(DDL 语句)：是不可逆操作，会将表所占用空间全部释放掉；

truncate(DDL 语句)：只针对于删除表的操作，在删除过程中不会激活与表有关的删 除触发器并且不会把删除记录放在日志中；当表被 truncate 后，这个表和索引会恢 复到初始大小；

delete(DML 语句)：可以删除表也可以删除行，但是删除记录会被计入日志保存， 而且表空间大小不会恢复到原来；

执行速度：drop>truncate>delete。

## 如何控制 HEAP（Memory）表的最大尺寸？

MySQL 中 **HEAP 表指的是 MEMORY 引擎表**

#### 永久生效（my.cnf / my.ini）

```ini
[mysqld]
max_heap_table_size = 256M
tmp_table_size = 256M
```

## MySQL 中货币字段的最佳类型选择

### 推荐类型：DECIMAL

在 MySQL 中存储货币数据时，应使用 **DECIMAL** 类型（或其同义词 NUMERIC）。这是一种固定精度和小数位数的数值类型，能够精确存储货币金额，避免浮点数运算带来的精度误差。

### 语法格式
```sql
DECIMAL(p, s)
-- 或
NUMERIC(p, s)
```

### 参数说明

**p（精度，Precision）**
- 表示可存储的十进制数字总位数（包括小数点左右两侧）
- 取值范围：1 ~ 38
- 默认值：18
- 示例：`DECIMAL(10, 2)` 中的 10 表示总共可存储 10 位数字

**s（小数位数，Scale）**
- 表示小数点右侧可存储的数字位数
- 取值范围：0 ~ p
- 默认值：0
- 必须先指定精度（p）才能指定小数位数
- 示例：`DECIMAL(10, 2)` 中的 2 表示保留 2 位小数

### 核心特性

1. **精确存储**：DECIMAL 存储的是精确的数值表示，不会像 FLOAT 或 DOUBLE 那样产生近似值
2. **功能等价**：NUMERIC 与 DECIMAL 在功能上完全等效，可互换使用
3. **最大精度**：最多支持 38 位数字，有效值范围为 -10³⁸ + 1 到 10³⁸ - 1
4. **存储优化**：实际存储大小根据指定的精度动态变化

### 货币字段使用建议
```sql
-- 推荐：适用于大多数货币场景
amount DECIMAL(19, 4)  -- 支持千万亿级金额，保留 4 位小数

-- 常用：一般业务场景
price DECIMAL(10, 2)   -- 最大支持 99,999,999.99

-- 高精度：金融交易场景
balance DECIMAL(20, 6) -- 支持更高精度计算
```

### 为什么不使用 FLOAT 或 DOUBLE？

浮点类型会导致精度丢失，例如：
- 0.1 + 0.2 可能不等于 0.3
- 累计计算会产生误差累积
- 货币计算的结果可能出现分的零头误差

**结论**：货币数据必须使用 DECIMAL 类型以确保精确计算和存储。

## InnoDB存储引擎的锁的算法有三种

这是MySQL InnoDB存储引擎中用于实现并发控制的三种行锁算法，主要用于**防止幻读**和保证事务隔离性。

### 1. Record Lock (记录锁)
**最简单的锁类型**，直接锁定索引记录本身。

**举例**：
```sql
SELECT * FROM users WHERE id = 10 FOR UPDATE;
```
只锁定 id=10 这一行，其他行不受影响。

---

### 2. Gap Lock (间隙锁)
锁定索引记录之间的"间隙"，**不包括记录本身**。

**作用**：防止其他事务在这个间隙中插入数据（防止幻读）。

**举例**：
假设表中有 id = 5, 10, 15 三条记录
```sql
SELECT * FROM users WHERE id > 5 AND id < 15 FOR UPDATE;
```
会锁定 (5, 15) 这个区间，阻止插入 id=6,7,8...14 的记录，但 id=5 和 id=15 本身不被锁定。

---

### 3. Next-Key Lock (临键锁)
**Record Lock + Gap Lock 的组合**，锁定一个范围并包含记录本身。

**这是InnoDB的默认行锁算法**（在RR隔离级别下）。

**举例**：

假设索引值为 5, 10, 15

```sql
SELECT * FROM users WHERE id >= 10 FOR UPDATE;
```

实际锁定的是：

| 锁定范围 | 锁类型 | 说明 |
|---|---|---|
| `id = 10` | Record Lock | 记录本身 |
| `(10, 15]` | Next-Key Lock | 区间 + 记录 15 |
| `(15, +∞)` | Next-Key Lock | 15 之后到正无穷 |

---

### 实际意义

| 锁类型 | 锁定内容 | 主要用途 |
|--------|----------|----------|
| Record Lock | 单行记录 | 防止其他事务修改/删除这行 |
| Gap Lock | 记录间的间隙 | 防止幻读（插入新数据） |
| Next-Key Lock | 记录+间隙 | RR隔离级别下的默认锁，同时防止修改和幻读 |

**核心要点**：这套机制让InnoDB在可重复读(RR)隔离级别下就能防止幻读，而不需要使用串行化(Serializable)级别，在并发性能和数据一致性之间取得平衡。

## MySQL 大表优化策略

当单表记录数过大时，CRUD 性能会明显下降。优化手段可以从**查询约束、架构拆分、数据分片**三个层面入手。

**限定数据范围** 是最简单有效的方式——强制要求所有查询必须携带范围条件，例如只允许查询最近一个月的订单，避免全表扫描。

**读写分离** 是经典的横向扩展方案：主库专注写操作，从库承担读压力，适合读多写少的业务场景。

**垂直分区** 是按列拆分，将一张宽表拆成多张窄表，甚至拆到不同的库中。适合表中有明显的"冷热字段"时，比如用户登录信息和用户详细资料分开存储。

**水平分区** 是按行拆分，表结构不变，将数据分散到多张表或多个库中，适合数据量极大（单表超过 200 万行）的场景。

## 解释一下什么是池化设计思想。什么是数据库连接池?为什么需要数 据库连接池？

### 池化设计思想

**核心概念**：预先创建并维护一定数量的资源对象，需要时直接从池中获取，用完后归还，避免频繁创建和销毁资源的开销。

**生活化类比**：就像食堂打饭，大妈提前盛好几份饭放着，你来了直接拿饭加菜就行，不用现场又盛饭又打菜，效率自然高。

#### 常见实现
- Java线程池（ThreadPoolExecutor）
- JDBC连接池（HikariCP、Druid）
- Redis连接池（JedisPool）
- HTTP连接池

#### 池化设计的关键参数
- **初始值（initialSize）**：池启动时预创建的资源数量
- **最小值（minIdle）**：池中保持的最小空闲资源数
- **最大值（maxTotal）**：池中允许的最大资源数
- **活跃值（active）**：当前正在使用的资源数

---

### 数据库连接池

**本质**：维护数据库连接的缓存容器，连接可以被重复使用。

**底层原理**：数据库连接本质是一个Socket连接，服务端需要为每个连接维护缓存、用户权限、会话状态等信息，创建和销毁的成本较高。

---

### 为什么需要数据库连接池？

#### 1. **性能提升**
- 避免频繁创建/销毁连接的开销（TCP三次握手、权限验证等）
- 连接复用，减少响应时间

#### 2. **资源管理**
- 限制最大连接数，防止数据库过载
- 统一管理连接的生命周期

#### 3. **提高并发能力**
- 多个请求可以共享有限的连接资源
- 对于高并发场景，连接池能有效缓冲请求压力

#### 4. **连接保活与健康检查**
- 自动检测失效连接并重建
- 维护连接的有效性（如心跳检测）

---

### 工作流程示意

```
请求到达 → 从池中获取连接 → 执行SQL → 归还连接到池
                ↓
           如果池为空且未达上限 → 创建新连接
                ↓
           如果已达上限 → 等待或拒绝
```

**总结**：池化设计是典型的"空间换时间"策略，通过预分配资源和资源复用，在高并发场景下显著提升系统性能和稳定性。

---

##  分库分表之后,id主键如何处理？

因为要是分成多个表之后，每个表都是从1开始累加，这样是不对的，我们需要一个全局唯一的id来 支持。 生成全局id有下面这几种方式:

* UUID：不适合作为主键，因为太长了，并且无序不可读，查询效率低。比较适合用于生成唯一的名 字的标示比如文件的名字。
* 数据库自增id:两台数据库分别设置不同步长，生成不重复ID的策略来实现高可用。这种方式生成的 id有序，但是需要独立部署数据库实例，成本高，还会有性能瓶颈、
* 利用redis生成id:性能比较好，灵活方便，不依赖于数据库。♦但 再 入了新的组件造成系统更加 复杂，可用性降低，编码更加复杂，增加了系统成本。
* Twitter的snowflake算 法 ：Github 地址：<https://github.com/twitter-archive/snowflake>[ ](https://github.com/twitter-archive/snowflake)
* 美团的Leaf分布式ID生成系统：Leaf是美团开源的分布式ID生成器，能保证全局唯一性、趋势递 增、单调递增、信息安全，里 面 也 提 到 了 几 种 分 案 的 对 比 ，但也需要依赖关系数据库、 Zookeeper等中间件。感觉还不错。美 团 技 术 团 队 一篇 文 章 ：https: / / tech.meituan.com/2017/04/ 21/ mt-leaf.html 。
