## 一、计算机网络基础

### OSI 七层模型是什么？每一层的作用是什么？

OSI（Open System Interconnection）七层参考模型由国际标准化组织（ISO）提出，从高到低依次为：

| 层级  | 名称       | 主要功能                                           |
| ----- | ---------- | -------------------------------------------------- |
| 第7层 | 应用层     | 为应用程序提供网络服务接口（如浏览器、邮件客户端） |
| 第6层 | 表示层     | 数据格式转换、加密/解密、压缩                      |
| 第5层 | 会话层     | 管理（建立、维护、重连）应用程序之间的会话         |
| 第4层 | 传输层     | 端到端通信、可靠传输（TCP/UDP）                    |
| 第3层 | 网络层     | 路由与寻址（IP协议）                               |
| 第2层 | 数据链路层 | 帧传输、MAC寻址、错误检测                          |
| 第1层 | 物理层     | 比特流传输、物理介质                               |

![](https://oss.javaguide.cn/github/javaguide/osi%E4%B8%83%E5%B1%82%E6%A8%A1%E5%9E%8B2.png)

> OSI 概念清晰、理论完整，但较复杂且不实用，部分功能在多层中重复出现。

### ⭐️ TCP/IP 四层模型是什么？

TCP/IP 四层模型是目前广泛采用的实际网络模型，可看作 OSI 七层模型的精简版：

| 层级       | 对应 OSI 层              | 代表协议             |
| ---------- | ------------------------ | -------------------- |
| 应用层     | 应用层 + 表示层 + 会话层 | HTTP、FTP、DNS、SMTP |
| 传输层     | 传输层                   | TCP、UDP             |
| 网络层     | 网络层                   | IP、ARP、ICMP        |
| 网络接口层 | 数据链路层 + 物理层      | Ethernet、Wi-Fi      |

### 为什么网络要分层？

网络分层的三大原因：

1. **各层相互独立**：每层只需关注自己的功能，无需了解其他层的实现细节（类似接口调用）。
2. **灵活性与可替换性**：每一层可独立修改或替换，不影响整体架构（高内聚、低耦合）。
3. **大问题化小**：将复杂的网络问题分解为多个边界清晰的小问题，易于设计、实现和标准化。

> 经典名言：*"计算机科学领域的任何问题都可以通过增加一个间接的中间层来解决。"*

### 常见协议汇总

**应用层常见协议：**

- HTTP（Hypertext Transfer Protocol，超文本传输协议）：基于 TCP 协议，是一种用于传输超文本和多媒体内容的协议，主要是为 Web 浏览器与 Web 服务器之间的通信而设计的。当我们使用浏览器浏览网页的时候，我们网页就是通过 HTTP 请求进行加载的。
- SMTP（Simple Mail Transfer Protocol，简单邮件发送协议）：基于 TCP 协议，是一种用于发送电子邮件的协议。注意 ⚠️：SMTP 协议只负责邮件的发送，而不是接收。要从邮件服务器接收邮件，需要使用 POP3 或 IMAP 协议。
- POP3/IMAP（邮件接收协议）：基于 TCP 协议，两者都是负责邮件接收的协议。IMAP 协议是比 POP3 更新的协议，它在功能和性能上都更加强大。IMAP 支持邮件搜索、标记、分类、归档等高级功能，而且可以在多个设备之间同步邮件状态。几乎所有现代电子邮件客户端和服务器都支持 IMAP。
- FTP（File Transfer Protocol，文件传输协议） : 基于 TCP 协议，是一种用于在计算机之间传输文件的协议，可以屏蔽操作系统和文件存储方式。注意 ⚠️：FTP 是一种不安全的协议，因为它在传输过程中不会对数据进行加密。建议在传输敏感数据时使用更安全的协议，如 SFTP。
- Telnet（远程登陆协议）：基于 TCP 协议，用于通过一个终端登陆到其他服务器。Telnet 协议的最大缺点之一是所有数据（包括用户名和密码）均以明文形式发送，这有潜在的安全风险。这就是为什么如今很少使用 Telnet，而是使用一种称为 SSH 的非常安全的网络传输协议的主要原因。
- SSH（Secure Shell Protocol，安全的网络传输协议）：基于 TCP 协议，通过加密和认证机制实现安全的访问和文件传输等业务
- RTP（Real-time Transport Protocol，实时传输协议）：通常基于 UDP 协议，但也支持 TCP 协议。它提供了端到端的实时传输数据的功能，但不包含资源预留存、不保证实时传输质量，这些功能由 WebRTC 实现。
- DNS（Domain Name System，域名管理系统）: 通常基于 UDP 协议（端口 53），用于解决域名和 IP 地址的映射问题。当响应数据过大或进行区域传送时会改用 TCP。


**传输层常见协议：**
- **TCP**：面向连接、可靠传输
- **UDP**：无连接、尽最大努力传输，简单高效

**网络层常见协议：**
- IP（Internet Protocol，网际协议）：TCP/IP 协议中最重要的协议之一，属于网络层的协议，主要作用是定义数据包的格式、对数据包进行路由和寻址，以便它们可以跨网络传播并到达正确的目的地。目前 IP 协议主要分为两种，一种是过去的 IPv4，另一种是较新的 IPv6，目前这两种协议都在使用，但后者已经被提议来取代前者。
- ARP（Address Resolution Protocol，地址解析协议）：ARP 协议解决的是网络层地址和链路层地址之间的转换问题。因为一个 IP 数据报在物理上传输的过程中，总是需要知道下一跳（物理上的下一个目的地）该去往何处，但 IP 地址属于逻辑地址，而 MAC 地址才是物理地址，ARP 协议解决了 IP 地址转 MAC 地址的一些问题。
- ICMP（Internet Control Message Protocol，互联网控制报文协议）：一种用于传输网络状态和错误消息的协议，常用于网络诊断和故障排除。例如，Ping 工具就使用了 ICMP 协议来测试网络连通性。
- NAT（Network Address Translation，网络地址转换协议）：NAT 协议的应用场景如同它的名称——网络地址转换，应用于内部网到外部网的地址转换过程中。具体地说，在一个小的子网（局域网，LAN）内，各主机使用的是同一个 LAN 下的 IP 地址，但在该 LAN 以外，在广域网（WAN）中，需要一个统一的 IP 地址来标识该 LAN 在整个 Internet 上的位置。
- OSPF（Open Shortest Path First，开放式最短路径优先）：一种内部网关协议（Interior Gateway Protocol，IGP），也是广泛使用的一种动态路由协议，基于链路状态算法，考虑了链路的带宽、延迟等因素来选择最佳路径。
- RIP（Routing Information Protocol，路由信息协议）：一种内部网关协议（Interior Gateway Protocol，IGP），也是一种动态路由协议，基于距离向量算法，使用固定的跳数作为度量标准，选择跳数最少的路径作为最佳路径。
- BGP（Border Gateway Protocol，边界网关协议）：一种用来在路由选择域之间交换网络层可达性信息（Network Layer Reachability Information，NLRI）的路由选择协议，具有高度的灵活性和可扩展性。

## 二、HTTP

### ⭐️ 从输入 URL 到页面展示发生了什么？

整体流程如下：

1. 浏览器输入 URL
2. **DNS 解析**：获取域名对应的 IP 地址
3. **TCP 三次握手**：与目标服务器建立连接
4. **发送 HTTP 请求**：请求页面内容
5. **服务器响应**：返回 HTTP 响应报文
6. **浏览器渲染**：解析 HTML，加载 CSS/JS/图片等资源（可能触发多次 HTTP 请求）
7. **关闭连接**：对应 TCP 四次挥手,通信结束后关闭 TCP 连接

### ⭐️ HTTP 和 HTTPS 有什么区别？

| 对比项   | HTTP                 | HTTPS                       |
| -------- | -------------------- | --------------------------- |
| 端口     | 80                   | 443                         |
| URL 前缀 | `http://`            | `https://`                  |
| 传输方式 | 明文                 | SSL/TLS 加密                |
| 安全性   | 低（可被窃听、篡改） | 高（对称加密 + 非对称加密） |
| 性能     | 较快                 | 略慢（加密消耗资源）        |
| SEO      | 一般                 | 搜索引擎优先收录            |

### HTTP/1.0 和 HTTP/1.1 的区别？

| 对比项   | HTTP/1.0                       | HTTP/1.1                             |
| -------- | ------------------------------ | ------------------------------------ |
| 连接方式 | 短连接                         | 支持长连接（keep-alive）             |
| 状态码   | 较少                           | 新增 24 种错误状态码                 |
| 缓存机制 | `If-Modified-Since`、`Expires` | 新增 `ETag`、`If-None-Match` 等      |
| 带宽利用 | 不支持断点续传                 | 引入 `Range` 头，支持断点续传（206） |
| 虚拟主机 | 不支持                         | 引入 `Host` 头，支持虚拟主机         |

---

### ⭐️ HTTP/1.1 和 HTTP/2.0 的区别？

| 对比项     | HTTP/1.1                  | HTTP/2.0                    |
| ---------- | ------------------------- | --------------------------- |
| 传输格式   | 文本格式                  | 二进制帧（更紧凑高效）      |
| 多路复用   | 不支持（需多个 TCP 连接） | 支持（单连接并行多请求）    |
| 头部压缩   | 不支持 Header 压缩        | HPACK 算法压缩 Header       |
| 服务器推送 | 不支持                    | 支持主动推送资源            |
| 队头阻塞   | 应用层存在                | 解决应用层，但 TCP 层仍存在 |

---

### HTTP/2.0 和 HTTP/3.0 的区别？

| 对比项   | HTTP/2.0                          | HTTP/3.0                  |
| -------- | --------------------------------- | ------------------------- |
| 传输协议 | TCP                               | QUIC（基于 UDP）          |
| 连接建立 | 需 TCP 三次握手 + TLS（约 3 RTT） | 0-RTT 或 1-RTT            |
| 头部压缩 | HPACK                             | QPACK（更高效）           |
| 队头阻塞 | TCP 层仍存在                      | 基本解决（流之间独立）    |
| 连接迁移 | 不支持（依赖四元组）              | 支持（64 位 ID 标识连接） |
| 安全性   | TLS 加密应用层数据                | QUIC 对整个数据包加密     |

---

### HTTP/1.1 和 HTTP/2.0 的队头阻塞有什么不同？

| 对比项   | HTTP/1.1                   | HTTP/2.0                                 |
| -------- | -------------------------- | ---------------------------------------- |
| 阻塞层级 | 应用层                     | 传输层（TCP）                            |
| 根本原因 | 无多路复用，请求必须按顺序 | TCP 要求数据包顺序交付，丢包阻塞整个连接 |
| 影响范围 | 单请求阻塞后续请求         | 单 TCP 包丢失影响所有 HTTP/2 流          |
| 缓解方法 | 开启多个 TCP 连接          | 减少丢包或使用 QUIC（HTTP/3）            |

### ⭐️ HTTP 是无状态协议，如何保存用户状态？

**方案一：Session + Cookie（主流）**

1. 用户登录，服务器创建 Session 对象并分配 `SessionID`
2. 通过 `Set-Cookie` 将 SessionID 发送给浏览器
3. 浏览器后续每次请求自动携带 Cookie
4. 服务器通过 SessionID 找到对应 Session

Session 存储方式：服务器内存 / 数据库 / **Redis（推荐）**

**方案二：URL 重写**（Cookie 被禁用时备用）

将 SessionID 附加到 URL 参数中，安全性低，不推荐。

**方案三：Token（JWT）**

1. 登录后服务器返回签名的 JWT
2. 客户端存储在 `localStorage` 中
3. 每次请求在 Header 中携带 JWT
4. 服务器验证 JWT 有效性

> **总结**：Cookie + Session 是传统方案；Token/JWT 在现代前后端分离项目中更流行。

### ⭐️ 13. GET 和 POST 的区别

| 对比项   | GET                      | POST                           |
| -------- | ------------------------ | ------------------------------ |
| 语义     | 获取/查询资源            | 创建/修改资源                  |
| 幂等性   | 幂等（多次执行结果相同） | 非幂等                         |
| 参数位置 | URL 查询字符串           | 请求体（Body）                 |
| 缓存     | 可被缓存                 | 不适合缓存                     |
| 安全性   | 参数暴露在 URL，更易泄露 | 相对安全（但 HTTP 下都不安全） |

> **重点**：核心区别在于**语义**，GET 查询，POST 提交。

## 三、WebSocket

### 什么是 WebSocket？

WebSocket 是一种基于 TCP 的**全双工通信协议**，客户端和服务器可以同时互相发送和接收数据。

- 2008 年诞生，2011 年成为国际标准
- 弥补 HTTP 在持久通信上的不足
- 一次握手即可建立持久连接

![](https://oss.javaguide.cn/github/javaguide/system-design/web-real-time-message-push/1460000042192394.png)

**常见应用场景**：视频弹幕、实时消息推送、在线游戏对战、多人协作编辑、社交聊天

---

### ⭐️ WebSocket 和 HTTP 有什么区别？

| 对比项     | HTTP                   | WebSocket          |
| ---------- | ---------------------- | ------------------ |
| 通信方向   | 单向（客户端发起）     | 双向（全双工）     |
| 协议前缀   | `http://` / `https://` | `ws://` / `wss://` |
| 连接方式   | 每次请求新建连接       | 一次握手，持久连接 |
| 数据头部   | 每次携带完整 Header    | 头部较小，开销少   |
| 服务器推送 | 不支持                 | 支持               |

---

### WebSocket 的工作过程？

1. 客户端发送 HTTP 请求，携带 `Upgrade: websocket` 头
2. 服务器返回 `101 Switching Protocols`，完成协议升级
3. 建立持久 WebSocket 连接，双方可随时收发数据（以帧为单位）
4. 任一方发送关闭帧，双方关闭 TCP 连接
5. 通过**心跳机制**维持连接稳定

---

### ⭐️ WebSocket 与短轮询、长轮询的区别

| 对比项     | 短轮询               | 长轮询             | WebSocket        |
| ---------- | -------------------- | ------------------ | ---------------- |
| 原理       | 定时发 HTTP 请求     | 请求挂起直到有数据 | 持久全双工连接   |
| 实时性     | 差（取决于轮询间隔） | 较好               | 最好（延迟极低） |
| 资源消耗   | 高（大量无效请求）   | 中                 | 低（单连接复用） |
| 实现难度   | 简单                 | 中等               | 相对复杂         |
| 服务器推送 | 不支持               | 模拟支持           | 原生支持         |

---

### ⭐️ SSE 与 WebSocket 有什么区别？

| 对比项     | SSE                                                                                           | WebSocket                                                                                                                                |
| ---------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 通信方向   | 单向（服务器 → 客户端）                                                                       | 双向（全双工）                                                                                                                           |
| 底层协议   | HTTP/HTTPS                                                                                    | 独立的 ws/wss 协议                                                                                                                       |
| 实现复杂度 | 简单 （主要在服务器端处理。浏览器端有标准的 EventSource API，使用方便。开发和维护成本较低。） | 较复杂 （需要服务器端专门处理 WebSocket 连接和协议，客户端也需要使用 WebSocket API。如果需要考虑兼容性、心跳、重连等，开发成本会更高。） |
| 断线重连   | 浏览器原生支持                                                                                | 需手动实现                                                                                                                               |
| 数据类型   | 主要文本（UTF-8）                                                                             | 文本 + 二进制（无需额外编码）                                                                                                            |
| 典型用途   | AI 流式输出（OpenAI、DeepSeek）                                                               | 实时聊天、游戏                                                                                                                           |

为了提供更好的用户体验和利用其简单、高效、基于标准 HTTP 的特性，Server-Sent Events (SSE) 是目前大型语言模型 API（如 OpenAI、DeepSeek 等）实现流式响应的常用甚至可以说是标准的技术选择。

可以看到，响应头应里包含了 text/event-stream，说明使用的确实是 SSE。并且，响应数据也确实是持续分块传输。

## 四、PING

### PING 命令的作用是什么？

PING 是常用的网络诊断工具，用于测试：
- 两台主机之间的**网络连通性**
- 网络**往返延迟（RTT）**
- 数据包**丢包率**

这里简单举一个例子，我们来 PING 一下百度。

```bash
# 发送4个PING请求数据包到 www.baidu.com
❯ ping -c 4 www.baidu.com

PING www.a.shifen.com (14.119.104.189): 56 data bytes
64 bytes from 14.119.104.189: icmp_seq=0 ttl=54 time=27.867 ms
64 bytes from 14.119.104.189: icmp_seq=1 ttl=54 time=28.732 ms
64 bytes from 14.119.104.189: icmp_seq=2 ttl=54 time=27.571 ms
64 bytes from 14.119.104.189: icmp_seq=3 ttl=54 time=27.581 ms

--- www.a.shifen.com ping statistics ---
4 packets transmitted, 4 packets received, 0.0% packet loss
round-trip min/avg/max/stddev = 27.571/27.938/28.732/0.474 ms
```

### PING 命令的工作原理是什么？

PING 基于网络层的 **ICMP 协议**：

1. 向目标主机发送 **ICMP Echo Request**（类型 8）
2. 目标主机返回 **ICMP Echo Reply**（类型 0）
3. 根据往返时间和响应情况判断网络状态

> ICMP 报文分为两类：**查询报文**（如 PING 使用的 Echo Request/Reply）和**差错报文**（用于报告网络错误）。

## 五、DNS

### DNS 的作用是什么？

DNS（Domain Name System，域名管理系统）解决**域名和 IP 地址的映射问题**。

- 应用层协议，运行在 UDP 或 TCP 之上，端口为 **53**
- 采用**分布式、层次数据库**结构
- 解析查询顺序：浏览器缓存 → 操作系统缓存 → 路由器缓存 → DNS 服务器

---

### DNS 服务器层级结构

| 层级   | 名称                | 作用                              |
| ------ | ------------------- | --------------------------------- |
| 最高层 | 根 DNS 服务器       | 提供顶级域（TLD）服务器的 IP 地址 |
| 第二层 | 顶级域（TLD）服务器 | 管理 `.com`、`.org`、`.cn` 等后缀 |
| 第三层 | 权威 DNS 服务器     | 保存具体域名到 IP 的映射记录      |
| 辅助层 | 本地 DNS 服务器     | ISP 提供，作为代理转发 DNS 请求   |

> **注意**：全球根服务器并非只有 13 台，而是 13 组 IP 地址，实际物理服务器已超过 1700 台（截至 2023 年底）。

---

### ⭐️ DNS 解析的过程是什么样的？

以访问 `www.example.com` 为例：

1. 检查本地缓存（浏览器缓存 → 系统缓存 → Hosts 文件）
2. 向**本地 DNS 服务器**发起查询请求
3. 本地 DNS 向**根 DNS 服务器**查询 → 获得 `.com` TLD 服务器地址
4. 向 **TLD 服务器**查询 → 获得 `example.com` 权威 DNS 服务器地址
5. 向**权威 DNS 服务器**查询 → 获得 `www.example.com` 的 IP 地址
6. 返回结果并缓存，浏览器发起 TCP 连接

---

### 什么是 DNS 劫持？

DNS 劫持（也称 DNS 重定向/欺骗/污染）是一种网络攻击：

- **原理**：修改 DNS 解析结果，将域名指向错误的 IP 地址
- **危害**：用户被引导至恶意网站、无法访问正常网站
- **应对方式**：使用加密 DNS（DoH/DoT）、更换可信 DNS 服务器（如 `8.8.8.8`）、使用 HTTPS 验证服务器证书

## 六、URI 和 URL 的区别

| 概念 | 全称                                          | 说明                                   |
| ---- | --------------------------------------------- | -------------------------------------- |
| URI  | Uniform Resource Identifier（统一资源标志符） | 唯一标识一个资源（像"身份证号"）       |
| URL  | Uniform Resource Locator（统一资源定位符）    | 标识资源且提供定位路径（像"家庭住址"） |

> URL 是 URI 的子集。URL 不仅标识资源，还说明了如何访问该资源。

## 七、常见 HTTP Header 字段速查

| 字段                | 用途                               |
| ------------------- | ---------------------------------- |
| `Content-Type`      | 请求/响应体的媒体类型              |
| `Authorization`     | 认证信息                           |
| `Cache-Control`     | 缓存控制指令                       |
| `Cookie`            | 携带 Cookie 数据                   |
| `Host`              | 目标服务器域名（虚拟主机支持）     |
| `User-Agent`        | 客户端标识                         |
| `Accept`            | 客户端支持的响应内容类型           |
| `Referer`           | 请求来源页面 URL                   |
| `If-None-Match`     | 配合 ETag 做缓存验证               |
| `If-Modified-Since` | 配合 Last-Modified 做缓存验证      |
| `Range`             | 请求资源的某个部分（断点续传）     |
| `Upgrade`           | 要求升级到其他协议（如 WebSocket） |

## 八、核心知识点总结

| 考点            | 关键结论                                          |
| --------------- | ------------------------------------------------- |
| HTTP vs HTTPS   | HTTPS = HTTP + SSL/TLS，端口 80 vs 443            |
| GET vs POST     | 语义区分：查询 vs 提交；幂等 vs 非幂等            |
| HTTP/2 核心特性 | 多路复用 + 二进制帧 + 头部压缩 + 服务器推送       |
| HTTP/3 核心特性 | QUIC 协议（UDP） + 0-RTT 建连 + 解决 TCP 队头阻塞 |
| WebSocket       | 全双工持久连接，一次握手，低延迟                  |
| SSE             | 单向推送，基于 HTTP，AI 流式输出首选              |
| DNS             | UDP 53 端口，分层递归查询                         |
| PING            | 基于 ICMP，测连通性和延迟                         |
| 保持用户状态    | Session+Cookie（传统）/ JWT（现代前后端分离）     |
