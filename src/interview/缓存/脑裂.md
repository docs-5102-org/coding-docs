# 脑裂

脑裂（Split-Brain）在分布式系统中是指集群因网络分区导致被分割成多个独立部分，每个部分都认为自己是有效的主节点，从而出现多个"大脑"同时工作的情况。这会导致数据不一致、重复写入等严重问题。

## Redis集群中的脑裂

### 出现场景

在Redis主从复制架构中（配合Sentinel哨兵模式），典型的脑裂场景：

1. Master节点因网络分区与Sentinel和Slave失联
2. Sentinel认为Master已下线，选举一个Slave为新Master
3. 旧Master仍在运行并接受客户端写入
4. 网络恢复后，旧Master的数据会被新Master覆盖，导致数据丢失

### 解决方案

**1. 配置最小从节点数量**
```conf
# 要求至少有N个从节点在线
min-replicas-to-write 1

# 从节点延迟不能超过N秒
min-replicas-max-lag 10
```
这样当Master发现自己与从节点失联时，会拒绝写入，避免脑裂期间的数据丢失。

**2. 使用Redis Cluster**
Redis Cluster采用去中心化架构，通过Gossip协议和投票机制：
- 节点间互相通信，检测彼此状态
- 需要超过半数节点认可才能进行主从切换
- 自动进行slot迁移和数据同步

## Elasticsearch集群中的脑裂

### 出现场景
ES集群中的脑裂通常发生在：

1. 网络分区将集群分成两部分
2. 两部分都有足够的节点，各自选举出新Master
3. 出现两个Master同时管理不同的节点子集
4. 索引操作在不同的分区中进行，导致数据不一致

### 解决方案

**1. discovery.zen.minimum_master_nodes（ES 7.0之前）**
```yaml
# 设置最小主节点数 = (master候选节点数 / 2) + 1
discovery.zen.minimum_master_nodes: 2
```
这是最关键的配置，确保只有获得多数选票的节点才能成为Master。

例如：3个master候选节点，设置为2；5个设置为3。

**2. ES 7.0+的自动配置**
ES 7.0及以后版本移除了上述配置，改用自动quorum机制：
- 集群启动时自动发现符合条件的master节点
- 内置的cluster bootstrapping机制
- 自动计算并维护quorum

```yaml
# 初始化集群时指定master候选节点
cluster.initial_master_nodes: ["node-1", "node-2", "node-3"]
```

**3. 部署最佳实践**
- 部署**奇数个**master候选节点（3、5、7个）
- 至少3个master候选节点
- 确保网络稳定性，使用专用网络进行节点间通信
- 合理配置超时参数：
```yaml
discovery.zen.ping_timeout: 30s
discovery.zen.fd.ping_timeout: 30s
```

**4. 监控和告警**
- 监控集群状态（green/yellow/red）
- 监控master节点切换频率
- 设置节点失联告警

## 通用防护原则

对于Redis和ES，防止脑裂的核心思想都是：

1. **Quorum机制**：需要多数节点同意才能进行关键操作
2. **奇数节点**：避免平票情况
3. **最小节点数限制**：确保分区后只有一方能继续工作
4. **网络优化**：减少网络分区发生的概率
5. **合理的超时设置**：避免误判节点失效

这些机制本质上都是在可用性和一致性之间做权衡（CAP理论），通过牺牲部分可用性来保证数据一致性。
