# 脑裂

脑裂（Split-Brain）在分布式系统中是指集群因网络分区导致被分割成多个独立部分，每个部分都认为自己是有效的主节点，从而出现多个"大脑"同时工作的情况。这会导致数据不一致、重复写入等严重问题。

### 出现场景

在Redis主从复制架构中（配合Sentinel哨兵模式），典型的脑裂场景：

1. Master节点因网络分区与Sentinel和Slave失联
2. Sentinel认为Master已下线，选举一个Slave为新Master
3. 旧Master仍在运行并接受客户端写入
4. 网络恢复后，旧Master的数据会被新Master覆盖，导致数据丢失

### 解决方案

#### 方案一：min-replicas 配置（最常用）

```conf

# Master 要求至少 1 个从节点在线
min-replicas-to-write 1

# 从节点心跳延迟不能超过 10 秒
min-replicas-max-lag 10
```

**原理：** Master 检测不到足够数量的健康从节点时，**主动拒绝写入**，让脑裂期间的旧 Master 变成只读，从根本上避免数据写入后丢失。

```
脑裂发生：
  旧 Master 发现从节点全部失联
  → 不满足 min-replicas-to-write = 1
  → 拒绝所有写操作，返回错误
  → 客户端感知到写入失败，及时告警
  → 网络恢复后无数据冲突 ✅
```

**代价：** 这是用**可用性换一致性**，从节点全挂时 Master 拒绝写入，业务会报错。需要根据场景权衡：

```
金融/支付类业务   →  宁可不可用，不能丢数据  →  配置此项
缓存类业务        →  宁可丢数据，保证可用性  →  不配或设为 0
```

#### 方案二：合理设置 Sentinel 参数

```conf
# 判断 Master 下线的超时时间，不能太短，避免网络抖动误判

# 默认 30s，根据网络质量调整
sentinel down-after-milliseconds mymaster 10000

# 故障转移超时时间
sentinel failover-timeout mymaster 60000
```


#### 方案三：客户端写入确认（WAIT 命令）

```java
// 写入后等待至少 1 个从节点同步，超时 100ms
jedis.set("key", "value");
long syncedReplicas = jedis.wait(1, 100);

if (syncedReplicas < 1) {
    // 没有从节点确认同步，记录告警
    log.warn("数据未同步到从节点，存在丢失风险");
}
```

**注意：** WAIT 不是强一致，只是尽力而为，网络分区时依然可能失效。

---

#### 方案四：使用 Redis Cluster

Redis Cluster 采用去中心化架构，通过 **Gossip 协议 + 投票机制**解决脑裂：


**节点故障判定流程：**

```
单个节点发现 Master 无响应  →  标记 PFAIL（疑似下线）
                               ↓
超过半数 Master 节点都标记 PFAIL  →  升级为 FAIL（确认下线）
                               ↓
该 Master 的从节点发起选举  →  获得超过半数 Master 投票
                               ↓
晋升为新 Master，接管对应 Slot

```

**为什么能防止脑裂：**

网络分区时少数派分区（Master 数量 ≤ 总数/2）
  → 无法获得超过半数的投票
  → 无法触发故障转移
  → 少数派分区变为只读，不接受写入 ✅

### 四种方案对比

| 方案 | 实现难度 | 防脑裂效果 | 代价 |
|------|---------|-----------|------|
| min-replicas 配置 | 简单 | 好 | 从节点挂了主节点也拒写 |
| Sentinel 参数调优 | 简单 | 减少误判，治标 | 不能完全避免 |
| WAIT 命令 | 中等 | 一定程度降低丢失 | 性能下降，非强一致 |
| Redis Cluster | 复杂 | 最好，架构级保障 | 部署运维成本高 |

> 生产环境推荐：**min-replicas 配置 + Sentinel 参数调优** 作为基础保障，数据一致性要求极高的场景上 **Redis Cluster**。


## Elasticsearch 集群脑裂

### 什么是脑裂

脑裂指网络分区或节点异常导致集群中出现**两个都认为自己是 Master 的节点**，
各自管理不同的节点子集，索引操作在不同分区中进行，导致数据不一致。

---

### 触发原因

**1. 网络分区**

集群被分成两部分，两部分都有足够节点，各自选举出新 Master，
出现两个 Master 同时运行的局面。

**2. GC 停顿（生产环境最常见）**

Master 节点发生长时间 Full GC（Stop-The-World）
→ 无法响应心跳
→ 其他节点误判 Master 下线
→ 触发重新选举
→ GC 结束后出现两个 Master

```
GC 停顿时间 > discovery 超时时间 → 必然触发误判
所以堆内存不宜过大，建议不超过 32GB，减少 Full GC 频率
```

**3. 节点负载过高**

节点 CPU 或 IO 负载过高，心跳响应超时，被其他节点误判为下线。

---

### 脑裂发生的完整过程

```
正常状态：
  Master(Node1) ←→ Node2
                ←→ Node3

网络分区：
  [分区A]  Master(Node1) ← Client 继续写入
  ─────────── 网络断开 ───────────
  [分区B]  Node2、Node3 → 选举 Node2 为新 Master

两个 Master 同时运行：
  分区A：Node1 继续接受写入，索引数据 v1
  分区B：Node2 接受新写入，索引数据 v2

网络恢复：
  Node1 被降级，数据以多数派（分区B）为准
  分区A 期间的写入全部丢失 ❌
```

---

### 解决方案

#### 1. minimum_master_nodes（ES 7.0 之前）

```yaml
# 设置最小主节点数 = (master 候选节点数 / 2) + 1
discovery.zen.minimum_master_nodes: 2
```

**核心公式：**

| master 候选节点数 | minimum_master_nodes |
|-----------------|----------------------|
| 3               | 2                    |
| 5               | 3                    |
| 7               | 4                    |

原理：分区后少数派节点数不足 minimum_master_nodes，无法选出新 Master，
只有多数派分区能继续工作，从架构上避免两个 Master 同时存在。

---

#### 2. 自动 Quorum 机制（ES 7.0+）

ES 7.0 移除了 `discovery.zen.minimum_master_nodes`，改为内置自动 quorum：

- 集群启动时自动发现符合条件的 Master 候选节点
- 自动计算并维护 quorum（多数派）
- 内置 cluster bootstrapping 机制，无需手动配置节点数

```yaml
# 仅在集群第一次初始化时使用，后续重启不需要也不生效
cluster.initial_master_nodes: ["node-1", "node-2", "node-3"]
```

> ⚠️ `cluster.initial_master_nodes` 只用于集群首次启动的引导，
> 不是运行时参数，集群正常运行后可以从配置中移除。

---

#### 3. Voting-Only 节点（ES 7.3+）

ES 7.3 引入的专属特性，用于低成本凑奇数节点：

```yaml
# 配置为 voting_only 角色
node.roles: [ voting_only ]
```

```
特点：
  ✅ 参与 Master 选举投票，贡献票数
  ✅ 自己不会成为 Master
  ✅ 资源消耗极低

典型部署（降低成本）：
  2 个正常 Master 候选节点（高配）
  + 1 个 Voting-Only 节点（低配）
  = 共 3 票，满足 quorum ✅
```

---

#### 4. 部署最佳实践

**节点数量：**

```
Master 候选节点必须是奇数：3、5、7
最少 3 个，避免平票导致无法选举
```

**JVM 堆内存：**

```yaml
# jvm.options
# 堆内存不超过 32GB，减少 Full GC 停顿时间
-Xms16g
-Xmx16g
```

**超时参数（注意版本差异）：**

```yaml
# ES 7.0 之前
discovery.zen.ping_timeout: 30s
discovery.zen.fd.ping_timeout: 30s

# ES 7.0+（参数已重命名）
discovery.request_peers_timeout: 30s
transport.ping_schedule: 5s
```

**网络隔离：**

```yaml
# 节点间通信使用专用内网，与客户端请求网络隔离
network.host: 192.168.1.x
transport.host: 192.168.1.x
http.host: 0.0.0.0
```

---

#### 5. 监控与告警

```
监控指标：
  cluster.status      green / yellow / red 状态变化
  master_node         Master 节点切换频率
  jvm.gc              Full GC 停顿时间和频率
  节点失联次数         单位时间内超过阈值立即告警

告警阈值建议：
  Master 切换 > 1次/小时    → 告警
  Full GC 停顿 > 5s         → 告警
  集群状态持续 red > 1分钟  → 紧急告警
```

---

### 脑裂发生后如何恢复

```
步骤一：确认两个分区的数据现状
  → 对比两个 Master 各自的索引版本号和文档数量
  → 确认哪个分区数据更完整、更新

步骤二：停止少数派分区
  → 手动停止少数派节点，避免继续写入
  → 防止恢复时产生更多冲突

步骤三：重新加入集群
  → 让少数派节点重新加入多数派集群
  → 节点会自动从多数派同步数据（shard recovery）

步骤四：验证数据一致性
  → 检查索引文档数量是否符合预期
  → 必要时通过业务日志手动补偿丢失的数据

步骤五：排查根因
  → 查看 GC 日志、网络监控
  → 修复根本原因，避免再次发生
```

### 与 Redis 脑裂的对比

| 对比项 | Redis（Sentinel 模式） | Elasticsearch |
|--------|----------------------|---------------|
| 选举机制 | Sentinel 投票 | Raft 协议变体 |
| 防脑裂配置 | min-replicas-to-write | minimum_master_nodes / 自动 quorum |
| 最小节点要求 | 3 个 Sentinel | 3 个 Master 候选节点 |
| GC 影响 | 影响较小 | 影响较大，是主要触发原因之一 |
| 恢复方式 | 自动 | 需人工介入验证 |

---

### 核心原则总结

防止脑裂本质上都是 **CAP 理论中 C（一致性）与 A（可用性）的权衡**：

```
Quorum 机制    → 需要多数节点同意才能选举，少数派分区自动停写
奇数节点       → 避免平票，保证选举一定能产生结果
最小节点数     → 分区后只有多数派能继续工作
超时合理设置   → 避免因网络抖动或 GC 误判节点失效
堆内存控制     → 减少 Full GC 停顿，降低误判概率
```

> 预防 > 恢复。通过合理的部署架构和参数配置，
> 绝大多数脑裂场景都可以在发生前被规避。
