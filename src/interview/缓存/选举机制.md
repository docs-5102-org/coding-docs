## 核心概念

### 什么是 Redis Cluster 的故障转移？

当 Redis 集群中的某个**主节点（Master）**宕机后，集群会自动将该主节点的某个**从节点（Slave）**提升为新的主节点，这个过程称为 **Failover（故障转移）**。

### 关键特点

- ✅ **去中心化架构**：无需哨兵，集群节点自己完成选举
- ✅ **自动化**：无需人工干预，自动完成故障转移
- ✅ **数据优先**：优先选择数据最新的从节点
- ✅ **多数派投票**：需要超过半数主节点同意才能完成选举

## 故障检测机制

### 两个阶段的故障判定

#### 1️⃣ 主观下线（PFAIL - Possible Failure）

**定义**：单个节点认为目标节点可能已经下线

**触发条件**：
```
节点 A 向节点 B 发送 PING
超过 cluster-node-timeout 未收到 PONG 响应
→ 节点 A 将节点 B 标记为 PFAIL
```

#### 2️⃣ 客观下线（FAIL - Failure）

**定义**：集群多数节点确认目标节点已经下线

**触发条件**：
```
超过半数的主节点认为节点 B 处于 PFAIL 状态
→ 节点 B 被标记为 FAIL（客观下线）
→ 触发故障转移流程
```

### 故障检测示例

```
集群配置：3 个主节点（A, B, C）

时间线：
T0: 主节点 A 宕机
T1: 主节点 B 检测到 A 超时 → 标记 A 为 PFAIL
T2: 主节点 C 检测到 A 超时 → 标记 A 为 PFAIL
T3: B 和 C 交换信息，发现都认为 A 是 PFAIL
T4: 超过半数主节点（2/3）确认 → A 被标记为 FAIL
T5: 触发故障转移流程
```

**⚠️ 重要**：只有**主节点**才有投票权判断故障，从节点无投票权。

## 选举流程详解

### 完整的六个步骤

#### ① 故障检测：超过半数主节点判断其宕机

```
前提条件：
- 目标主节点进入 FAIL 状态
- 超过 N/2 的主节点确认（N = 主节点总数）
```

#### ② 从节点发起选举

当主节点被标记为 FAIL 后：
- 该主节点的**所有从节点**都有资格参与选举
- 从节点不会同时发起选举，而是等待一个**延迟时间**

#### ③ 延迟机制：数据越新优先级越高

**延迟计算公式**：
```
延迟时间 = 固定延迟 + 随机延迟 + (偏移量排名 * 1000ms)
```

**偏移量排名规则**：
- 复制偏移量越大 = 数据越新 = 排名越靠前
- 排名越靠前 = 延迟越短 = 越早发起选举

**示例**：
```
主节点 A（已宕机）有 3 个从节点：

从节点 A1: offset = 10000 (最新) → 延迟 500ms
从节点 A2: offset = 9800  (次新) → 延迟 1500ms  
从节点 A3: offset = 9500  (最旧) → 延迟 2500ms

结果：A1 最先发起选举请求
```

#### ④ 从节点请求投票

从节点向**所有主节点**发送投票请求：
```
FAILOVER_AUTH_REQUEST
```

**请求内容包括**：
- 当前配置纪元（epoch）
- 从节点的复制偏移量
- 原主节点的 ID

#### ⑤ 主节点投票

每个主节点收到投票请求后，根据以下条件决定是否投票：

**投票条件**：
```
✅ 确认原主节点确实处于 FAIL 状态
✅ 该从节点确实是原主节点的合法从节点
✅ 本轮选举（epoch）中尚未投票给其他节点
✅ 请求的时效性在可接受范围内
```

**投票规则**：
- 每个主节点在一个配置纪元（epoch）内**只能投 1 票**
- **先到先得**：第一个发起请求的从节点优先获得投票
- 投票后会回复：`FAILOVER_AUTH_ACK`

**示例**：
```
集群：6 个主节点（B, C, D, E, F, G）

A1 发起投票请求：
→ 主节点 B：投票给 A1 ✅
→ 主节点 C：投票给 A1 ✅
→ 主节点 D：投票给 A1 ✅
→ 主节点 E：投票给 A1 ✅
→ 主节点 F：还未收到请求
→ 主节点 G：还未收到请求

A1 获得 4 票（> 6/2 = 3），选举成功
```

#### ⑥ 获得多数票的从节点晋升为主节点

**晋升条件**：
```
获得票数 > 主节点总数 / 2
```

**晋升操作**：
```bash
# 从节点执行
SLAVEOF NO ONE

# 成为独立的主节点
# 开始接管原主节点的槽位
```

**广播通知**：
```
新主节点向所有集群节点发送：
FAILOVER_MANIFEST

内容包括：
- 新主节点的 ID
- 接管的槽位信息
- 新的配置纪元
```

## 投票机制

### 投票权限

| 节点类型 | 是否有投票权 | 说明 |
|---------|-------------|------|
| **主节点** | ✅ 有 | 唯一拥有投票权的节点 |
| **从节点** | ❌ 无 | 只能被投票，不能投票给别人 |

### 投票数量计算

```
需要票数 = (主节点总数 / 2) + 1

示例：
- 3 个主节点：需要 2 票
- 6 个主节点：需要 4 票
- 9 个主节点：需要 5 票
```

### 为什么需要多数派投票？

**防止脑裂问题**：
```
场景：网络分区导致集群被分成两部分

分区 1：主节点 A、B（2 个）
分区 2：主节点 C（1 个）

如果不要求多数派：
→ 分区 2 可能单独选举新主节点
→ 集群出现两个主节点（脑裂）

采用多数派投票：
→ 分区 2 只有 1 票，无法完成选举（需要 2 票）
→ 只有分区 1 可以完成选举
→ 避免脑裂
```

### 一句话总结流程

> **多数主节点判断原主节点挂了 → 偏移量最新的从节点发起投票 → 获得多数主节点授权 → 晋升为新主节点 → 广播路由 → 集群恢复**

## 关键参数配置

### cluster-node-timeout

**含义**：节点超时判定时间

**默认值**：15000（15秒）

**作用**：
- 超过此时间未收到 PONG 响应 → 标记为 PFAIL
- 影响故障检测的速度

**配置建议**：
```conf
# 生产环境建议值
cluster-node-timeout 15000

# 高可用优先（快速故障转移）
cluster-node-timeout 5000

# 稳定性优先（避免误判）
cluster-node-timeout 30000
```

### cluster-replica-validity-factor

**含义**：从节点数据有效性因子

**默认值**：10

**作用**：
```
如果从节点与主节点断开时间超过：
(cluster-node-timeout * cluster-replica-validity-factor) + repl-ping-replica-period

则该从节点不参与选举
```

**配置示例**：
```conf
# 允许数据稍微落后的从节点参与选举
cluster-replica-validity-factor 10

# 设为 0：禁用此检查，所有从节点都能参与选举
cluster-replica-validity-factor 0
```

### cluster-require-full-coverage

**含义**：是否要求完整覆盖所有槽位

**默认值**：yes

**作用**：
```
yes: 如果有槽位未分配，整个集群停止服务
no:  即使有槽位未分配，其他槽位仍可用
```

**配置建议**：
```conf
# 生产环境推荐：保证数据完整性
cluster-require-full-coverage yes

# 高可用优先：允许部分服务
cluster-require-full-coverage no
```

## 常见问题

### Q1: 如果多个从节点同时发起选举怎么办？

**答**：不会同时发起。

- 通过**延迟机制**避免冲突
- 复制偏移量越大，延迟越短
- 数据最新的从节点会最先发起选举
- 由于投票是"先到先得"，最先发起的从节点会获得大部分投票

### Q2: 如果没有从节点怎么办？

**答**：无法自动故障转移。

```
场景：主节点 A 没有从节点
结果：
- 主节点 A 宕机后，其负责的槽位无法服务
- 集群会标记为 FAIL 状态
- 需要人工介入修复
```

**建议**：每个主节点至少配置 1 个从节点。

### Q3: 主节点恢复后会怎样？

**答**：变成从节点。

```
时间线：
T0: 主节点 A 宕机
T1: 从节点 A1 晋升为新主节点
T2: 旧主节点 A 恢复上线
T3: A 发现 A1 已经是主节点（epoch 更大）
T4: A 自动变成 A1 的从节点
```

### Q4: 网络分区会导致脑裂吗？

**答**：不会。

```
场景：集群被分成两个分区

分区 1: 主节点 A、B、C（3个）
分区 2: 主节点 D、E（2个）

如果某个主节点在分区 2 宕机：
→ 分区 2 只有 2 个主节点，无法获得多数票（需要 3 票）
→ 选举失败，不会产生新主节点
→ 避免脑裂

只有拥有多数主节点的分区才能完成选举
```

### Q5: 为什么要求至少 3 个主节点？

**答**：满足多数派投票机制。

```
2 个主节点的问题：
- 需要 2 票才能选举成功（2/2 + 1）
- 如果 1 个主节点宕机，只剩 1 个主节点
- 1 票无法完成选举
- 集群无法自动故障转移

3 个主节点：
- 需要 2 票（3/2 + 1）
- 1 个主节点宕机，剩余 2 个主节点
- 2 票可以完成选举 ✅
```

### Q6: 从节点优先级如何影响选举？

**答**：Redis Cluster 的选举主要依据**复制偏移量**，没有像 Sentinel 那样的显式优先级配置。

**选举优先级**：
```
1. 复制偏移量（最重要）：数据越新越优先
2. Run ID：偏移量相同时，字典序小的优先
```

如果需要手动干预选举，可以：
- 手动执行 `CLUSTER FAILOVER` 强制提升某个从节点
- 使用 `CLUSTER FAILOVER TAKEOVER` 跳过一致性检查（危险）

## Sentinel 的故障转移

### 故障检测

**三个哨兵监控一主多从**：

```
哨兵1、哨兵2、哨兵3
    ↓ 监控
主节点Master（挂了）
  ├─ 从节点Slave1
  ├─ 从节点Slave2
  └─ 从节点Slave3
```

### 投票选举过程

**第一阶段：选出领导哨兵**

```
1. 哨兵1发现主节点下线（主观下线）
2. 哨兵1询问其他哨兵："你们觉得主节点下线了吗？"
3. 超过 quorum 数量的哨兵确认 → 客观下线
4. 哨兵们投票选出一个领导哨兵（Raft算法）
   - 每个哨兵在一个纪元内只能投1票
   - 需要获得 >哨兵总数/2 的票数
```

**第二阶段：领导哨兵选择新主节点**

```
领导哨兵根据以下优先级选择从节点：

1. 优先级（slave-priority）：数值越小优先级越高
2. 复制偏移量：数据越新越优先
3. Run ID：字典序最小的

假设：
- Slave1（优先级100，偏移量1000）
- Slave2（优先级100，偏移量1020）← 被选中
- Slave3（优先级50，偏移量990）

选择结果：Slave2 晋升为主节点
```

### 详细示例

**配置**：
```
# sentinel.conf
sentinel monitor mymaster 192.168.1.100 6379 2  # quorum=2
sentinel down-after-milliseconds mymaster 5000
sentinel parallel-syncs mymaster 1
sentinel failover-timeout mymaster 180000
```

**故障转移流程**：
```
时间线：
T0: 主节点Master宕机
T1: 哨兵1检测到超时（5秒后）→ 主观下线
T2: 哨兵1询问哨兵2和3
T3: 哨兵2确认下线 → 达到quorum(2) → 客观下线
T4: 哨兵们投票选举领导哨兵
    - 哨兵1获得2票 → 成为领导者
T5: 哨兵1选择Slave2作为新主节点
T6: 哨兵1执行failover：
    - 将Slave2提升为主节点
    - 让Slave1和Slave3指向新主节点
    - 标记旧Master为从节点（恢复后会变成从节点）
```

## 总结

### 核心机制概述

Redis Cluster 采用**去中心化的多数派投票机制**实现自动故障转移，无需依赖外部哨兵组件。整个故障转移过程分为故障检测、选举发起、投票决策、主从切换四个阶段，通过精妙的延迟机制和投票规则，确保数据最新的从节点成为新主节点，实现高可用性和数据一致性的完美平衡。

### 故障检测机制

故障检测采用**两阶段确认机制**：首先由单个节点标记为主观下线(PFAIL)，当超过半数主节点都认为目标节点不可达时，该节点被标记为客观下线(FAIL)并在集群中广播。这种设计有效避免了网络抖动导致的误判，同时通过`cluster-node-timeout`参数控制检测灵敏度。检测过程中，节点间通过Gossip协议持续交换状态信息，确保故障信息能够快速传播到整个集群。

### 选举发起与延迟机制

当主节点被标记为客观下线后，其所有从节点都有资格发起选举，但**不会同时发起**。这里的关键设计是**基于复制偏移量的延迟机制**：复制偏移量越大（数据越新）的从节点，其选举延迟越短，优先发起投票请求。具体计算公式为：`DELAY = 500ms + random(0~500ms) + RANK * 1000ms`，其中RANK是该从节点按偏移量排序后的排名（偏移量最大者RANK=0）。这确保了数据最完整的从节点能够抢先获得投票机会。

### 投票决策规则

投票遵循**严格的多数派原则和先到先得规则**：每个主节点在同一配置纪元(Config Epoch)中只能投票一次，且会将票投给第一个请求投票的从节点。从节点需要获得**超过集群主节点总数一半的选票**才能当选。投票时主节点会验证请求者的复制偏移量，确保其数据足够新。如果第一轮选举失败（如多个从节点同时发起导致选票分散），从节点会递增配置纪元并发起新一轮选举，每轮选举间隔逐渐增加以避免活锁。

### 一主多从场景处理

在一主多从的典型场景中，假设主节点有3个从节点（偏移量分别为1000、950、900），当主节点故障时：
1. **偏移量1000的从节点**延迟500-1000ms后发起选举
2. **偏移量950的从节点**延迟1500-2000ms后发起选举  
3. **偏移量900的从节点**延迟2500-3000ms后发起选举

由于数据最新的从节点率先发起投票，且主节点遵循"先到先得"原则，该从节点会最先获得多数派支持并当选，其他从节点收到当选广播后自动放弃选举。这种机制天然保证了**数据最新者优先当选**，无需复杂的数据比对过程。

### 网络分区与脑裂防护

Redis Cluster 通过**多数派投票机制天然防止脑裂**。在网络分区场景下，只有包含多数派主节点的分区能够完成故障转移，少数派分区因无法获得足够选票而无法选举新主节点。例如，在3主3从的集群中，如果网络分为2:1分区，包含2个主节点的分区可以完成选举（2 > 3/2），而只有1个主节点的分区无法完成选举。同时，客户端通过集群拓扑信息能够识别并连接到多数派分区，确保服务连续性。

### 与Sentinel模式对比

| 对比维度 | Redis Cluster | Redis Sentinel |
|---------|---------------|----------------|
| **架构设计** | 去中心化，主节点直接参与投票 | 中心化，独立的哨兵进程监控 |
| **投票主体** | 其他主节点投票选从节点 | 哨兵先选领导者，再由领导者选从节点 |
| **选举依据** | 单一标准：复制偏移量（数据新旧） | 多重标准：优先级→偏移量→RunID |
| **延迟机制** | 有延迟机制，数据越新延迟越短 | 无延迟机制，依赖优先级配置 |
| **票数要求** | 需要 >主节点总数/2 | 需要 >哨兵总数/2（选领导）+ quorum（确认下线）|
| **部署复杂度** | 相对简单，无需额外组件 | 需要部署和维护独立哨兵集群 |
| **适用场景** | 大规模分布式场景，需要数据分片 | 小规模主从场景，无需分片 |

Cluster模式的优势在于**去中心化设计更简洁**，主节点既负责数据服务又参与故障转移决策，减少了组件依赖；Sentinel模式则通过**独立的监控层**提供更灵活的配置（如slave-priority），适合对故障转移有特殊要求的场景。

### 最佳实践建议

**部署架构层面**：
- ✅ 每个主节点配置**至少1-2个从节点**，保证故障转移可用性
- ✅ 集群至少部署**3个主节点**，满足多数派投票要求（建议奇数个）
- ✅ 主从节点**跨机架/跨可用区部署**，避免单点故障影响整个分片
- ✅ 合理规划**节点数量与槽位分配**，避免数据倾斜

**监控运维层面**：
- ✅ 实时监控**复制延迟(repl_offset)**，确保从节点数据及时同步
- ✅ 监控**cluster_state状态**，及时发现槽位分配问题
- ✅ 配置**节点故障告警**，在PFAIL阶段即介入检查
- ✅ 定期**演练故障转移流程**，验证集群高可用性配置
- ✅ 记录**Config Epoch变化**，追踪集群拓扑变更历史

**性能优化层面**：
- ✅ 根据业务特点调整**cluster-node-timeout**，平衡检测速度和稳定性
- ✅ 合理设置**复制缓冲区大小**，减少全量同步概率
- ✅ 使用**无盘复制(repl-diskless-sync)**提升同步性能
- ✅ 监控**网络延迟和带宽**，确保集群通信质量

### 常见问题与解决方案

**问题1：从节点数据延迟大，故障转移后数据丢失**  
解决：配置`min-slaves-to-write`和`min-slaves-max-lag`，当可用从节点不足或延迟过大时主节点拒绝写入，牺牲可用性保证数据安全性

**问题2：网络抖动导致频繁故障转移**  
解决：适当增加`cluster-node-timeout`值，或在网络层面优化，减少丢包和延迟波动

**问题3：脑裂导致数据不一致**  
解决：确保客户端使用集群模式连接（使用MOVED/ASK重定向），避免直连节点导致写入少数派分区

**问题4：从节点太多导致选举时间过长**  
解决：控制单个主节点的从节点数量（建议不超过3个），过多从节点会增加选举延迟和资源消耗

### 一句话精髓

> Redis Cluster通过**去中心化的多数派投票**+**基于复制偏移量的延迟机制**，实现了毫秒级故障检测、秒级自动切换的高可用架构，在无需外部组件的前提下，保证了数据一致性、服务连续性和分布式环境下的脑裂防护，是大规模Redis部署的首选方案。
