# 缓存与数据库一致性：延迟双删及相关策略

> **核心问题**：在并发场景下，读写操作可能交错执行，导致缓存与数据库的数据不同步。

---

## 一、为什么会出现不一致？

以最常见的"先删缓存，再更新数据库"为例：

```
T1: 请求A 删除 Cache
T2: 请求B 查 Cache 未命中 → 查 DB（此时 DB 还是旧值）
T3: 请求A 更新 DB 为新值
T4: 请求B 把旧值写入 Cache
结果：Cache = 旧值，DB = 新值 ❌
```

不同的策略选择，本质上都是在试图解决这个**并发写-读窗口期**的问题。

---

## 二、主要策略详解

### 1. Cache Aside Pattern（先更新 DB，再删除缓存）

**执行流程：**

```
写操作：更新 DB → 删除 Cache
读操作：查 Cache → 未命中 → 查 DB → 写入 Cache
```

**为什么推荐这种方式？**

- DB 是唯一真实数据源，以 DB 为准
- 删除缓存比更新缓存更安全（避免复杂的数据转换逻辑）
- 下次读取时自动从 DB 加载最新数据

**潜在问题：**

```
T1: 请求A 更新 DB 成功（name = "新值"）
T2: 请求A 尝试删除 Cache，但失败了！
T3: 请求B 读取 Cache，拿到旧值
结果：数据不一致 ❌
```

**解决方案：**

- 使用消息队列重试删除
- 记录删除失败的 key，后台异步处理

---

### 2. 延迟双删策略

**执行流程：**

```
1. 删除缓存（第一次）
2. 更新数据库
3. 等待 N 毫秒（通常 100~500ms）
4. 再次删除缓存（第二次）
```

**解决的核心问题：**

不使用延迟双删时：

```
T1: 请求A 删除 Cache
T2: 请求B 查 Cache 未命中 → 查 DB（旧值）
T3: 请求A 更新 DB 为新值
T4: 请求B 把旧值写入 Cache
结果：Cache = 旧值，DB = 新值 ❌
```

使用延迟双删后：

```
T1: 请求A 删除 Cache（第一次）
T2: 请求B 查 Cache 未命中 → 查 DB → 写入 Cache（旧值）
T3: 请求A 更新 DB
T4: 等待 500ms（确保请求B 已完成写入）
T5: 请求A 再次删除 Cache（第二次，清除 B 写入的旧值）
结果：最终一致 ✅（概率上）
```

**延迟时间如何确定？**

> 需要大于一次完整读操作的耗时（查 DB + 写 Cache），通常设置为 **100~500ms**。可结合线上监控 P99 响应时间来决定。

**代码示例：**

```java
public void updateData(String key, Object newValue) {
    // 1. 第一次删除缓存
    cache.delete(key);

    // 2. 更新数据库
    db.update(key, newValue);

    // 3. 延迟后再次删除（生产环境建议用异步线程或定时任务，避免阻塞主流程）
    Thread.sleep(500);
    cache.delete(key);
}
```

> ⚠️ **生产建议**：不要在主线程 `sleep`，应将第二次删除提交到异步线程池或延迟队列执行。

---

#### 延迟双删仍然存在的问题

延迟双删**不能保证**一致性，只能**大幅降低**不一致的概率。

| 问题 | 说明 |
|------|------|
| **第二次删除可能失败** | 网络抖动或 Redis 宕机导致第二次删除未执行，Cache 依然是旧值 |
| **延迟时间不一定够** | 若请求B 的 DB 查询 + 写 Cache 超过设定的等待时间，B 写完后 Cache 又变成旧值 |
| **窗口期内读到旧值** | 等待的 500ms 内，所有读请求都会拿到 Cache 的旧值，强一致性场景不可接受 |

---

### 3. 设置合理的过期时间（兜底策略）

**核心理念：** 允许短暂不一致，依靠过期时间自动修复。

```
T1: Cache 与 DB 不一致（Cache = 旧值，DB = 新值）
T2: 系统继续运行，期间用户可能读到旧值
T3: Cache 过期（如 5 分钟后自动失效）
T4: 下次读取时从 DB 加载新值，恢复一致
```

**过期时间设置建议：**

| 数据类型 | 推荐过期时间 |
|----------|------------|
| 热点数据（高频读） | 5 ~ 30 分钟 |
| 普通业务数据 | 1 ~ 24 小时 |
| 强一致性数据 | 不建议单独依赖此策略 |

**适用场景：** 对一致性要求不高的业务，如商品浏览量、文章阅读数等。

---

### 4. Binlog + MQ 异步删除（推荐方案）

**架构流程：**

```
应用更新 DB
    ↓
MySQL 产生 binlog
    ↓
Canal 监听 binlog 变更
    ↓
解析变更内容，发送消息到 MQ（如 Kafka）
    ↓
消费者接收消息 → 删除 / 更新 Cache
```

> 什么是Canal?，[详见](../../article/canal.md)

**优点：**

- 业务代码无侵入，不需要手动管理缓存删除
- MQ 保证消息不丢失，可配置重试机制
- 彻底解耦业务逻辑与缓存更新

**实现示例（伪代码）：**

```java
// Canal 监听器：监听 DB 变更事件
public class CanalListener {
    @Subscribe
    public void onDatabaseChange(BinlogEvent event) {
        if (event.isUpdate() || event.isDelete()) {
            String key = generateCacheKey(event.getTableName(), event.getId());
            mqProducer.send(new CacheInvalidateMessage(key));
        }
    }
}

// MQ 消费者：异步执行缓存删除
public class CacheInvalidateConsumer {
    @MessageListener
    public void handleMessage(CacheInvalidateMessage msg) {
        cache.delete(msg.getKey());
        // 失败时 MQ 可自动重试，保证最终删除成功
    }
}
```

**与延迟双删的核心区别：**

| 对比点 | 延迟双删 | Binlog + MQ |
|--------|----------|-------------|
| 代码侵入 | 有（需手动处理） | 无 |
| 可靠性 | 第二次删除可能失败 | MQ 重试保证可靠 |
| 延迟时间 | 靠"猜"经验值 | 无需猜测，事件驱动 |
| 实现复杂度 | 低 | 中（需引入 Canal + MQ） |

---

## 三、方案选型对比

| 方案 | 一致性 | 复杂度 | 适用场景 |
|------|--------|--------|----------|
| Cache Aside + 重试 | 最终一致 | 低 | 通用场景 |
| 延迟双删 | 最终一致（概率） | 低 | 一般业务，快速落地 |
| 设置过期时间 | 弱一致（兜底） | 极低 | 低一致性要求的业务 |
| Binlog + MQ | 最终一致（可靠） | 中 | **推荐，分布式系统** |
| 分布式锁 | 强一致 | 高 | 金融、库存等核心场景 |
| 直接读 DB | 强一致 | 低 | 低并发、小流量系统 |

---

## 四、实际应用建议

根据业务对一致性的要求，选择合适的策略：

| 业务场景 | 推荐方案 |
|----------|----------|
| 订单、支付等核心链路 | 先更新 DB 再删 Cache + MQ 重试机制 |
| 用户信息、配置数据 | 延迟双删 |
| 浏览量、点赞数等 | 过期时间策略即可 |
| 大型分布式系统 | Binlog + MQ 异步方案 |

**组合使用（推荐生产实践）：**

```
主策略：先更新 DB，再删除 Cache
  + 兜底：设置合理的 Cache 过期时间
  + 增强：延迟双删 或 Binlog + MQ
```

> **核心原则：** 没有银弹，关键是根据业务对一致性的容忍度，选择合适的策略或组合。强一致性要付出更高的复杂度和性能代价，弱一致性则换来更好的可用性和吞吐量。
