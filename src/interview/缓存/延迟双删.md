# 延迟双删

延迟双删 可以保证缓存与数据库的一致性

## 为什么会出现不一致？

在并发场景下，读写操作可能交错执行，导致缓存和数据库数据不同步。

## 各种策略详解

### **1. 先更新数据库，再删除缓存（Cache Aside Pattern）**

**执行流程：**
```
写操作：更新DB → 删除Cache
读操作：查Cache → 未命中 → 查DB → 写入Cache
```

**为什么推荐这种方式？**
- 数据库是唯一真实数据源
- 删除缓存比更新缓存更安全（避免复杂的数据转换逻辑）
- 下次读取时自动从数据库加载最新数据

**潜在问题：**
```
时间线：
T1: 请求A更新DB成功（name = "新值"）
T2: 请求A尝试删除Cache，但失败了！
T3: 请求B读取Cache，拿到旧值（name = "旧值"）
结果：数据不一致
```

**解决方案：**
- 使用消息队列重试删除
- 记录删除失败的key，后台异步处理

---

### **2. 延迟双删策略**

**执行流程：**
```
1. 删除缓存（第一次）
2. 更新数据库
3. 等待 N 秒（比如500ms）
4. 再次删除缓存（第二次）
```

**解决的问题场景：**
```
不使用延迟双删时的问题：
T1: 请求A删除Cache
T2: 请求B查Cache未命中，去查DB（此时DB还是旧值）
T3: 请求A更新DB为新值
T4: 请求B把旧值写入Cache
结果：Cache是旧值，DB是新值

使用延迟双删：
T1: 请求A删除Cache（第一次）
T2: 请求B查Cache未命中，查DB写入Cache（旧值）
T3: 请求A更新DB
T4: 等待500ms（确保请求B完成）
T5: 请求A再次删除Cache（第二次，清除B写入的旧值）
结果：一致性得到保证
```

**延迟时间如何确定？**
- 需要大于一次读操作的时间（查DB + 写Cache）
- 通常设置为 **100-500ms**

**代码示例：**
```java
public void updateData(String key, Object newValue) {
    // 1. 第一次删除缓存
    cache.delete(key);
    
    // 2. 更新数据库
    db.update(key, newValue);
    
    // 3. 延迟删除
    Thread.sleep(500); // 或使用定时任务
    cache.delete(key);
}
```

### **3. 设置合理的过期时间**

**理念：** 允许短暂的不一致，通过过期时间自动修复

```
T1: Cache和DB不一致（Cache=旧值，DB=新值）
T2: ... 系统继续运行，用户可能读到旧值
T3: Cache过期（比如5分钟后）
T4: 下次读取时从DB加载新值
结果：不一致自动修复
```

**适用场景：**
- 对一致性要求不高的业务（比如商品浏览量、文章阅读数）
- 可以容忍短时间内的数据延迟

**过期时间设置建议：**
- 热点数据：5-30分钟
- 普通数据：1-24小时
- 根据业务容忍度调整

### **4. Binlog + MQ 异步更新（最终一致性）**

**架构流程：**
```
1. 应用更新数据库
2. MySQL产生binlog日志
3. Canal等工具监听binlog
4. 解析binlog变更内容
5. 发送消息到MQ（如Kafka）
6. 消费者接收消息
7. 更新/删除缓存
```

**优点：**
- 业务代码无侵入（不需要手动删除缓存）
- 可靠性高（MQ保证消息不丢失）
- 解耦业务逻辑和缓存更新

**实现示例（伪代码）：**
```java
// Canal监听器
public class CanalListener {
    @Subscribe
    public void onDatabaseChange(BinlogEvent event) {
        if (event.isUpdate() || event.isDelete()) {
            String tableName = event.getTableName();
            String key = generateCacheKey(tableName, event.getId());
            
            // 发送到MQ
            mqProducer.send(new CacheInvalidateMessage(key));
        }
    }
}

// MQ消费者
public class CacheInvalidateConsumer {
    @MessageListener
    public void handleMessage(CacheInvalidateMessage msg) {
        cache.delete(msg.getKey());
    }
}
```

## 实际应用建议

| 场景 | 推荐方案 |
|------|---------|
| **高一致性要求**（如订单、支付） | 先更新DB再删Cache + 重试机制 |
| **中等一致性要求**（如用户信息） | 延迟双删 |
| **低一致性要求**（如浏览量） | 过期时间策略 |
| **大型分布式系统** | Binlog + MQ |

**组合使用：**
```
先更新DB再删Cache（主策略）
+ 设置过期时间（兜底方案）
+ 延迟双删（增强一致性）
```

关键是根据业务对一致性的要求程度，选择合适的策略或组合！
