# Redisson Watch Dog 机制 - 完整面试题

## 一、基础问题

### Q1: 什么是 Redisson 的 Watch Dog 机制？

**参考答案：**

Watch Dog（看门狗）是 Redisson 分布式锁的自动续期机制。

**核心特点：**
- 默认锁过期时间：30 秒
- 续期检查间隔：10 秒（锁时间的 1/3）
- 工作原理：加锁成功后，启动后台守护线程，每隔 10 秒检查一次，如果客户端还持有锁，就将锁的过期时间重置为 30 秒

**解决的问题：**
避免业务逻辑执行时间超过锁的过期时间，导致锁被自动释放，破坏互斥性。

---

## 二、原理深入

### Q2: Watch Dog 的完整工作流程是什么？

**参考答案：**

```
1. 客户端调用 lock.lock()
   ↓
2. 获取锁成功（SET key value NX PX 30000）
   ↓
3. 启动 Watch Dog 后台线程（Netty 的 HashedWheelTimer）
   ↓
4. 每隔 10 秒执行一次续期任务
   ↓
5. 检查当前线程是否还持有锁
   ↓
6. 如果持有 → 执行 Lua 脚本延长过期时间到 30 秒
   ↓
7. 重复步骤 4-6，直到：
   - 锁被手动释放（unlock）
   - 客户端宕机（Watch Dog 停止）
   - 续期失败（网络故障等）
```

**续期的 Lua 脚本示例：**
```lua
if redis.call('hexists', KEYS[1], ARGV[2]) == 1 then
    redis.call('pexpire', KEYS[1], ARGV[1])
    return 1
end
return 0
```

---

### Q3: 为什么续期间隔是 10 秒，而不是其他值？

**参考答案：**

**设计原则：续期间隔 = 锁过期时间 / 3**

- 锁过期时间：30 秒
- 续期间隔：10 秒

**原因：**
1. **安全余量**：即使一次续期失败，还有 2 次机会（10s、20s、30s）
2. **网络容错**：给网络抖动、GC 停顿留出缓冲时间
3. **性能平衡**：太频繁浪费资源，太稀疏容易超时

**时间轴示例：**
```
0s   - 加锁成功，TTL=30s
10s  - 第1次续期，TTL=30s
20s  - 第2次续期，TTL=30s
30s  - 第3次续期，TTL=30s（如果还持有锁）
```

## 三、实战场景

### Q4: 如果业务代码中有无限循环，会发生什么？

**参考答案：**

```java
RLock lock = redisson.getLock("myLock");
lock.lock();  // Watch Dog 启动
try {
    while (true) {  // 无限循环 BUG
        // 业务逻辑
        Thread.sleep(1000);
    }
} finally {
    lock.unlock();  // 永远执行不到
}
```

**后果：**
1. ❌ Watch Dog 会无限续期
2. ❌ 锁永远不会释放
3. ❌ 其他客户端永远无法获取锁
4. ❌ **真正的死锁！**

**Redisson 的缺陷：**
- 没有最大续期次数限制
- 没有最大持锁时间限制

### Q5: 如何避免 Watch Dog 导致的死锁问题？

**参考答案：**

#### 方案 1：指定固定过期时间（不使用 Watch Dog）
```java
// 10 秒后强制释放，不会自动续期
lock.lock(10, TimeUnit.SECONDS);
try {
    // 业务逻辑（必须在 10 秒内完成）
} finally {
    lock.unlock();
}
```
- ✅ 优点：不会永久占锁
- ❌ 缺点：业务超过 10 秒会失去互斥性

#### 方案 2：tryLock 设置等待和持锁超时
```java
// 最多等待 100ms，最多持锁 30 秒
if (lock.tryLock(100, 30, TimeUnit.SECONDS)) {
    try {
        // 业务逻辑
    } finally {
        lock.unlock();
    }
} else {
    // 获取锁失败的降级处理
}
```

#### 方案 3：业务层超时控制（双保险）
```java
lock.lock();  // 使用 Watch Dog
try {
    ExecutorService executor = Executors.newSingleThreadExecutor();
    Future<?> future = executor.submit(() -> {
        // 业务逻辑
    });
    
    // 30 秒业务超时
    future.get(30, TimeUnit.SECONDS);
} catch (TimeoutException e) {
    log.error("Business timeout, force unlock!");
} finally {
    lock.unlock();
}
```

#### 方案 4：监控告警
```java
long startTime = System.currentTimeMillis();
lock.lock();
try {
    // 业务逻辑
} finally {
    long duration = System.currentTimeMillis() - startTime;
    if (duration > 30000) {
        // 发送告警：持锁时间过长
        alertService.send("Lock held too long: " + duration + "ms");
    }
    lock.unlock();
}
```

#### 方案 5：分段处理
```java
// 把大任务拆成小任务，每次持锁时间短
for (Batch batch : largeTask) {
    lock.lock(10, TimeUnit.SECONDS);
    try {
        processBatch(batch);  // 每批次 < 10 秒
    } finally {
        lock.unlock();
    }
}
```

### Q6: Watch Dog 和固定过期时间如何选择？

**参考答案：**

| 场景 | 推荐方案 | 过期时间设置 | 原因 |
|------|---------|------------|------|
| 快速操作（< 3秒） | 固定时间 | 10 秒 | 简单可控，不需要续期 |
| 数据库事务 | 固定时间 | 事务超时的 1.5 倍 | 对齐超时时间 |
| 文件上传/下载 | Watch Dog + 监控 | - | 时间不可预估 |
| 调用外部 API | 固定时间 | API 超时 + 5 秒 | 防止 API 超时后继续占锁 |
| 大批量处理 | 分批 + 固定时间 | 单批次时间 * 2 | 降低风险 |
| 定时任务 | 固定时间 | 任务周期的 50% | 防止任务重叠 |

**核心原则：**
- 业务时间可预估 → 固定时间（给 1.5-2 倍余量）
- 业务时间不可控 → Watch Dog + 监控告警
- 宁可任务失败重试，也不能永久占锁

## 四、底层实现

### Q7: Watch Dog 底层是如何实现的？

**参考答案：**

#### 1. 使用 Netty 的时间轮算法（HashedWheelTimer）
```java
// Redisson 内部实现（简化版）
private void scheduleExpirationRenewal(long threadId) {
    if (expirationRenewalMap.containsKey(getEntryName())) {
        return;
    }
    
    Timeout task = commandExecutor.getConnectionManager()
        .newTimeout(timeout -> {
            // 续期逻辑
            renewExpiration();
            
            // 递归调度下一次续期
            scheduleExpirationRenewal(threadId);
        }, internalLockLeaseTime / 3, TimeUnit.MILLISECONDS);
    
    expirationRenewalMap.put(getEntryName(), task);
}
```

#### 2. 续期的 Lua 脚本
```lua
-- 检查锁是否存在且属于当前客户端
if redis.call('hexists', KEYS[1], ARGV[2]) == 1 then
    -- 续期：重置过期时间
    redis.call('pexpire', KEYS[1], ARGV[1])
    return 1
end
return 0
```

#### 3. Watch Dog 生命周期管理
- **启动时机**：`lock.lock()` 成功后
- **停止时机**：
  - 调用 `unlock()` 时主动取消
  - 客户端进程退出时自动停止
  - 续期失败时停止

### Q8: 如果客户端宕机了，Watch Dog 如何处理？

**参考答案：**

**场景分析：**
```
0s   - 客户端 A 加锁成功，TTL=30s
10s  - 第1次续期成功，TTL=30s
15s  - 客户端 A 宕机 💥（Watch Dog 停止）
20s  - 无法续期（客户端已死）
30s  - 锁自动过期释放 ✅
31s  - 客户端 B 可以获取锁
```

**保护机制：**
1. **锁本身有过期时间**：即使 Watch Dog 失效，最多 30 秒后锁会自动释放
2. **Watch Dog 是守护线程**：JVM 退出时自动停止
3. **续期是主动行为**：客户端死了就无法续期

**对比：如果没有过期时间**
```
客户端 A 宕机 → 锁永远不释放 → 死锁 ❌
```

**这就是为什么 Redis 分布式锁必须设置过期时间！**

## 五、高级问题

### Q9: Watch Dog 机制在主从切换时会有什么问题？

**参考答案：**

**问题场景：**
```
1. 客户端 A 在 Master 上加锁成功
2. Watch Dog 每 10 秒续期
3. Master 宕机，数据未同步到 Slave
4. Slave 提升为新 Master（锁数据丢失）
5. 客户端 B 在新 Master 上加锁成功
6. 客户端 A 和 B 同时持有锁 ❌
```

**原因：**
- Redis 主从复制是**异步**的
- Master 写入成功后立即返回，不等待 Slave 确认
- 主从切换可能导致数据丢失

**解决方案：**

#### 1. 使用 RedLock（不推荐）
在多个独立的 Redis Master 上加锁，超过半数成功才算成功

#### 2. 使用 Redisson 的 RedLock
```java
RLock lock1 = redisson1.getLock("myLock");
RLock lock2 = redisson2.getLock("myLock");
RLock lock3 = redisson3.getLock("myLock");

RedissonRedLock redLock = new RedissonRedLock(lock1, lock2, lock3);
redLock.lock();
```

#### 3. 改用 ZooKeeper、etcd（推荐）
- 强一致性保证
- 不会出现双写问题

#### 4. 业务层幂等设计
即使出现短暂双写，业务逻辑也能正确处理

### Q10: Watch Dog 续期失败会怎样？

**参考答案：**

**续期失败的原因：**
1. 网络故障（客户端与 Redis 断开）
2. Redis 服务器宕机
3. Redis 命令执行超时
4. 锁已经被其他客户端占用（异常情况）

**失败后的行为：**
```java
// Redisson 内部逻辑
private void renewExpiration() {
    Timeout task = commandExecutor.getConnectionManager()
        .newTimeout(timeout -> {
            RFuture<Boolean> future = renewExpirationAsync(threadId);
            future.onComplete((res, e) -> {
                if (e != null) {
                    // 续期失败，不再重试
                    log.error("Can't update lock expiration", e);
                    return;
                }
                
                if (res) {
                    // 续期成功，调度下一次
                    renewExpiration();
                } else {
                    // 锁已经不属于当前客户端
                    cancelExpirationRenewal(threadId);
                }
            });
        }, internalLockLeaseTime / 3, TimeUnit.MILLISECONDS);
}
```

**结果：**
1. ❌ Watch Dog 停止续期
2. ⏰ 锁在剩余 TTL 后自动过期
3. ✅ 其他客户端可以获取锁

**最差情况：**
- 续期失败时锁还有 20 秒 TTL
- 业务逻辑还需要 30 秒才能完成
- 20 秒后锁被释放，其他客户端拿到锁
- **互斥性被破坏** ❌

**防护措施：**
```java
lock.lock();
try {
    // 业务执行前先检查锁是否还有效
    if (!lock.isLocked()) {
        throw new IllegalStateException("Lock lost!");
    }
    
    // 业务逻辑
    
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

## 六、对比分析

### Q11: Redisson Watch Dog vs 原生 Redis 实现有什么区别？

**参考答案：**

| 特性 | 原生 Redis 实现 | Redisson Watch Dog |
|------|----------------|-------------------|
| **加锁命令** | `SET key value NX PX 30000` | 相同 |
| **续期机制** | ❌ 无，30 秒后强制过期 | ✅ 每 10 秒自动续期 |
| **适用场景** | 快速操作（< 过期时间） | 长时间任务 |
| **死锁风险** | ✅ 低（30 秒必释放） | ⚠️ 中（代码 bug 可能永久占锁） |
| **实现复杂度** | 简单 | 复杂（需要后台线程） |
| **可重入性** | 需要手动实现 | ✅ 原生支持 |
| **公平锁** | 需要手动实现 | ✅ 原生支持 |

**原生 Redis 实现示例：**
```java
// 加锁
String result = jedis.set(
    "lock_key",           // key
    requestId,            // value（客户端唯一标识）
    "NX",                 // 不存在才设置
    "PX",                 // 毫秒级过期
    30000                 // 30 秒过期
);

// 释放锁（Lua 脚本保证原子性）
String script = 
    "if redis.call('get', KEYS[1]) == ARGV[1] then " +
    "    return redis.call('del', KEYS[1]) " +
    "else " +
    "    return 0 " +
    "end";
jedis.eval(script, Collections.singletonList("lock_key"), 
           Collections.singletonList(requestId));
```

## 七、综合实战

### Q12: 设计一个带 Watch Dog 的分布式锁工具类

**参考答案：**

```java
@Component
@Slf4j
public class DistributedLockService {
    
    @Autowired
    private RedissonClient redisson;
    
    /**
     * 执行带锁的业务逻辑（自动续期）
     */
    public <T> T executeWithLock(String lockKey, 
                                  Supplier<T> supplier) {
        RLock lock = redisson.getLock(lockKey);
        lock.lock();  // 使用 Watch Dog
        
        long startTime = System.currentTimeMillis();
        try {
            return supplier.get();
        } finally {
            long duration = System.currentTimeMillis() - startTime;
            
            // 监控持锁时间
            if (duration > 30000) {
                log.warn("Lock held too long: key={}, duration={}ms", 
                         lockKey, duration);
            }
            
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
    
    /**
     * 执行带锁的业务逻辑（固定过期时间）
     */
    public <T> T executeWithLock(String lockKey, 
                                  long leaseTime,
                                  TimeUnit unit,
                                  Supplier<T> supplier) {
        RLock lock = redisson.getLock(lockKey);
        lock.lock(leaseTime, unit);  // 不使用 Watch Dog
        
        try {
            return supplier.get();
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
    
    /**
     * 执行带锁的业务逻辑（带超时控制）
     */
    public <T> T executeWithLockAndTimeout(String lockKey,
                                           long waitTime,
                                           long leaseTime,
                                           TimeUnit unit,
                                           Supplier<T> supplier) 
            throws InterruptedException {
        RLock lock = redisson.getLock(lockKey);
        
        if (lock.tryLock(waitTime, leaseTime, unit)) {
            try {
                return supplier.get();
            } finally {
                if (lock.isHeldByCurrentThread()) {
                    lock.unlock();
                }
            }
        } else {
            throw new RuntimeException("Failed to acquire lock: " + lockKey);
        }
    }
    
    /**
     * 执行带锁的业务逻辑（双重超时保护）
     */
    public <T> T executeWithLockSafely(String lockKey,
                                       long businessTimeout,
                                       TimeUnit unit,
                                       Supplier<T> supplier) 
            throws Exception {
        RLock lock = redisson.getLock(lockKey);
        lock.lock();  // 使用 Watch Dog
        
        ExecutorService executor = Executors.newSingleThreadExecutor();
        try {
            Future<T> future = executor.submit(() -> supplier.get());
            
            // 业务层超时控制
            return future.get(businessTimeout, unit);
            
        } catch (TimeoutException e) {
            log.error("Business timeout: key={}, timeout={}{}",
                     lockKey, businessTimeout, unit);
            throw e;
        } finally {
            executor.shutdownNow();
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

**使用示例：**
```java
// 场景 1：快速操作，使用固定时间
lockService.executeWithLock("order:123", 10, TimeUnit.SECONDS, () -> {
    // 处理订单（< 10 秒）
    return processOrder();
});

// 场景 2：长时间任务，使用 Watch Dog
lockService.executeWithLock("batch:export", () -> {
    // 导出大文件（时间不确定）
    return exportLargeFile();
});

// 场景 3：关键任务，双重超时保护
lockService.executeWithLockSafely("payment:456", 30, TimeUnit.SECONDS, () -> {
    // 支付处理（最多 30 秒）
    return processPayment();
});
```

## 八、总结要点

### 核心知识点
1. ✅ Watch Dog 是自动续期机制，默认 30 秒过期，每 10 秒续期一次
2. ✅ 解决了业务执行时间 > 锁过期时间的问题
3. ⚠️ 可能因代码 bug（无限循环）导致永久占锁
4. ✅ 客户端宕机后，最多 30 秒锁会自动释放
5. ✅ 指定过期时间会禁用 Watch Dog

### 最佳实践
1. **快速操作**：使用固定过期时间，不需要 Watch Dog
2. **长时间任务**：使用 Watch Dog + 监控告警
3. **关键任务**：业务层加超时控制，双重保护
4. **大批量处理**：分段处理，每段用固定时间
5. **核心原则**：宁可任务失败重试，也不能永久占锁

### 常见误区
1. ❌ 认为 Watch Dog 会无限续期（实际上客户端死了就停止）
2. ❌ 认为指定时间就安全（实际上业务超时会失去互斥性）
3. ❌ 忘记在 finally 中释放锁
4. ❌ 没有考虑主从切换的数据丢失问题
5. ❌ 在锁内执行长时间阻塞操作（如网络 IO）
