# 缓存穿透

缓存空值、布隆过滤器、接口校验可以有效防止缓存穿透么？如果我用了大量的 数据库中没有的key 而且不是重复的, 上面的方案还有效果么？

## 场景示例：电商系统商品查询

假设我们有一个商品查询接口，数据库中商品ID范围是 1-10000。

### 攻击场景
恶意用户故意查询大量不存在的商品：
```
GET /product/99999
GET /product/88888
GET /product/77777
... (持续用不同的非法ID攻击)
```

---

## 方案1：缓存空值

### 实现示例
```java
public Product getProduct(Long productId) {
    String cacheKey = "product:" + productId;
    
    // 1. 查询Redis
    String cached = redis.get(cacheKey);
    if (cached != null) {
        if ("NULL".equals(cached)) {
            return null; // 缓存的空值
        }
        return JSON.parseObject(cached, Product.class);
    }
    
    // 2. 查询数据库
    Product product = productDao.selectById(productId);
    
    // 3. 缓存结果（包括空值）
    if (product != null) {
        redis.setex(cacheKey, 3600, JSON.toJSONString(product));
    } else {
        // 缓存空值，设置较短过期时间
        redis.setex(cacheKey, 30, "NULL");
    }
    
    return product;
}
```

### 效果分析

**面对重复攻击：**
```bash
# 第一次请求 ID=99999（不存在）
请求 → Redis未命中 → DB查询 → 缓存"NULL" 30秒

# 后续30秒内的相同请求
请求 → Redis命中"NULL" → 直接返回 ✅ 
# 数据库被保护了
```

**面对大量不重复攻击：❌ 基本无效**
```bash
# 攻击者每次用不同ID
GET /product/99999  → DB查询 + 缓存NULL
GET /product/88888  → DB查询 + 缓存NULL
GET /product/77777  → DB查询 + 缓存NULL
GET /product/66666  → DB查询 + 缓存NULL
... (每次都是新ID，每次都要查DB)

# 问题：
1. 每个新ID都要查询一次数据库
2. Redis会被大量无效key占满内存
3. 如果攻击者1分钟请求1000个不同ID，就会产生1000次数据库查询
```

**内存占用问题：**
```bash
# 假设攻击者10分钟内用了10万个不同ID
# 每个空值占用约 50 字节
10万 × 50字节 = 5MB

# 如果持续攻击，Redis会被垃圾数据填满
```

## 方案2：布隆过滤器 ⭐

### 实现示例
```java
public class ProductService {
    // 布隆过滤器，预计10000个商品，误判率0.01
    private BloomFilter<Long> bloomFilter = 
        BloomFilter.create(Funnels.longFunnel(), 10000, 0.01);
    
    @PostConstruct
    public void init() {
        // 启动时将所有商品ID加载到布隆过滤器
        List<Long> allProductIds = productDao.getAllProductIds();
        for (Long id : allProductIds) {
            bloomFilter.put(id);
        }
    }
    
    public Product getProduct(Long productId) {
        // 1. 布隆过滤器快速判断（纳秒级）
        if (!bloomFilter.mightContain(productId)) {
            // 一定不存在，直接返回
            return null; ✅
        }
        
        // 2. 可能存在，查询缓存
        String cacheKey = "product:" + productId;
        String cached = redis.get(cacheKey);
        if (cached != null) {
            return JSON.parseObject(cached, Product.class);
        }
        
        // 3. 查询数据库
        Product product = productDao.selectById(productId);
        if (product != null) {
            redis.setex(cacheKey, 3600, JSON.toJSONString(product));
        }
        
        return product;
    }
}
```

### 效果分析

**面对大量不重复攻击：✅ 非常有效**
```bash
# 攻击者用不同的非法ID
GET /product/99999  → 布隆过滤器判断：不存在 → 直接返回 ✅
GET /product/88888  → 布隆过滤器判断：不存在 → 直接返回 ✅
GET /product/77777  → 布隆过滤器判断：不存在 → 直接返回 ✅

# 100万次攻击，只需要100万次内存判断（微秒级）
# 数据库查询次数：0 ✅✅✅
```

**性能对比：**
```
无防护：      100万次请求 → 100万次DB查询（系统崩溃）
缓存空值：    100万次请求 → 100万次DB查询（第一次）+ 缓存占用
布隆过滤器：  100万次请求 → 0次DB查询 ✅
```

**误判问题：**
```java
// 布隆过滤器可能误判"存在"（但不会误判"不存在"）
GET /product/12345（实际不存在，但布隆过滤器误判为存在）
→ 查询Redis未命中
→ 查询DB（发现真的不存在）
→ 缓存空值

// 误判率0.01，意味着10000次查询中，约100次会误判
// 这100次会打到DB，但相比无防护的100%，已经降低99%
```

**内存占用：**
```
10000个商品，误判率0.01的布隆过滤器：
约 14KB 内存 ✅ （远小于缓存空值的5MB）
```

## 方案3：接口校验

### 实现示例
```java
@RestController
public class ProductController {
    
    @GetMapping("/product/{id}")
    public Result getProduct(@PathVariable Long id) {
        // 1. 参数校验
        if (id == null || id <= 0) {
            return Result.error("商品ID非法");
        }
        
        // 2. 范围校验（如果知道合法范围）
        if (id > 100000) { // 假设最大ID是10万
            return Result.error("商品不存在");
        }
        
        // 3. 格式校验
        String idStr = String.valueOf(id);
        if (!idStr.matches("^[1-9]\\d{0,5}$")) { // 1-6位数字
            return Result.error("商品ID格式错误");
        }
        
        // 4. 频率限制（限流）
        String clientIp = getClientIp();
        if (!rateLimiter.tryAcquire(clientIp)) {
            return Result.error("请求过于频繁");
        }
        
        // 通过校验后才查询
        Product product = productService.getProduct(id);
        return Result.success(product);
    }
}
```

### 效果分析

**面对大量不重复攻击：⚠️ 部分有效**
```bash
# 可以拦截明显非法的请求
GET /product/-1      → 参数校验拦截 ✅
GET /product/0       → 参数校验拦截 ✅
GET /product/9999999 → 范围校验拦截 ✅

# 但无法拦截"看起来合法"的请求
GET /product/50001   → 校验通过 → 查询DB ❌
GET /product/50002   → 校验通过 → 查询DB ❌
GET /product/50003   → 校验通过 → 查询DB ❌
# 如果合法范围是1-100000，攻击者可以用这个范围内的任意不存在ID
```

**配合限流：**
```java
// 使用 Guava RateLimiter 或 Redis 限流
@Autowired
private RedisTemplate redisTemplate;

public boolean checkRateLimit(String clientIp) {
    String key = "rate_limit:" + clientIp;
    Long count = redisTemplate.opsForValue().increment(key, 1);
    
    if (count == 1) {
        redisTemplate.expire(key, 1, TimeUnit.SECONDS);
    }
    
    // 每秒最多10次请求
    return count <= 10;
}
```

## 最佳实践：组合方案

```java
@RestController
public class ProductController {
    @Autowired
    private BloomFilter<Long> bloomFilter;
    @Autowired
    private ProductService productService;
    @Autowired
    private RateLimiter rateLimiter;
    
    @GetMapping("/product/{id}")
    public Result getProduct(@PathVariable Long id, HttpServletRequest request) {
        // 第一层：接口校验（拦截明显非法请求）
        if (id == null || id <= 0 || id > 100000) {
            log.warn("非法请求: id={}", id);
            return Result.error("商品ID非法");
        }
        
        // 第二层：限流（防止恶意高频攻击）
        String clientIp = getClientIp(request);
        if (!rateLimiter.tryAcquire(clientIp)) {
            return Result.error("请求过于频繁");
        }
        
        // 第三层：布隆过滤器（快速判断是否存在）
        if (!bloomFilter.mightContain(id)) {
            log.info("布隆过滤器拦截: id={}", id);
            return Result.success(null); // 一定不存在
        }
        
        // 第四层：缓存 + 数据库
        Product product = productService.getProduct(id); // 内部处理缓存空值
        
        return Result.success(product);
    }
}
```

### 防御效果

```bash
# 10万次不重复攻击的处理流程

60,000次明显非法请求（如负数、超大数）
  → 接口校验拦截 ✅ 数据库查询：0次

30,000次看似合法但不存在的ID
  → 通过接口校验
  → 布隆过滤器拦截 ✅ 数据库查询：0次

10,000次合法范围内但不存在的ID（布隆过滤器误判）
  → 通过接口校验
  → 布隆过滤器误判为"可能存在"
  → 查询缓存未命中
  → 查询数据库（发现不存在）
  → 缓存空值 30秒
  ⚠️ 数据库查询：10,000次

其中5,000次是同一个IP的重复攻击
  → 限流拦截 ✅ 实际查询：5,000次

---
最终结果：10万次攻击，仅5,000次打到数据库
防护率：95% ✅✅✅
```

## 总结

### 单独使用各方案面对大量不重复攻击

1. **缓存空值**：❌ **几乎无效**
   - 每个新ID都要查DB
   - 内存被垃圾数据占满

2. **布隆过滤器**：✅ **非常有效**
   - 99%+的请求被拦截
   - 内存占用极小
   - **但有误判，需要配合缓存空值处理误判情况**

3. **接口校验**：⚠️ **部分有效**
   - 能拦截明显非法请求
   - 无法拦截"合法范围内的非法ID"
   - 需要明确知道合法范围

### 推荐方案

```
高价值系统（如交易、支付）：
布隆过滤器 + 接口校验 + 限流 + 缓存空值（处理误判）

一般系统：
布隆过滤器 + 接口校验 + 限流

低价值系统：
接口校验 + 限流 + 缓存空值
```
