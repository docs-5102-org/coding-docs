# Redis 面试题精编1

## 基础概念

### 1. Redis 是什么？主要应用场景有哪些？

Redis（Remote Dictionary Server）是一个使用 C 语言开发的开源、高性能的内存数据库，支持多种数据结构。

**典型应用场景：**
- 缓存热点数据（文章详情、商品信息等）
- 计数器（点赞数、浏览量、评论数）
- 会话管理（用户登录状态）
- 排行榜系统
- 分布式锁
- 消息队列

### 2. Redis 核心功能有哪些？

- **数据缓存**：提供高速数据访问
- **分布式锁**：实现分布式系统的资源同步
- **持久化**：支持 RDB 和 AOF 两种持久化方式
- **事务支持**：提供基本的事务功能
- **发布订阅**：支持消息队列模式

### 3. Redis 与 Memcached 的区别？

| 对比维度 | Redis | Memcached |
|---------|-------|-----------|
| 数据类型 | 支持 String、List、Hash、Set、Sorted Set | 仅支持简单的 key-value |
| 持久化 | 支持 RDB 和 AOF | 不支持，数据仅存内存 |
| 数据大小 | 单个 value 最大 512MB | 单个 value 最大 1MB |
| 性能 | 更快，自建 VM 机制 | 较快 |
| 线程模型 | 单线程（6.0后支持多线程I/O） | 多线程 |


### 4. Redis 为什么叫做单线程模型？

#### 1. 单线程模型的定义

Redis 被称为单线程模型，是因为其核心的**文件事件处理器（File Event Handler）是单线程的**。这意味着 Redis 在处理客户端请求时，所有的命令执行都在一个线程中按顺序完成。

#### 2. 文件事件处理器的结构

Redis 的文件事件处理器包含 4 个核心部分：

1. **多个 Socket**：与多个客户端建立连接
2. **IO 多路复用程序**：同时监听多个 Socket，使用 select/epoll/kqueue 等机制
3. **文件事件分派器**：将 Socket 产生的事件分派给对应的处理器
4. **事件处理器**：
   - 连接应答处理器：处理客户端连接请求
   - 命令请求处理器：处理客户端发送的命令
   - 命令回复处理器：将结果返回给客户端

##### 请求处理完整流程图

```
客户端1  客户端2  客户端3
   |       |       |
   v       v       v
[Socket1][Socket2][Socket3]  ← 多个 Socket
   |       |       |
   +-------+-------+
           |
           v
   ┌───────────────────┐
   │  IO多路复用程序    │  ← 使用 select/epoll/kqueue 监听
   │  (epoll_wait)    │
   └───────────────────┘
           |
           v
   ┌───────────────────┐
   │    事件队列        │  ← Socket产生的事件排队
   │  [事件1][事件2]   │     (先进先出)
   │  [事件3][事件4]   │
   └───────────────────┘
           |
           v (单线程逐个取出)
   ┌───────────────────┐
   │  文件事件分派器    │  ← 从队列取出事件并分派
   └───────────────────┘
           |
           +------------------+------------------+
           |                  |                  |
           v                  v                  v
   ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
   │ 连接应答处理器 │  │ 命令请求处理器 │  │ 命令回复处理器 │
   │ (accept)     │  │ (execute)    │  │ (reply)      │
   └──────────────┘  └──────────────┘  └──────────────┘
           |                  |                  |
           v                  v                  v
      建立连接          执行 SET/GET        返回结果
```

##### 具体执行示例

```
时间线：单线程顺序处理

t1: 客户端1发送连接请求
    → IO多路复用检测到Socket1可读
    → 事件入队列 [连接事件1]
    → 分派器取出 → 连接应答处理器 → 建立连接

t2: 客户端1发送命令 "SET key value"
    → IO多路复用检测到Socket1可读
    → 事件入队列 [命令事件1]
    → 分派器取出 → 命令请求处理器 → 执行SET命令

t3: 返回结果给客户端1
    → 事件入队列 [回复事件1]
    → 分派器取出 → 命令回复处理器 → 发送"OK"

t4: 客户端2发送命令 "GET key"
    → IO多路复用检测到Socket2可读
    → 事件入队列 [命令事件2]
    → 分派器取出 → 命令请求处理器 → 执行GET命令

注意：所有事件都在一个线程中串行执行，不会并发处理
```

#### 3. 工作流程

1. 多个 Socket 可能并发产生不同的操作和事件
2. IO 多路复用程序监听所有 Socket，将产生的事件放入**队列**中排队
3. 文件事件分派器从队列中**依次取出**一个事件
4. 将事件交给对应的事件处理器进行处理
5. 处理完成后继续处理下一个事件

这种串行化的事件处理方式，就是 Redis 单线程模型的体现。

#### 4. 为什么采用单线程模型？

**核心原因：**

- **性能瓶颈不在 CPU**：Redis 的瓶颈通常是内存大小和网络带宽，而不是 CPU 处理能力
- **避免并发问题**：单线程避免了线程切换和锁竞争的开销，不需要考虑线程安全问题
- **简化实现**：代码逻辑更简单，更容易维护和调试
- **高效的数据结构**：Redis 使用了高效的内存数据结构，单线程也能达到很高的性能

**实际性能数据：**
- 读操作：约 110,000 次/秒
- 写操作：约 81,000 次/秒

#### 5. 重要补充

**Redis 6.0 的多线程改进：**

Redis 6.0 版本引入了多线程 I/O 功能，但需要注意：
- 多线程只用于处理网络 I/O（读取请求、发送响应）
- **核心的命令执行仍然是单线程**
- 这样既提高了网络 I/O 的吞吐量，又保持了命令执行的简单性

#### 6. 总结

Redis 的单线程模型通过 IO 多路复用技术和高效的事件处理机制，在保持简单性的同时实现了高性能。虽然是单线程，但通过避免锁竞争和线程切换的开销，配合优秀的数据结构设计，Redis 依然能够满足大多数高并发场景的需求。

## 数据类型与应用

### 5. Redis 支持哪些数据类型？各有什么应用场景？

#### String（字符串）
**常用命令：** SET、GET、INCR、DECR、MGET

**应用场景：**
- 缓存对象（JSON 序列化）
- 计数器（播放量、点赞数）
- 分布式锁
- Session 共享

#### Hash（哈希表）
**常用命令：** HSET、HGET、HMGET、HGETALL

**应用场景：**
- 存储对象信息（用户信息、商品详情）
- 购物车数据

**示例：**
```
key = user:1001
value = {
  "id": 1001,
  "name": "张三",
  "age": 25,
  "city": "北京"
}
```

#### List（列表）
**常用命令：** LPUSH、RPUSH、LPOP、RPOP、LRANGE

**应用场景：**
- 消息队列
- 最新动态列表
- 关注/粉丝列表
- 简单的分页功能

#### Set（集合）
**常用命令：** SADD、SPOP、SMEMBERS、SINTER、SUNION

**应用场景：**
- 标签系统（用户标签、文章标签）
- 共同好友、共同关注
- 抽奖系统（随机抽取）
- 去重场景

#### Sorted Set（有序集合）
**常用命令：** ZADD、ZRANGE、ZREM、ZCARD、ZRANK

**应用场景：**
- 排行榜系统（游戏积分、热度排名）
- 延迟队列（按时间排序）
- 优先级队列

## 缓存问题与解决方案

### 6. 什么是缓存穿透？如何解决？

**定义：** 查询一个数据库中不存在的数据，由于缓存未命中，每次请求都会打到数据库。

**解决方案：**
1. **缓存空值**：将查询结果为空的 key 也缓存起来，设置较短的过期时间（如 30 秒）
2. **布隆过滤器**：在缓存前加一层布隆过滤器，快速判断数据是否存在
3. **接口校验**：对请求参数进行合法性校验，拦截非法请求

更详细的说明：

- [缓存穿透](./缓存穿透.md)
- [布隆过滤器](../../article/布隆过滤器.md)
 
### 7. 什么是缓存击穿？如何解决？

**定义：** 热点 key 在过期瞬间，大量并发请求同时访问，导致请求直接打到数据库。

**解决方案：**
1. **互斥锁**：使用 SETNX 实现分布式锁，只允许一个线程查询数据库并重建缓存
2. **热点数据永不过期**：设置逻辑过期时间，后台异步更新
3. **预热**：提前将热点数据加载到缓存

:::tip
- [互斥锁详解](./互斥锁.md)
- [热点数据永不过期 - Java实现](../../article/热点数据永不过期%20-%20Java实现.md)
:::

#### 什么是缓存预热?

缓存预热就是系统上线后，提前将相关的缓存数据直接加载到缓存系统。避免在用户请求的时候，先查询数据库，然后再将数据缓存的问题！用户直接查询事先被预热的缓存数据！

缓存预热解决方案：

- 直接写个缓存刷新页面，上线时手工操作下；
- 数据量不大，可以在项目启动的时候自动进行加载；
- 定时刷新缓存；

#### 什么是缓存降级?

缓存降级是**服务降级的一种具体实现方式**,指的是当系统面临高负载、服务异常或性能问题时,通过优先使用缓存数据(即使可能不是最新数据)来保证核心服务可用性的策略。

##### 缓存降级的核心思想

在正常情况下,系统会实时查询数据库或调用服务获取最新数据;但在降级场景下,系统会:
- **直接返回缓存中的数据**,跳过实时查询
- **延长缓存过期时间**,减少对后端服务的访问
- **使用静态数据或兜底数据**,确保服务不中断

##### 常见的缓存降级场景

**1. 数据库压力过大**
- 当数据库连接池耗尽或查询响应缓慢时,直接返回缓存数据
- 例如:商品详情页在促销时段,即使库存略有延迟也优先展示缓存的商品信息

**2. 下游服务不可用**
- 当依赖的第三方服务或微服务不响应时,返回缓存的历史数据
- 例如:推荐系统故障时,展示用户上次浏览的缓存推荐列表

**3. 流量突增**
- 在秒杀、热点事件等场景下,大部分请求直接走缓存
- 例如:明星新闻页面突然爆火,所有用户看到的都是缓存版本

**4. 非核心功能降级**
- 将非关键功能切换为缓存模式,保证核心流程
- 例如:电商结算时,用户评价、商品推荐等使用缓存,确保支付流程顺畅

##### 缓存降级 vs 服务降级

- **服务降级**:更广泛的概念,包括关闭功能、简化流程、返回默认值等多种手段
- **缓存降级**:服务降级的一个子集,特指通过使用缓存数据来实现降级

本质上, 缓存降级是在系统可用性和数据实时性之间做出的取舍——宁可数据稍旧,也要保证服务不挂。

### 8. 什么是缓存雪崩？如何解决？

**定义：** 大量缓存在同一时间失效，或缓存服务器宕机，导致所有请求打到数据库。

**解决方案：**
1. **过期时间打散**：给每个 key 的过期时间加上随机值，避免集中失效
2. **多级缓存**：设置二级缓存（本地缓存 + Redis）
3. **限流降级**：使用令牌桶或漏桶算法限制数据库访问量
4. **Redis 集群**：提高缓存服务的可用性

### 9. 如何保证缓存与数据库的一致性？

**常用策略：**
1. **先更新数据库，再删除缓存**（推荐）
   - 优点：实现简单，一致性较好
   - 缺点：删除失败会导致不一致

2. **延迟双删**
   ```
   删除缓存 → 更新数据库 → 延迟N秒 → 再次删除缓存
   ```
   > [延迟双删详解](延迟双删.md)
3. **设置合理的过期时间**：即使出现不一致，也会在过期后自动修复

4. **binlog + MQ 异步更新**：通过监听数据库变更，异步更新缓存

## 持久化机制

### 10. Redis 的持久化方式有哪些？

#### RDB（Redis Database）

在指定时间间隔内，生成内存数据的完整二进制快照并保存到磁盘（默认文件名 `dump.rdb`）。底层利用操作系统的 **COW（Copy-On-Write，写时复制）** 机制保证快照数据一致性。

---

##### 触发方式

**1. 配置自动触发**
```
save 900 1     # 900 秒内至少 1 次写操作
save 300 10    # 300 秒内至少 10 次写操作
save 60 10000  # 60 秒内至少 10000 次写操作
```
满足任意一条即触发 `BGSAVE`。

**2. 手动触发**
- `SAVE` — 阻塞主线程，期间无法处理任何请求，生产环境慎用
- `BGSAVE` — fork 子进程在后台执行，主线程继续处理请求

**3. 关闭服务器时自动触发**
执行 `SHUTDOWN` 且**未开启 AOF** 时自动触发，若已开启 AOF 则优先使用 AOF 持久化。

**4. 主从复制时自动触发**
从节点首次连接主节点进行全量同步时，主节点自动执行 `BGSAVE` 生成 RDB 文件传输给从节点。

---

##### 执行流程（BGSAVE）

```
主进程
  │
  ├─ fork() ──────────────────► 子进程
  │    │                           │
  │    │ (fork瞬间主线程短暂阻塞)    │ 遍历内存数据
  │    │                           │ 写入临时 RDB 文件
  │ 继续处理请求                    │
  │    │                           │ 完成后替换旧 RDB 文件
  │    │◄──────────── 通知父进程完成─┘
  │
```

> ⚠️ fork 本身会造成**毫秒到秒级的主线程阻塞**，数据量越大阻塞越长，这是 BGSAVE 唯一阻塞主线程的阶段。

---

##### 优点

| 优点 | 说明 |
|------|------|
| 恢复速度快 | 直接加载二进制文件，比 AOF 重放日志快得多 |
| 文件紧凑 | 二进制压缩格式，适合定期备份和异地容灾 |
| 性能影响小 | fork 子进程处理，主线程几乎不受影响 |
| 适合大规模恢复 | 全量快照，适合数据量大的灾难恢复场景 |

---

##### 缺点

| 缺点 | 说明 |
|------|------|
| 数据丢失风险 | 最多丢失上次快照到宕机之间的所有写入（按 `save 900 1` 配置最长可丢失 **15 分钟**数据） |
| fork 阻塞问题 | 数据量大时 fork 耗时较长，可能引起服务短暂卡顿 |
| 不适合高频持久化 | 频繁触发快照开销大，不适合对数据丢失零容忍的场景 |

---

##### 相关配置

```bash
# 快照文件名
dbfilename dump.rdb

# 快照保存目录
dir /var/lib/redis

# 开启/关闭 RDB 压缩（默认开启，节省磁盘但消耗 CPU）
rdbcompression yes

# RDB 文件校验（默认开启，加载时校验完整性）
rdbchecksum yes

# 禁用 RDB（不推荐，除非完全依赖 AOF）
save ""
```

---

##### 与 AOF 对比一句话总结

> RDB 适合**容忍少量数据丢失、追求快速恢复**的场景；AOF 适合**对数据完整性要求高**的场景；生产环境通常**两者同时开启**，优先用 AOF 恢复，RDB 作为备份兜底。


#### AOF（Append Only File）
**特点：** 记录每一条写命令，恢复时重新执行所有命令。

**开启AOF** 配置文件中设置 `appendonly yes`

**同步策略：**
- `always`：每条命令都同步，最安全但性能差
- `everysec`：每秒同步一次（推荐）
- `no`：由操作系统决定，性能好但可能丢失较多数据不会被持久化

**优点：**
- 数据完整性更好
- AOF 文件可读，便于分析和修复

**缺点：**
- 文件体积大
- 恢复速度慢

**修复AOF文件方法：**

1. 将现有已经坏损的AOF文件额外拷贝出来一份。
2. 执行`redis-check-aof --fix <filename>`命令来修复坏损的AOF文件。
3. 用修复后的AOF文件重新启动Redis服务器。

#### 如何选择？
- **仅做缓存**：可以不使用持久化
- **要求高可用**：RDB + AOF 同时开启
- **主从架构**：主节点关闭持久化或仅 AOF，从节点使用 RDB 备份

## 集群与高可用

### 11. Redis 集群如何实现？

#### 哈希槽（Hash Slot）
- Redis 集群使用 16384 个哈希槽
- 每个 key 通过 CRC16 校验后对 16384 取模，确定所属槽位 `slot = CRC16(key) % 16384`
- 每个节点负责一部分槽位

**示例：**
```
节点A：负责 0-5460 槽
节点B：负责 5461-10922 槽
节点C：负责 10923-16383 槽
```

#### Redis Cluster 支持 哈希标签，如果 key 中含有 {...}，例如：

```
user:{1001}:profile
user:{1001}:friends
```

实际用于计算槽位的部分为 {1001}，因此这两个 key 会落在 相同槽位，从而可以在同一节点实现跨 key 操作（如 Lua、事务、MSET/MGET）。

#### Redis 集群如何选择数据库？每个节点的 database index 是否必须一致？

必须一致，而且必须全部是 DB 0。
Redis 集群目前无法做数据库选择，默认在 0 数据库。


#### **槽位定位和 key 的路由是由主节点(master)负责的么？**。

##### 主节点的职责

- **槽位分配**：每个主节点负责 16384 个槽位中的一部分
- **Key 路由**：根据 `CRC16(key) % 16384` 计算出槽位，然后找到负责该槽位的主节点
- **读写操作**：默认情况下，所有的读写请求都由主节点处理

##### 从节点的职责

- **数据复制**：从节点复制主节点的数据，作为备份
- **故障转移**：当主节点宕机时，从节点可以被提升为主节点
- **只读查询**（可选）：在配置了 `READONLY` 命令后，从节点可以处理读请求，但这不是默认行为

##### 实际路由过程

当客户端发送请求时：

1. 客户端计算 key 的槽位
2. 如果请求发到了错误的节点，该节点会返回 `MOVED` 重定向，告诉客户端正确的主节点地址
3. 客户端重新向正确的主节点发送请求

**总结**：槽位定位和 key 路由的责任在**主节点**，从节点主要用于高可用和故障恢复。


#### 应用层访问哪个节点？

**默认情况下，应用层操作的是主节点**，包括读和写操作。

##### **场景1：默认模式（推荐）**

```
应用 → 主节点B → 读写操作
       ↓
     从节点B1, B2（仅做数据备份）
```

##### **场景2：读写分离模式（需要主动开启）**
如果你想让从节点处理读请求，需要：

```redis
# 客户端连接到从节点后执行
READONLY
```

此时的架构：
```
应用 → 主节点B → 写操作
应用 → 从节点B1 → 读操作（执行 READONLY 后）
```

##### 注意事项

**为什么默认不用从节点读？**
- **数据一致性**：主从复制是异步的，从节点数据可能有延迟
- **简单性**：直接访问主节点，逻辑更简单

**什么时候考虑从节点读？**
- 读请求量特别大
- 能容忍轻微的数据延迟
- 需要降低主节点压力

**总结**：应用层默认操作**主节点**（读+写），从节点主要是**备份和高可用**，不是用来分担读压力的（除非你明确配置）。

### 12. Redis 集群的主从复制模型？

- 每个主节点可以有多个从节点
- 采用**异步复制**机制
- 主节点故障时，从节点自动提升为主节点
- 集群中超过半数主节点故障时，整个集群不可用

> [选举机制](./主从选举机制.md)

### 13. Redis 会丢失数据吗？

**会，原因包括：**
- 异步复制存在延迟，主节点故障时未同步的数据会丢失
- AOF 使用 `everysec` 策略时，最多丢失 1 秒数据
- 网络分区可能导致数据不一致

**Redis 不保证强一致性**，适合对一致性要求不高的场景。

## 内存管理

### 14. Redis 的内存淘汰策略有哪些？

| 策略 | 说明 |
|-----|------|
| **noeviction** | 不淘汰，内存满时写入失败（默认） |
| **allkeys-lru** | 从所有 key 中淘汰最少使用的 |
| **allkeys-lfu** | 从所有 key 中淘汰访问频率最低的 |
| **allkeys-random** | 从所有 key 中随机淘汰 |
| **volatile-lru** | 从设置了过期时间的 key 中淘汰最少使用的 |
| **volatile-lfu** | 从设置了过期时间的 key 中淘汰访问频率最低的 |
| **volatile-random** | 从设置了过期时间的 key 中随机淘汰 |
| **volatile-ttl** | 淘汰即将过期的 key |

**推荐配置：** `allkeys-lru`，适合大多数缓存场景。

### 15. 如何保证 Redis 中都是热点数据？

**场景：** MySQL 有 2000 万数据，Redis 只能存 20 万。

**解决方案：**
1. 设置合理的内存淘汰策略（如 `allkeys-lru`）
2. 设置 `maxmemory` 限制内存使用
3. 监控热点数据访问频率，主动预热

### 16. Redis 内存优化建议？

- **使用 Hash 存储对象**：相比多个 String key，可节省内存
- **控制 key 的长度**：使用简短有意义的 key
- **设置合理的过期时间**：及时清理无用数据
- **使用压缩**：对大 value 进行压缩存储
- **避免大 key**：单个 key 不要存储过大的数据

## 高级特性

### 17. Redis 事务是什么？

**特点：**
- 所有命令按顺序执行，不会被其他客户端打断
- 不支持回滚（与 MySQL 不同）
- 语法错误会导致整个事务失败，运行时错误只跳过错误命令

**命令：**
```
MULTI      # 开启事务
...        # 执行命令（加入队列）
EXEC       # 提交事务
DISCARD    # 取消事务
```

**与 MySQL 事务的区别：**
- MySQL 支持 `ROLLBACK` 回滚，Redis 不支持
- Redis 事务更轻量，但功能较弱
- Redis 使用 `DISCARD` 只能清空命令队列，不会回滚已执行的命令

### 18. Redis 管道（Pipeline）是什么？

**定义：** 将多个命令打包一次性发送到服务器，减少网络往返次数。

**优势：**
- 显著提高性能（减少 RTT）
- 适合批量操作场景

**注意：** 管道中的命令不是原子性的，不要依赖前一个命令的结果。

### 19. 如何使用 Redis 做消息队列？

#### 方案一：List 结构

```
# 生产者
RPUSH queue_name message

# 消费者
BLPOP queue_name 0  # 阻塞等待
```

##### 消息什么时候会丢失？

关键在于 `BLPOP` 的行为：

```
List 中的消息
      │
      │ BLPOP 取出
      ▼
  消费者内存
      │
      │ 处理中... 此时宕机 💥
      ▼
    消息消失
```

**`BLPOP` 是"取出即删除"的操作。**

消息一旦被 `BLPOP` 弹出，就从 List 里永久移除了。如果消费者在**取出消息之后、处理完成之前**崩溃，这条消息就丢了——既不在 Redis 里，也没有被成功处理。

---

##### 消费者"下线"要分两种情况

| 情况 | 消息是否丢失 |
|------|------------|
| 消费者下线，**还没有 BLPOP 取走消息** | ❌ 不丢失，消息仍在 List 中等待 |
| 消费者 **BLPOP 取出后**，处理途中崩溃 | ✅ **丢失**，消息已从 List 删除 |

所以原文说"消费者下线时消息会丢失"，准确说法应该是：

> **消息被取出但未处理完成时消费者崩溃，会导致消息丢失。**

---

##### 根本原因

List 方案没有 **ACK 机制**（确认机制）。

消息队列的可靠消费通常需要：
1. 取出消息
2. 处理消息
3. **确认消费成功（ACK）→ 才真正删除**

List 的 `BLPOP` 把第 1 步和第 3 步合并了，取出即删除，没有"处理中"的中间状态。

---

##### 如何解决？

用 `BRPOPLPUSH` 或 `LMOVE`（Redis 6.2+）配合一个**备份队列**：

```bash
# 取出消息的同时，备份到 processing 队列
BRPOPLPUSH queue_name processing_queue 0

# 处理成功后，手动从备份队列删除（相当于 ACK）
LREM processing_queue 1 message
```

这样消费者崩溃后，消息还在 `processing_queue` 里，可以恢复重试。

不过这个方案实现较复杂，如果业务对消息可靠性要求高，通常直接换用 **Redis Stream** 或专业 MQ（Kafka、RabbitMQ）。

#### 方案二：Pub/Sub 发布订阅
```
# 订阅
SUBSCRIBE channel_name

# 发布
PUBLISH channel_name message
```

**缺点：** 不支持消息持久化，订阅者离线时会丢失消息。

#### 方案三：Stream（Redis 5.0+）
**推荐使用**，支持消息持久化、消费者组、消息确认等特性，更适合作为消息队列。

**建议：** 生产环境建议使用专业消息队列（RabbitMQ、Kafka）。

### 20. 如何实现 Redis 分布式锁？

**基本实现：**
```
# 加锁
SET lock_key unique_value NX PX 30000

# 解锁（使用 Lua 脚本保证原子性）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**关键点：**
- 使用 `NX`（不存在才设置）保证互斥
- 设置过期时间防止死锁
- 使用唯一值（UUID）防止误删他人的锁
- 使用 Lua 脚本保证解锁的原子性

**更可靠方案：** 使用 Redlock 算法或 Redisson 框架。

## 性能优化

### 21. Redis 常见性能问题及解决方案？

| 问题 | 解决方案 |
|-----|---------|
| 主库执行 RDB 阻塞 | 不在主库执行 RDB，由从库负责持久化 |
| 主从复制延迟 | 主从部署在同一局域网，减少网络延迟 |
| 慢查询 | 避免使用 KEYS、SMEMBERS 等全量操作 |
| 大 key 操作 | 拆分大 key，使用 SCAN 代替 KEYS |
| 内存碎片 | 重启 Redis 或使用 `MEMORY PURGE` |

### 22. Redis Key 设计最佳实践？

- **使用冒号分隔**：`user:1001:profile`
- **避免过长**：控制在 50 字符以内
- **包含业务含义**：便于理解和维护
- **设置过期时间**：避免无用数据堆积
- **统一命名规范**：制定团队统一的命名标准
