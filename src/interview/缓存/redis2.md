# Redis 缓存面试集锦2

## 什么是 定期删除和 惰性删除？使用场景是什么？

Redis 对过期键的删除采用了**定期删除**和**惰性删除**两种策略的组合，以平衡内存占用和 CPU 消耗。

---

### 1. 惰性删除（Lazy Expiration）

#### 概念
**被动触发**的删除策略，只有在访问某个 Key 时，才检查其是否过期，如果过期则删除。

#### 工作原理
```
客户端访问 Key → Redis 检查是否过期 → 已过期则删除并返回 nil → 未过期则正常返回
```

#### 代码示例
```bash
# 设置 Key 并设置 5 秒过期
SET mykey "hello" EX 5

# 5 秒内访问，正常返回
GET mykey  # "hello"

# 等待 6 秒后访问，触发惰性删除
GET mykey  # (nil)
# 此时 Redis 才真正删除这个 Key
```

#### 优点
- **CPU 友好** - 只在访问时才执行删除操作，不消耗额外 CPU
- **实现简单** - 逻辑清晰，开销小

#### 缺点
- **内存不友好** - 如果大量过期 Key 长期不被访问，会一直占用内存
- **内存泄漏风险** - 过期但未访问的 Key 永远不会被删除

#### 适用场景
- 热点数据访问频繁的场景
- Key 访问分布均匀，过期后大概率会被再次访问

---

### 2. 定期删除（Periodic Expiration）

#### 概念
**主动触发**的删除策略，Redis 定期随机抽取一批设置了过期时间的 Key，检查并删除已过期的 Key。

#### 工作原理
Redis 默认每秒执行 10 次过期扫描（serverCron 函数）：

```
每 100ms 执行一次：
1. 随机抽取 20 个（默认）设置了过期时间的 Key
2. 删除其中所有已过期的 Key
3. 如果过期 Key 比例超过 25%，重复步骤 1
4. 单次执行时间不超过 25ms，避免阻塞主线程
```

#### 配置参数
```bash
# redis.conf 配置

# 定期删除频率（默认 10，即每秒 10 次）
hz 10

# 每次检查的 Key 数量（默认 20）
# 这个参数在源码中硬编码，通常不可配置
```

#### 优点
- **内存友好** - 主动清理过期 Key，避免内存浪费
- **控制可预测** - 通过 `hz` 参数可调节执行频率

#### 缺点
- **CPU 消耗** - 需要定期执行扫描操作
- **删除不及时** - 随机抽样可能遗漏部分过期 Key
- **可能阻塞** - 大量 Key 过期时，单次清理时间可能较长

#### 适用场景
- 存在大量设置过期时间的 Key
- 需要主动回收内存的场景
- 冷数据较多，访问频率低的场景

---

### 3. 两种策略的对比

| 对比项 | 惰性删除 | 定期删除 |
|--------|----------|----------|
| **触发方式** | 被动（访问时） | 主动（定时任务） |
| **CPU 消耗** | 低（按需删除） | 相对较高（周期执行） |
| **内存占用** | 高（可能积压） | 低（主动清理） |
| **删除及时性** | 不及时 | 相对及时 |
| **实现复杂度** | 简单 | 复杂 |
| **典型问题** | 内存泄漏 | CPU 波动 |

---

redis默认**两种策略同时生效**，你没得选。

#### 你设置过期时间后，Redis 同时做两件事

```
SET key "value" EX 100
        │
        ▼
  记录过期时间戳
        │
        ├─────────────────────────────────┐
        │                                 │
        ▼                                 ▼
   惰性删除                           定期删除
  （被动触发）                        （主动触发）
  有人访问时检查                   后台定时随机扫描
  发现过期就删除                    发现过期就删除
```

这两个机制是 Redis 内部自动运行的，**不需要也不能单独配置选哪个**。

---

#### 所以你平时用的时候

```bash
SET key "hello" EX 60
```

你只是设置了过期时间，底层同时跑着这两套机制。至于这个 key 最终被哪种方式删掉——

- 如果 60 秒内有人访问过它且已过期 → 惰性删除干掉的
- 如果没人访问，后台扫到了 → 定期删除干掉的
- 如果后台一直没扫到 → 一直占着内存，直到被惰性删除或内存淘汰策略处理

**你感知不到区别，也不需要关心是哪个删的。**

---

#### 什么时候需要关心这个？

面试或排查问题时：

> "为什么 key 过期了，内存没有立刻降下来？"

答案就是：定期删除是随机抽样的，不保证及时；惰性删除要等访问触发。过期不等于立刻释放内存。


### 4. 组合使用的必要性

Redis **同时使用两种策略**，互补优势：

#### 为什么不能只用惰性删除？
```bash
# 场景：设置 100 万个 Key，5 秒后过期
SETEX key1 5 "value1"
SETEX key2 5 "value2"
...
SETEX key1000000 5 "value1000000"

# 5 秒后这些 Key 都过期了，但如果没有访问
# 它们会一直占用内存，造成内存泄漏
```

#### 为什么不能只用定期删除？
```bash
# 定期删除每次只随机抽取 20 个 Key
# 如果有 1000 万个过期 Key，清理完需要很长时间
# 期间会持续占用大量内存
```

---

### 5. 实际应用场景

#### 场景 1：会话管理（Session）
```bash
# 用户登录后创建 Session，30 分钟过期
SETEX session:user123 1800 "user_data"

# 用户活跃时会频繁访问 → 惰性删除生效
# 用户不活跃时 → 定期删除兜底清理
```

#### 场景 2：短信验证码
```bash
# 验证码 5 分钟有效
SETEX sms:13800138000 300 "123456"

# 用户输入验证码时触发惰性删除
# 用户忘记输入，定期删除在后台清理
```

#### 场景 3：缓存数据
```bash
# 缓存热点商品信息，1 小时过期
SETEX product:1001 3600 "product_info"

# 热点商品频繁访问 → 惰性删除
# 冷门商品少人问津 → 定期删除
```

---

#### 6. 内存淘汰策略（兜底方案）

当内存不足时，即使有定期删除和惰性删除，Redis 还会启用**内存淘汰策略**（maxmemory-policy）：

```bash
# redis.conf 配置
maxmemory 2gb
maxmemory-policy allkeys-lru
```

**常见淘汰策略：**
- `noeviction` - 禁止写入，返回错误（默认）
- `allkeys-lru` - 淘汰最少使用的 Key
- `volatile-lru` - 只淘汰设置了过期时间的 Key 中最少使用的
- `allkeys-random` - 随机淘汰
- `volatile-ttl` - 淘汰剩余 TTL 最短的 Key

---

### 7. 最佳实践建议

#### 优化建议
```bash
# 1. 合理设置 hz 参数（默认 10）
hz 10  # 不建议设置过高，避免 CPU 消耗

# 2. 监控过期 Key 数量
INFO stats | grep expired_keys

# 3. 避免同时大量 Key 过期
# 错误示例：所有 Key 在整点过期
EXPIRE key1 3600
EXPIRE key2 3600
...

# 正确示例：添加随机时间，分散过期时间
EXPIRE key1 (3600 + random(0, 300))
```

### 监控指标
```bash
# 查看过期 Key 相关统计
redis-cli INFO stats

# 关键指标
expired_keys:12345        # 累计过期删除的 Key 数
evicted_keys:0            # 内存淘汰删除的 Key 数
keyspace_hits:100000      # 命中次数
keyspace_misses:5000      # 未命中次数（可能已过期）
```

---

## 总结

- **惰性删除**：访问时检查，CPU 友好但可能积压内存
- **定期删除**：周期性扫描，内存友好但消耗 CPU
- **组合使用**：两种策略互补，平衡内存和 CPU
- **兜底机制**：内存淘汰策略作为最后防线

**核心思想：** 用少量的 CPU 时间换取及时的内存释放，同时避免持续的性能开销。

## Redis主从模式宕机处理方式？

### 1. Slave宕机
相对简单：
- Slave重启后会自动重连Master
- 执行增量同步或全量同步（取决于断线时间和复制积压缓冲区情况）
- 数据自动恢复到最新状态

### 2. Master宕机

#### **重要说明：主从模式 vs 哨兵模式 vs 集群模式**

**纯主从模式（没有哨兵）：**
- ❌ **不能自动故障转移**
- 仅提供数据备份和读写分离
- Master宕机需要手动处理
  - 需要手动执行 `SLAVEOF NO ONE` 提升从库
  - 需要手动修改应用配置指向新主库`SLAVEOF`
- 运维成本高，有服务中断时间

**哨兵模式（Sentinel）：**
- ✅ **自动故障检测和转移**
- 哨兵集群通过投票机制（需要多数派同意）自动选举新Master
- 选举标准：优先级、复制偏移量、runid
- 自动通知客户端新Master地址
- 原Master恢复后自动降级为Slave
- **这才是生产环境的标准配置**

#### 哨兵模式故障转移流程：
```
1. 主观下线检测（单个哨兵判断）
2. 客观下线确认（多数哨兵投票确认）
3. 选举Leader哨兵执行故障转移
4. 从Slave中选举新Master（投票机制）
5. 其他Slave指向新Master
6. 通知客户端新Master地址
```

## Redis主从复制是如何实现？主从复制的原理？

Redis 主从复制是一个异步复制过程,主要包括以下几个阶段:

### 1. **建立连接阶段**

从节点执行 `slaveof <master_ip> <master_port>` 命令后:
- 从节点保存主节点信息
- 从节点与主节点建立 socket 连接
- 从节点发送 PING 命令检测连通性
- 进行身份验证(如果配置了密码)

### 2. **数据同步阶段**

这是核心环节,分为**全量复制**和**增量复制**:

**全量复制(首次同步)**
- 从节点发送 `PSYNC ? -1` 命令请求同步
- 主节点执行 `BGSAVE` 生成 RDB 快照文件
- 主节点将 RDB 文件发送给从节点
- 在生成 RDB 期间,主节点会将新的写命令记录到复制缓冲区(replication buffer)
- 从节点接收并加载 RDB 文件
- 主节点将缓冲区中的增量命令发送给从节点

**增量复制(断线重连)**
- 从节点发送 `PSYNC <runid> <offset>` 命令
- 主节点检查复制积压缓冲区(replication backlog)中是否还有对应偏移量的数据
- 如果有,则只发送缺失的部分;如果没有,则退化为全量复制

```
从服务器重连 → 发送PSYNC <runid> <offset>
              ↓
主服务器判断：
- Run ID匹配 && offset在backlog范围内 → 部分重同步
- 否则 → 完整重同步
```

### 3. **命令传播阶段**

同步完成后,主节点会持续将写命令异步发送给从节点:
- 主节点执行写命令后,将命令发送到复制缓冲区
- 从节点接收并执行这些命令,保持数据一致

### 4. **心跳检测**

- 从节点默认每秒向主节点发送 `REPLCONF ACK <offset>` 命令
- 作用包括:检测网络连接状态、辅助实现 min-slaves 功能、检测命令丢失

### 关键机制

**复制偏移量(offset)**: 主从节点各自维护,用于标识复制进度

**复制积压缓冲区**: 主节点维护的一个固定大小的 FIFO 队列,默认 1MB,用于支持部分重同步

**runid**: 主节点的唯一标识,用于判断主节点是否发生变化

这种设计使得 Redis 主从复制既高效又可靠,能够在网络抖动等异常情况下快速恢复。

## 是否使用过Redis集群，集群的原理是什么？

### **1. Redis Sentinel**
- ✅ 着眼于高可用
- ✅ 自动故障转移
- ⚠️ **但也只有一个Master提供写服务**
- ⚠️ **存在性能和容量瓶颈**（单点写入）
- 适合：中小规模、对可用性要求高但数据量不大的场景

### **2. Redis Cluster**
- ✅ 着眼于扩展性（水平扩展）
- **自动故障转移(高可用)**：Master宕机，其Slave自动投票晋升
- **数据分片**：16384个hash slot分配给多个Master, 多个Master节点同时提供读写服务
- **路由机制**：CRC16(key) % 16384 计算slot，客户端重定向
- **自动故障转移**：Master宕机，其Slave自动投票晋升
- **去中心化**：无代理，客户端直连数据节点

- 适合：大数据量、高并发、需要水平扩展的场景

## Twemproxy 的概念与工作原理

**核心概念：**
Twemproxy 是一个轻量级的 Redis 代理中间件，作为客户端和 Redis 服务器之间的代理层。

**工作原理：**
- 客户端连接 Twemproxy 而非直接连接 Redis
- Twemproxy 使用一致性哈希算法将请求路由到后端的多个 Redis 实例
- 接收 Redis 响应后，将结果返回给客户端
- 对于应用层来说，使用方式与单机 Redis 完全相同

**优势：**
- 部署简单，只需修改连接配置
- 适合旧项目的平滑扩展

**存在的问题：**
- Twemproxy 本身可能成为性能瓶颈
- 节点数量变化时，一致性哈希结果改变
- 数据无法自动迁移到新节点，需要手动处理

**实现思路：**

- 根据哈希结果路由到对应的 Redis 实例

**需要考虑的关键问题：**

- 实例健康检查与监控告警
- 一致性哈希或其他分片算法的选择
- 连接池管理和性能优化

**适用场景：**
对技术团队要求较高,需要完全掌控分片逻辑的场景。

## 分布式 Redis 应该在什么阶段规划?

**建议：尽早规划，前期就采用分布式架构。**

**原因分析：**
- Redis 单实例资源占用极小(约 1MB 内存)
- 即使在单台服务器上,也可以运行多个 Redis 实例实现分布式
- 前期规划好分片策略,后期扩容只需迁移实例,而非重新设计架构

**最佳实践：**
- 初期就启动 32 或 64 个实例进行分片
- 数据增长需要更多服务器时,只需将实例迁移到新服务器
- 避免后期扩容时的数据重新分片和业务中断

## Redis 内存用完后会发生什么?

**默认行为：**
- 写命令返回错误信息 (OOM 错误)
- 读命令仍可正常执行

**解决方案：**
配置内存淘汰策略 (maxmemory-policy):
- **noeviction** - 拒绝写入 (默认)
- **allkeys-lru** - 淘汰最近最少使用的 Key
- **volatile-lru** - 淘汰设置了过期时间的 Key 中最少使用的
- **allkeys-random** - 随机淘汰任意 Key
- **volatile-random** - 随机淘汰有过期时间的 Key
- **volatile-ttl** - 淘汰即将过期的 Key

## 如何实现缓存与数据库双写一致性问题?

### 问题背景

当系统同时使用缓存和数据库时，更新操作需要同时修改两个存储，这就产生了**双写一致性问题**。由于网络延迟、并发操作等因素，很容易导致缓存和数据库的数据不一致。

### 常见的不一致场景

#### 场景1：先更新数据库，再删除缓存
- 线程A更新数据库成功
- 线程A删除缓存失败（网络问题）
- 结果：缓存中是旧数据，数据库是新数据

#### 场景2：先删除缓存，再更新数据库
- 线程A删除缓存
- 线程B读取缓存（未命中），从数据库读取旧值并写入缓存
- 线程A更新数据库
- 结果：数据库是新数据，缓存是旧数据

### 主流解决方案

#### 1. **Cache Aside Pattern（旁路缓存模式）** - 最常用

**读操作**：先读缓存，未命中则读数据库，然后写入缓存

**写操作**：先更新数据库，再删除缓存（而不是更新缓存）

**为什么删除而不是更新？**
- 更新缓存可能涉及复杂计算，消耗资源
- 如果是低频访问的数据，更新缓存可能浪费
- 删除缓存更简单，下次读取时自动加载最新数据

**如何保证一致性？**
```
1. 延迟双删策略：
   - 更新数据库
   - 删除缓存
   - 延迟N秒（如500ms-1s）
   - 再次删除缓存
   
2. 使用消息队列保证删除成功：
   - 更新数据库
   - 发送删除缓存消息到MQ
   - 消费者删除缓存，失败则重试
```

#### 2. **Read/Write Through Pattern（读写穿透）**

由缓存层统一管理数据库和缓存的读写，应用层只与缓存交互。这种模式实现复杂，但一致性更好。

#### 3. **Write Behind Pattern（异步回写）**

先更新缓存，异步批量更新数据库。性能最好，但可能丢失数据，适合对一致性要求不高的场景（如浏览量统计）。

#### 4. **订阅数据库binlog（推荐方案）**

通过Canal等工具订阅MySQL的binlog，当数据库发生变更时：
- 自动同步到缓存
- 或删除对应的缓存
- 保证最终一致性

**优点**：
- 业务代码无侵入
- 可靠性高
- 解耦数据库和缓存操作

详情参考：[binlog订阅方案详解](../../article/binlog订阅方案.md)

### 串行化方案

将同一个数据的读写请求放入同一个内存队列，按顺序执行。这样可以保证**强一致性**，但会带来严重的性能问题：

- 吞吐量大幅下降
- 响应时间增加
- 需要更多机器资源

**适用场景**：金融交易、库存扣减等对一致性要求极高的场景

**实现方式**：
- 根据数据ID进行hash，路由到固定的队列
- 每个队列单线程处理
- 类似Actor模型

### 实际选择建议

#### 对于大多数业务场景（允许短暂不一致）：
- 使用Cache Aside + 延迟双删
- 或使用binlog订阅方案
- 设置合理的缓存过期时间作为兜底

#### 对于强一致性要求的场景：
- 不使用缓存，直接访问数据库
- 或使用分布式锁 + 串行化
- 或使用分布式事务（如Seata）

### 总结

缓存一致性问题本质上是**CAP理论**的体现，在分布式系统中很难同时保证一致性和高可用性。实际应用中需要根据业务特点，在一致性、性能、复杂度之间做出权衡。
