## 核心概念

### Memcached 是什么？

Memcached 是一个高性能的分布式内存对象缓存系统，用于加速动态 Web 应用程序，减轻数据库负载。它通过在内存中缓存数据和对象来减少读取数据库的次数。

### 基本特点

- **非阻塞的事件驱动架构**：能够很好地解决 C10K 问题
- **分布式存储**：支持多节点部署
- **简单的键值存储**：类似巨大的哈希表
- **LRU 淘汰策略**：自动管理内存

## 架构与原理

### 工作原理：两阶段哈希

Memcached 采用**两阶段哈希（Two-Stage Hash）**机制：

#### 第一阶段：客户端哈希（节点选择）
客户端根据 key 计算哈希值，确定数据应该存储在哪个 Memcached 节点上。

#### 第二阶段：服务端哈希（数据定位）
选中的 Memcached 节点使用内部哈希算法，在节点内部定位具体的数据项（item）。

### 工作流程示例

假设有 3 个客户端（Client 1, 2, 3）和 3 台 Memcached 服务器（A, B, C）：

**存储流程：**
1. Client 1 想存储数据 "barbaz"，key 为 "foo"
2. Client 1 对 key "foo" 进行哈希计算，假设选中了节点 B
3. Client 1 直接连接到 Memcached B，存储数据

**读取流程：**
1. Client 2 使用相同的客户端库和节点列表
2. 对 key "foo" 进行相同的哈希计算，同样定位到节点 B
3. Client 2 直接从 Memcached B 获取数据 "barbaz"

### 架构特性

- **无中心节点**：节点之间不通信，避免网络风暴
- **客户端路由**：智能由客户端完成
- **独立节点**：每个节点独立运行，互不影响

## 性能优势

### 核心优势

#### 1. 极佳的水平扩展性
- 客户端完成哈希分片，易于添加节点
- 节点间无通信，不会增加额外负载
- 无多播协议，避免网络拥塞

#### 2. 灵活的集群管理
- **内存不足？** 添加更多节点
- **CPU 不够？** 增加服务器
- **有空闲内存？** 充分利用资源

#### 3. 高性能表现
- 基于事件驱动的非阻塞 I/O
- 多线程支持（1.2+ 版本）
- 简单高效的内存管理

## 对比分析

### Memcached vs MySQL Query Cache

| 特性 | Memcached | MySQL Query Cache |
|------|-----------|-------------------|
| **扩展性** | 优秀，可独立扩展 | 受限于单机内存 |
| **多核支持** | 良好 | 存在全局锁瓶颈 |
| **存储内容** | 任意数据 | 仅 SQL 查询结果 |
| **失效机制** | 灵活控制 | 表更新时全部失效 |
| **写密集场景** | 适合 | 频繁失效，性能下降 |

**适用场景：**
- **小型网站**：Query Cache 简单够用
- **大型网站**：Memcached 更具优势

### Memcached vs Local Cache（APC、mmap 等）

| 特性 | Memcached | Local Cache |
|------|-----------|-------------|
| **访问速度** | 有网络延迟 | 最快（本地内存） |
| **容量限制** | 集群总内存 | 单机内存 |
| **集群失效** | 支持全局失效 | 需逐台通知或超时 |
| **数据一致性** | 较好 | 各节点可能不一致 |

**最佳实践：**
- **高频小数据**：放在 Local Cache
- **大量共享数据**：使用 Memcached
- **混合使用**：两级缓存架构

## 缓存机制

### LRU + 超时失效

Memcached 采用 **LRU（Least Recently Used）** 算法结合超时机制：

#### 淘汰策略
1. **优先淘汰**：已过期的 slabs
2. **次优淘汰**：最久未使用的 slabs
3. **按需分配**：不预加载数据

#### 过期时间设置
- **最大时长**：30 天
- **时间格式**：
  - 相对时间：秒数（如 3600 表示 1 小时）
  - 绝对时间：Unix 时间戳
- **永不过期**：设置为 0

### 内存管理：Slab Allocation

#### Slab 结构
- 内存被划分为不同大小的 slabs
- 每个 slab 包含相同大小的 chunks
- Chunk 大小按因子递增（默认 1.25）

#### 示例（最小 400B，因子 1.20）
```
slab1 → 400B
slab2 → 480B
slab3 → 576B
...
```

## 容错与冗余

### 设计哲学

> **Memcached 不提供冗余机制！**

这是设计选择，不是缺陷。Memcached 是**缓存层**，不是**持久化存储层**。

### 核心原则

1. **缓存失效是正常的**：应用必须能从数据源（数据库）重新加载数据
2. **不依赖缓存**：缓存是加速手段，不是数据源
3. **容忍失败**：节点失效不应导致应用崩溃

### 节点失效处理方案

#### 方案 1：忽略失效节点
- 依靠其他节点分担负载
- 等待节点恢复或替换

#### 方案 2：移除失效节点
⚠️ **风险**：使用余数哈希时，会导致大量缓存失效

#### 方案 3：热备节点接管
- 备用节点接管失效节点的 IP
- 避免哈希值变化

#### 方案 4：一致性哈希（推荐）
- 添加/移除节点时影响最小
- 只影响相邻节点的数据
- 客户端库广泛支持

#### 方案 5：二次哈希（Rehashing）
- 第一次哈希失败时，使用不同算法再次哈希
- ⚠️ **风险**：可能产生脏数据

### 应对策略建议

- **增加节点**：降低单点失效影响
- **监控告警**：及时发现问题
- **优化查询**：避免缓存雪崩时数据库压力过大
- **限流降级**：缓存失效时保护后端

## 安全与配置

### 身份认证

**Memcached 不提供身份认证！**

#### 设计理由
- 轻量级设计，快速创建连接
- 认证应该在应用层实现
- 避免增加复杂性

#### 安全建议
- **防火墙**：限制访问 IP
- **内网部署**：不暴露到公网
- **Unix Socket**：本地通信使用 socket
- **VPN/专网**：隔离网络环境

### 多线程模式

#### 启用场景
- 多核 CPU 服务器
- 高负载、高并发场景
- 需要充分利用硬件资源

#### 工作机制
- 命令解析：多线程并行
- 数据操作：基于全局锁（未来优化方向）
- 比单机多实例更高效（尤其是 multi-get 操作）

#### 启用方法
```bash
memcached -t 4  # 使用 4 个线程
```

## 技术限制

### Key 限制

| 项目 | 限制 | 说明 |
|------|------|------|
| **最大长度** | 250 字符 | 服务端限制 |
| **客户端前缀** | 可超过 250 | 如果客户端支持前缀功能 |
| **建议** | 使用短 key | 节省内存和带宽 |

### Value 限制

| 项目 | 限制 | 说明 |
|------|------|------|
| **最大值** | 1MB | 默认配置 |
| **修改方法** | 修改 `slabs.c:POWER_BLOCK` | 需重新编译 |

#### 为什么限制 1MB？

1. **内存分配器算法**：Slab 最大 chunk 设计
2. **内存利用率**：更大的值降低内存效率
3. **性能考虑**：大数据 load/unpack 耗时长

#### 超过 1MB 的数据怎么办？

- **客户端压缩**：减小数据体积
- **拆分存储**：分成多个 key
- **使用数据库**：MySQL、PostgreSQL
- **对象存储**：MogileFS、CouchDB、S3
- **混合方案**：热数据缓存，完整数据存数据库

### 过期时间限制

- **最大值**：30 天（2,592,000 秒）
- **超过 30 天**：被解释为 Unix 时间戳

## 最佳实践

### 数据导入导出

#### 为什么不建议批量导入导出？

1. **阻塞风险**：可能导致服务暂停
2. **数据一致性**：导出导入期间数据可能变化
3. **过期问题**：数据可能已过期

#### 适用场景

- 不变的静态数据
- 系统预热（warm-up）
- 数据迁移

#### 替代方案

**方案 1：使用 MogileFS**
- 预计算数据并存储到 MogileFS
- Memcached 作为 MogileFS 的缓存层
- 缓存未命中时从 MogileFS 加载

**方案 2：MySQL 存储**
```sql
CREATE TABLE cache_data (
    key_hash BIGINT PRIMARY KEY,
    key_original VARCHAR(255),
    value BLOB,
    created_at TIMESTAMP,
    INDEX(key_original)
);
```
- Key 哈希为 64 位整数作为主键
- 主键查询速度接近 Memcached
- 支持二级索引和批量清理

### 缓存策略

#### Cache-Aside（旁路缓存）
```python
def get_user(user_id):
    # 1. 尝试从缓存读取
    user = memcache.get(f"user:{user_id}")
    if user:
        return user
    
    # 2. 缓存未命中，从数据库读取
    user = db.query("SELECT * FROM users WHERE id = ?", user_id)
    
    # 3. 写入缓存
    memcache.set(f"user:{user_id}", user, expire=3600)
    return user
```

#### 防止缓存雪崩

**问题**：大量缓存同时失效，数据库压力骤增

**解决方案：**
1. **过期时间加随机值**
```python
expire = 3600 + random.randint(0, 300)  # 3600-3900 秒
```

2. **互斥锁**：避免惊群效应
```python
def get_with_lock(key):
    value = cache.get(key)
    if value:
        return value
    
    # 尝试获取锁
    if cache.add(f"lock:{key}", 1, expire=10):
        try:
            value = load_from_db(key)
            cache.set(key, value)
            return value
        finally:
            cache.delete(f"lock:{key}")
    else:
        # 等待其他线程加载完成
        time.sleep(0.1)
        return get_with_lock(key)
```

3. **提前刷新**：后台定时更新热点数据

#### 防止缓存穿透

**问题**：查询不存在的数据，每次都打到数据库

**解决方案：**
```python
# 缓存空值
if not user:
    memcache.set(f"user:{user_id}", None, expire=300)
```

### 节点配置建议

#### 不同内存大小的节点

- **可行**：Memcached 支持异构集群
- **常见做法**：大内存节点运行多个实例
  ```bash
  # 32GB 服务器运行 4 个实例，每个 8GB
  memcached -m 8192 -p 11211 -u memcache
  memcached -m 8192 -p 11212 -u memcache
  memcached -m 8192 -p 11213 -u memcache
  memcached -m 8192 -p 11214 -u memcache
  ```

#### 监控指标

- **命中率**：`get_hits / (get_hits + get_misses)`
- **内存使用率**：`bytes / limit_maxbytes`
- **淘汰率**：`evictions` 增长速度
- **连接数**：`curr_connections`

## 常见面试问题

### Q1: Memcached 和 Redis 的区别？

| 特性 | Memcached | Redis |
|------|-----------|-------|
| 数据类型 | 简单 key-value | 丰富数据结构（string、hash、list 等） |
| 持久化 | 不支持 | 支持 RDB、AOF |
| 分布式 | 客户端分片 | 原生 Cluster |
| 线程模型 | 多线程 | 单线程（6.0 后支持多线程 I/O） |
| 内存管理 | Slab Allocation | jemalloc |
| 适用场景 | 简单缓存 | 缓存 + 部分数据存储 |

### Q2: 如何保证 Memcached 的高可用？

1. **客户端容错**：一致性哈希 + 自动摘除故障节点
2. **多副本**：业务层实现双写
3. **监控告警**：及时发现问题
4. **热备节点**：快速切换
5. **限流降级**：保护后端服务

### Q3: Memcached 的内存回收机制？

- **Lazy Expiration**：访问时检查是否过期
- **LRU 淘汰**：内存不足时淘汰最少使用的
- **Slab 分配**：避免内存碎片

### Q4: 如何监控 Memcached？

```bash
# 查看统计信息
echo "stats" | nc localhost 11211

# 关键指标
- cmd_get/cmd_set: 读写次数
- get_hits/get_misses: 命中情况
- evictions: 淘汰次数
- bytes/limit_maxbytes: 内存使用
```

## 总结

### 核心要点

1. **定位明确**：Memcached 是缓存，不是数据库
2. **架构简单**：两阶段哈希，无中心节点
3. **扩展性强**：水平扩展，线性增长
4. **高性能**：事件驱动，多线程支持
5. **易于使用**：协议简单，客户端丰富

### 使用建议

- ✅ **适合**：高并发读、热点数据缓存、Session 存储
- ❌ **不适合**：需要持久化、复杂数据结构、分布式锁
